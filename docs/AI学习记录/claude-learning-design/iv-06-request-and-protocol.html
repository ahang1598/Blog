Chapter 6 · 面试视角（6/7）

请求双层类型 + compile 墙 + promptCacheKey

从"runner 想要一次推理"到"provider 收到 HTTP 字节"，中间有两道精心设计的墙：第一道把宽容的调用输入归一成严格的 LLMRequest（类型错误留在边界）；第二道 compile 墙把与 provider 无关的 LLMRequest 翻译成 provider 专属的 HTTP body（让加一个 provider 只改一个文件）。再加一个 promptCacheKey，让长 session 的系统块只付一次钱。

① 定位 ② 问题先于方案 ③ 设计拆解 ④ 生产级取舍 ★ 完整示例 ⑤ 双视角 🎯 面试追问

1一句话定位

第一层（lenient 输入）：runner 用宽容的 RequestInput 调 LLM.request(...)——system 可以是 string/数组、messages 可以是未构造的、prompt 是快捷方式。第二层（strict LLMRequest）：工厂把它 normalize 成一个 schema 严格、可比较、已校验的 LLMRequest，整个下层（路由/缓存/compile）只看这个。compile 墙：LLMRequest 到 provider HTTP body 之间的一道墙，集中校验 + 翻译。

🔑 一句话

两层类型把调用便利和下游严格分开；compile 墙把API 形状和部署细节分开。错误留在边界，下游永远干净。

2问题先于方案

如果只有一层类型、或 compile 在 runner 里直接拼 body，会发生什么？

痛点 A · 调用点样板爆炸

如果只有 strict 类型，每个调用点都得手动构造 SystemPart、Message、ContentPart……runner 代码被样板淹没，教程没法写，prompt: 快捷方式消失。

痛点 B · 错误推迟到 provider

如果只有 lenient，下游收到半构造的形状。malformed 输入在 provider 返回 400 时才暴露——错误远离根因，难诊断。

痛点 C · 加 provider = 改 runner

如果 compile 在 runner 里，每加一个 provider 就得动 runner 的 body 构造逻辑。N 个 provider = N 处 runner 改动，爆炸半径失控。

痛点 D · 缓存策略散落

没有 compile 墙，cache breakpoint 在每个 provider adapter 里各自推导。一次缓存策略变更 = N 处改动，且容易漏。

⚠ 共同病根

把"便利"、"严格"、"翻译"、"部署"四种关注点焊在一起。每一处改动都波及所有维度。

3设计拆解

两道墙，三个受益方。

三个设计点详解

① lenient → strict 两层类型

调用点用宽容输入（少样板）；工厂 normalize 成 strict LLMRequest（一次校验，下游不再校验）。类型错误留在工厂边界。

② promptCacheKey

从 sessionID 派生的稳定 key，让 provider 把同一 session 的请求路由到同一缓存桶。系统块只付一次钱，后续轮次命中缓存折扣。

③ compile 墙

LLMRequest → provider body 的集中翻译点。body schema 在这校验（HTTP 前拦错）；cache policy 在这施加（一处改全局生效）。

📌 Protocol ≠ Route（API 形状 ≠ 部署）

compile 墙还把"这个 API 长什么样"（Protocol：body.from、event codec、step 状态机）和"发去哪"（Route：URL、auth、framing）分开。Anthropic Cloud / Vertex-Anthropic / Bedrock-Anthropic 共享同一个 Protocol，只换 Route——这是 compile 墙带来的组合能力。

4生产级取舍

每道墙/层都有维护成本，但收益数量级地大于成本。

选择：两层类型

  • 调用点可读、样板少
  • 下游单一已校验对象
  • 类型错误在工厂边界暴露

合成一层的代价

  • strict-only：样板爆炸、教程难写
  • lenient-only：错误漏到 provider 400
  • 缓存/选项施加在半构造形状上

选择：compile 墙 + promptCacheKey

  • 加 provider 一个文件
  • 缓存策略一处施加全局生效
  • 长 session 系统块只付一次钱
  • Protocol 与 Route 可组合

无墙/无 cacheKey 的代价

  • N provider = N 处 runner 改动
  • 缓存策略散落、易漏
  • 系统块每轮全价（成本数量级上升）
  • 部署与 API 形状耦合死
🔑 本质

这套设计的核心是把关注点正交化：便利 / 严格 / 翻译 / 部署，各归各位。任何一处改动只动它那一层。这是可维护性的根基。

过 compile 墙后：Anthropic HTTP body（节选）

🔑 compile 做了三件事

① body.from(request) 把 LLMRequest 翻成 Anthropic 形状；② body.schema 校验（HTTP 前拦错）；③ applyCachePolicy 在 system/messages 上钉 cache_control 断点——一处施加，所有 provider 的 body.from 都能看到。

POST https://api.anthropic.com/v1/messages headers: { "x-api-key": ***, "anthropic-version": "2023-06-01" } body: { model: "claude-opus-4-1", system: [ { type: "text", text: "You are an expert...", cache_control: { type: "ephemeral" } // ← 断点：到此为止可缓存 }, { type: "text", text: "..." } ], messages: [ /* to-llm-message 投影的 messages，结构同上 */ ], tools: [ /* materialize 的工具，转成 Anthropic tool schema */ ], max_tokens: 8192, stream: true } // 响应：SSE → LLMEvent 流（message_start / content_block_delta / ...） // → 每个 event 增量写 durable log（iv-05）→ 模型可见状态单一真相源

5面试双视角

这题考的是成本意识 + 可扩展性设计——你懂不懂 prompt cache 经济学，懂不懂"加 provider 不动核心"。

🎙️ 面试官为何问这题

  1. 探 prompt cache 经济学——知不知道 promptCacheKey 省什么、不省什么。
  2. 探类型设计成熟度——能不能说出 lenient/strict 两层各买什么。
  3. 探可扩展性——加一个 provider 要改几处？compile 墙的价值。
  4. 埋雷：很多人答"用接口隔离 provider"。追问"接口在哪施加缓存断点？"——看你能不能答出"compile 墙集中施加"。

🧑‍💻 面试者拆解（五段式）

  1. 抽象定位：两道墙正交化四个关注点（便利/严格/翻译/部署），错误留边界，下游干净。
  2. 讲约束：lenient 输入 → normalize → strict LLMRequest → compile 墙 → provider body；promptCacheKey 派生自 sessionID。
  3. 讲收益：调用点可读；类型错误在工厂；加 provider 一个文件；cache 一处施加；长 session 系统块只付一次钱。
  4. 主动讲代价：两层类型多一层维护；compile 墙多一道间接。但远小于"样板爆炸/N 处改动/缓存散落"的代价。
  5. 给未来演化：Protocol 与 Route 分离是部署灵活性的接缝——同 provider 可上多云（Cloud/Vertex/Bedrock），只换 Route。
✅ 加分项

主动量化收益："一个 3000 token 的 system 数组，50 轮对话。无 cacheKey：50 × 3000 = 15 万全价输入 token。有 cacheKey + 命中：约 1 × 3000 全价 + 49 × 缓存折扣。省一个数量级的输入成本。"——把设计决策翻译成钱，是最有说服力的面试信号。
