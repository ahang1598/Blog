SystemContext 代数 + epoch 快照

系统提示词里那串"你在哪个目录、今天是几号、有哪些 skill"的环境信息，看起来只是拼字符串——但它是每轮都进 prompt cache 前缀的长寿命状态。每轮重建它，会因时间戳/排序的微小不确定让前缀字节漂移，把缓存读打回全价输入。opencode 把它建成一个代数：initialize / reconcile / replace，并给每个 session 钉一个 epoch 快照来对抗这种漂移。

① 定位 ② 问题先于方案 ③ 设计拆解 ④ 生产级取舍 ⑤ 双视角 🎯 面试追问

1一句话定位

SystemContext 是一组可组合的、缓慢变化的上下文源（环境、日期、skill 指引、reference 指引），它有三段操作：initialize（首次生成 baseline + 落一个结构化快照）、reconcile（拿当前观察和"已 admit 的快照"做 diff，只发真正变化的增量）、replace（重建整个 baseline，但只有当所有源都能再观察到时才行）。每个 session 一行 epoch 记录，存住"已 admit 的 baseline 文本 + 快照 + 一个 baselineSeq 锚点"。

🔑 一句话

不是"每轮拼一遍环境字符串"，而是"对照上次 admit 的快照做最小差异，让缓存前缀字节稳定"。epoch 是这稳定性的锚。

2问题先于方案

如果每轮都重新拼接环境信息塞进 system prompt，生产里会出什么问题？这些不是假想——是真实会发生的成本和正确性陷阱。

痛点 A · 缓存抖动（cache thrashing）

环境渲染有任何不确定（时间戳秒级变化、文件列表顺序波动、尾部空白），system 字符串就每轮不一样。Provider 的 prompt cache 是按前缀字节匹配的——前缀一变，缓存读变全价读。50 轮对话付 50 次系统块的钱。

痛点 B · 上下文漂移

没有"哪一份是权威 baseline"的概念，模型每轮看到一条新的"今天是 X / 环境是 Y"。历史里堆了一长串过时的环境描述，挤占上下文窗口，模型还可能引用到旧的。

痛点 C · 崩溃后无法对齐

进程在 turn 中间崩了。重启续跑时，你怎么知道"模型刚才看到的 baseline"是哪一份？没有锚点，续跑的请求可能用了一份不同的 baseline，模型上下文错位。

痛点 D · 不完整上下文被固化

一个源临时不可用（FS 没挂载、instruction 文件正写一半）。如果直接拼，模型第一次就看到一个残缺 baseline，并把它当"权威"记一辈子。残缺上下文被固化成 session 的世界观。

⚠ 共同病根

把"环境信息"当成无状态字符串。但它其实是有状态的长寿命模型可见状态——必须像对待数据库事务一样，有快照、有版本、有恢复契约。

3设计拆解

把环境信息建模成代数：每个源是一个 typed Source，三个操作解释它，组合它们得到整个 baseline。

三个操作的职责

initialize

session 第一次生成 baseline。所有源都必须可观察，否则 InitializationBlocked——拒绝在一个残缺上下文上启动 session。

reconcile

拿当前观察对比已 admit 的快照。源等价就复用存的字节（缓存前缀不动）；变了才发一个 update 增量消息。

replace

compaction 把 baselineSeq 推过 epoch，必须全量重建。若此时某源 unavailable，守住旧 baseline 而非造个残缺的新（ReplacementBlocked）。

📌 baselineSeq 是关键锚点

它指向"baseline 锚定在事件日志的哪个序号"。runner 投影历史时用它过滤：只投影这个 seq 之后的事件，保证 baseline 和历史是原子的对子。崩溃后续跑，靠它对齐"模型当时看到的 baseline"。

4生产级取舍

这套代数不是免费的——它引入了快照存储和 reconcile 复杂度。但对抗的是真金白银的缓存成本和上下文正确性。

选择：对照已 admit 快照做 reconcile

  • 源等价→复用字节→缓存前缀字节稳定
  • 只发真正变化的增量，不重写 system 块
  • baselineSeq 锚定历史投影，崩溃可对齐

每轮重建的代价

  • 渲染不确定→缓存抖动→50 轮付 50 次系统块
  • 无权威 baseline→上下文漂移堆积
  • 无锚点→崩溃续跑 baseline 错位

选择：InitializationBlocked / ReplacementBlocked

  • 残缺上下文不被固化为权威
  • 临时 FS 抖动不永久窄化模型视野
  • 守住旧 baseline，下轮重试

不守护栏的代价

  • 首次残缺→模型记一辈子错误世界观
  • compaction 时一源抖动→永久窄化
  • 难以诊断"为什么模型突然不知道 X"
🔑 本质

SystemContext 不是"拼字符串"，是把 prompt cache 当一等成本来设计。在多轮、长 session 的生产场景，缓存命中率直接决定账单数量级。这套代数把"字节稳定"从碰运气变成可推理的不变式。

5面试双视角

这题考的是成本意识 + 有状态系统设计——你是否意识到"系统提示词"是个有状态、长寿命、进缓存前缀的对象。

🎙️ 面试官为何问这题

  1. 探你懂不懂 prompt cache 经济学——知不知道前缀字节稳定=省钱，前缀漂移=全价。
  2. 探你把"环境信息"当无状态还是有状态——能不能识别它是长寿命模型可见状态。
  3. 探崩溃恢复直觉——续跑时怎么对齐 baseline？有没有锚点思维。
  4. 埋雷：很多人答"缓存就好"。追问"时间戳每秒变怎么办？"——看你能不能答出"对照已 admit 快照复用字节"。

🧑‍💻 面试者拆解（五段式）

  1. 抽象定位：环境信息是有状态的长寿命模型可见状态，进 prompt cache 前缀，必须按事务对待。
  2. 讲约束：三操作 initialize/reconcile/replace；reconcile 对照已 admit 快照做最小 diff；epoch 行存 baselineSeq 锚点。
  3. 讲收益：字节稳定→缓存命中→长 session 成本降一个数量级；崩溃可对齐；护栏防残缺固化。
  4. 主动讲代价：快照存储、reconcile 逻辑复杂、blocked 时下轮重试的延迟。但远小于缓存成本和正确性代价。
  5. 给未来演化：源是可注册的（registry）——加新上下文源（如用户偏好、团队规范）只需实现 Source 接口注册，不动 reconcile 主流程。
✅ 加分项

主动联系 iv-02："baselineSeq 锚点和 admission 的 durable log 是同一套可靠性思想的不同侧面——都是把'权威状态'落盘，让运行时可以崩溃/重跑而不丢一致性。" 能把多篇文章的设计哲学打通，是高级信号。
