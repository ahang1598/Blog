Chapter 10 · 智能体与工具（3/4）

工具调用全生命周期：一次完整往返

模型说"我要读 README.md"——这句话怎么变成 durable 事件、怎么被执行、结果怎么进下一轮历史？这条链路里藏着两个关键设计：① 工具调用在执行之前就先写进 durable log（崩溃可审计）；② 多个工具调用在 stream 期间就并发结算（eager，不等 stream 结束）。再加上 failUnsettledTools 兜底——任何崩溃路径都把悬挂的工具调用 fail-closed 关掉，保证 log 永远是可重放的。

① 定位 ② 问题先于方案 ③ 设计拆解 ④ 生产级取舍 ★ 完整示例 ⑤ 双视角 🎯 面试追问

1一句话定位

一次工具调用往返 = 模型在 stream 里 emit tool-call → 立刻写成 durable 的 Tool.Called 事件（执行前）→ 并发 settle（执行 + 产出结果）→ 写成 Tool.Success/Failed 事件 → 下一轮历史里看到 Message.tool(call+result)。两阶段持久化（先记调用、再记结果）+ eager 并发结算 + fail-closed 兜底，保证 log 永远自洽、可重放。

🔑 一句话

工具调用不是"调用一个函数"，是两个 durable 事件（Called + Success/Failed）的原子对。崩溃在任何点，log 都能告诉你"调用发了、执行没完成"，并把它 fail 掉。

2问题先于方案

如果工具调用只在内存里执行、结果直接塞回消息数组，生产里会怎样？

痛点 A · 悬挂调用（永远 pending）

模型 emit 了 tool-call，工具正在执行，进程崩了。log 里只有"模型要调用"，没有"结果"。下一轮重放时这个调用永远 pending，模型看到一个悬挂请求，要么盲目重试要么投影逻辑崩。

痛点 B · 串行结算慢

模型一条消息里 emit 了 5 个 read。如果在 stream 结束后串行执行，总延迟 = 5 个 read 之和。本可并发的 IO 被强行串行化，体验卡顿。

痛点 C · 崩溃不可审计

调用没写进 log 就执行。崩溃后无法知道"模型当时想调什么、执行到哪了"。没有审计线索，难以诊断"为什么仓库被改了"。

痛点 D · 工具崩了炸 stream

工具执行抛异常，直接打断整个 stream。一个工具失败 = 整轮失败，已流出的内容白费。

⚠ 共同病根

把"工具调用"当成"一次函数调用"，而不是"两个 durable 事件的原子对 + 可恢复的执行"。前者不可审计、不可恢复、不可并发；后者全可以。

3设计拆解

一次往返的时间线：先记调用、并发执行、再记结果，任何崩溃都有兜底。

三个关键设计

① 执行前先记 Called

模型 emit tool-call，立刻写 Tool.Called 事件（带名字、输入），然后才执行。崩溃后 log 知道"模型想调什么"，可审计。

② eager 并发结算

调用 fork 进 FiberSet，在 stream 期间就并发执行，不等 stream 结束。N 个 read 并发，总延迟≈最慢的一个。

③ fail-closed 兜底

任何崩溃/中断路径，failUnsettledTools 把所有未结算的调用写成 Tool.Failed。log 永远没有悬挂调用，可重放。

📌 settle 的契约：永远返回结果（成功或错误）

settle(input) 返回 { result, output?, outputPaths? }。工具抛异常会被捕获转成 {type:"error"}——工具崩不了 stream，只会产生一个失败的 ToolResult。这是"工具失败 ≠ 整轮失败"的保证。

4生产级取舍

两阶段持久化 + eager 结算有开销，但换来可审计、可恢复、可并发。

选择：执行前先记 Called + fail-closed

  • 崩溃可审计：log 知道想调什么
  • 悬挂调用被 fail，log 自洽
  • 下一轮重放必然一致

只在内存执行的代价

  • 悬挂调用永远 pending
  • 崩溃不可审计
  • 重放时投影逻辑崩

选择：eager 并发结算

  • N 个工具并发，延迟≈最慢的
  • stream 结束后 join（有屏障）
  • 工具失败不炸 stream（转 error 结果）

串行结算的代价

  • 5 个 read 串行，延迟=5 倍
  • 本可并发的 IO 被串行化
  • 体验卡顿
🔑 本质

工具调用是两个 durable 事件的原子对，不是函数调用。这个模型让"调用"变成可审计、可恢复、可并发的一等公民——和 iv-02/iv-05 的"durable log 是唯一真相源"一脉相承。

★完整示例：一次 read 调用的全旅程

用户说"读下 README"。从模型决策到下一轮历史，每一步都列出来。颜色对应阶段。

模型决策/stream durable 事件 工具执行 下一轮历史 注释
T1 · 模型在 stream 里决定调用
模型 emit 一个 tool-call 事件（name=read, input={path:"README.md"}）。这是 LLMEvent.tool-call，在 llm.stream 的 runForEach 里被接收。
T2 · 立刻写 Tool.Called（执行前！）
publisher 把这个调用写成 durable 的 SessionEvent.Tool.Called（callID、name、input）。此刻还没执行——先记下来。崩溃后 log 知道"模型想读 README"。
T3 · fork 进 FiberSet，eager 执行
runner 调 toolMaterialization.settle(...)，包在 uninterruptibleMask 里，fork 进 FiberSet。read 工具开始执行：解码 input、调 execute（读文件）、编码 output、过 ToolOutputStore（超限落盘+预览，见 iv-07）。stream 还在继续流。
T4 · stream 结束，await FiberSet
llm.stream 流完，runner join 所有工具 fiber。settle 返回 { result, output, outputPaths? }。工具抛异常会被捕获转成 {type:"error"}——崩不了 stream。
T5 · 写 Tool.Success / Failed
结算完成，写成 durable 的 SessionEvent.Tool.Success（带结构化 content + provider metadata）。失败写 Tool.Failed。Tool.Called + Tool.Success/Failed 是原子对。
T6 · 下一轮历史里看到它
continuation 重投影历史（iv-05）。to-llm-message 把这对事件投影成 Message.tool({ id, name, result })。下一轮的模型看到"我上轮读了 README，内容是 X"，基于结果继续。
💥 崩溃兜底
若 T3 执行中进程崩了，log 里只有 Tool.Called 没 Tool.Success。重启 drain 时 failInterruptedTools 把它写成 Tool.Failed（"interrupted"）。下一轮模型看到"上次读 README 失败了"，可决定重试。log 永远自洽。

durable log 里实际长什么样（事件序列）

// 一条 read 调用在 durable log 里产生的事件对： SessionEvent.Tool.Called { callID: "call_abc123", name: "read", input: { path: "README.md" }, assistantMessageID: "msg_001" } // ← T2 执行前先记 ... read 工具执行（FiberSet 并发）... SessionEvent.Tool.Success { callID: "call_abc123", // ← 与 Called 配对 result: { content: "# My Project\n..." }, outputPaths: [], // 小文件不必落盘 } // ← T5 结算后记 // ─── 下一轮 continuation 重投影（iv-05）─── messages: [ Message.user({ text: "读下 README" }), Message.assistant({ text: "我来读 README.md" }), Message.tool({ // ← Called+Success 投影成一条 id: "call_abc123", name: "read", result: { content: "# My Project\n..." } }) // 下一轮模型看到这对，基于内容继续 ] // ─── 崩溃场景：T3 执行中崩了 ─── // log 里只有 Called，没 Success。重启 drain： failInterruptedTools → SessionEvent.Tool.Failed { callID: "call_abc123", error: "interrupted" // ← 兜底关掉 } // 下一轮模型看到"读失败了"，自洽。log 永远可重放。
🎓 这个示例串起了 iv-02/05/07

Tool.Called 在执行前写进 durable log（iv-02 的两阶段持久化）；continuation 从 log 重投影这对事件成 Message.tool（iv-05 的纯函数历史）；超大 read 结果被 ToolOutputStore 落盘+预览（iv-07 的输出有界）。一次工具调用，三篇设计都在守护它。

5面试双视角

这题考的是分布式系统直觉 + 不变式思维——你能不能识别"工具调用是事件对，不是函数调用"。

🎙️ 面试官为何问这题

  1. 探事件溯源直觉——工具调用该不该先记再执行？崩溃怎么办？
  2. 探并发设计——多个工具调用串行还是并发？join 在哪？
  3. 探容错——工具崩了炸不炸 stream？悬挂调用怎么处理？
  4. 埋雷：很多人答"调用函数拿返回值"。追问"执行中崩了呢？"——看你能不能答出"两阶段持久化 + fail-closed"。

🧑‍💻 面试者拆解（五段式）

  1. 抽象定位：工具调用是两个 durable 事件的原子对（Called + Success/Failed），不是函数调用。
  2. 讲约束：执行前先记 Called；eager fork 进 FiberSet 并发；stream 结束 join；任何崩溃走 failUnsettledTools。
  3. 讲收益：可审计（log 知道想调什么）；可恢复（fail-closed 让 log 自洽）；可并发（延迟≈最慢工具）；工具崩不了 stream。
  4. 主动讲代价：两阶段持久化多一次写；FiberSet 并发有调度开销。但远小于"悬挂/串行/不可审计"的代价。
  5. 给未来演化：settle 是 ToolRegistry 的扩展点——加 provider-executed 工具（web search）只需跳过本地 settle，复用同一事件契约（见 iv-11）。
✅ 加分项

主动联系数据库/消息队列："这和 WAL（write-ahead log）、两阶段提交、saga 模式是同一思想——先记意图再执行，崩溃后靠 log 决定是重做还是补偿（这里是 fail）。能把这个 LLM 工具调用和经典分布式事务模式挂钩，是高级信号。"
