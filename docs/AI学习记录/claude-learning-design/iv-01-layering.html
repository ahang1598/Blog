分层与依赖方向

为什么 opencode 的依赖箭头只能朝一个方向？为什么 Client 永远不能 import Core？这不是洁癖，而是把可演化的边界钉死在编译期——一旦反向依赖发生，未来每一次重构都会被这条隐式耦合追着打。

① 定位 ② 问题先于方案 ③ 设计拆解 ④ 生产级取舍 ⑤ 双视角 🎯 面试追问

1一句话定位

把代码按"谁知道谁"切成单向的层：Schema 是契约的最底层，Core/Protocol 依赖它，Server 依赖 Core/Protocol，Client 只能依赖 Schema/Protocol，永远不能向上够到 Core 或 Server。依赖箭头只朝下/朝外指。

🔑 一句话

分层不是"把代码分文件夹"，而是用依赖方向把演化边界固化成编译期错误。谁依赖谁是设计的核心约束，不是事后整理。

2问题先于方案

先停 30 秒：如果一个 SDK / Server / Client 混在一起的"大泥球"项目，生产里会发生什么？下面是真实痛点，不是假想。

痛点 A · 改一行 Core，全世界重新发版

Client 直接 import Core 的某个 service。你只是想重构 Core 内部一个函数签名——结果 Client 编译挂了，所有用 SDK 的下游全断。重构成本被放大成"全链路协同发版"。

痛点 B · Server 逻辑偷偷漏进 Client

没有依赖墙，开发者图省事直接在 Client 里调 Server 的工具函数。三周后这个"工具函数"成了事实 API，没法在不破坏 Client 的前提下换 Server 实现。

痛点 C · 契约漂移，运行时才炸

没有独立的 Schema 层，Server 改了响应字段，Client 是另一个 PR 改的。两边各自编译通过，上线后 Client 拿到 undefined 才崩。错误推迟到运行时。

痛点 D · 测试只能整链路起

想测 Client 的一段序列化逻辑，必须把 Server + Core + DB 全拉起来。单测变成集成测，反馈从毫秒级退化到秒级，没人再写了。

⚠ 共同病根

这四个痛点的根都是同一个：依赖方向没被约束，所以耦合可以朝任意方向生长。等发现时已经是既成事实，回不去了。

3设计拆解

opencode 的解法是把"谁知道谁"画成一张单向 DAG。箭头只朝下指，环=编译错误。

三道不可逾越的边界

边界 1 · Schema 零依赖

Schema 层只有 Effect Schema 定义，不依赖任何运行时包。它是所有人共同的地面真理。任何包想改契约，都得先动 Schema，动 Schema 会触发下游全员重编。

边界 2 · Core/Protocol 朝下

Core 和 Protocol 都依赖 Schema，互不依赖。Server 依赖两者。这条单向流保证了改 Protocol 的传输细节绝不会波及 Core 的领域逻辑。

边界 3 · Client 够不到 Core/Server

Client（含生成代码、SDK）只能依赖 Schema 和 Protocol。这是最硬的墙：Server 实现可以整个换掉、Core 可以重构，Client 编译不受影响——因为 Client 压根看不到它们。

📌 这套规则在仓库里是成文约束

见 AGENTS.md · "Keep runtime dependencies directed..."：明确写了 "Client runtime code may depend on Schema and Protocol but never Core or Server"。这不是建议，是 PR 评审的硬标准。

4生产级取舍

每个设计选择都有它的代价。面试官最爱追问"那不这样呢？"——下面把选择和代价配对。

选择：独立 Schema 层

  • 契约变更编译期可见
  • Server/Client 可独立发版
  • 单测不必起整链路

不这么做的代价

  • 契约漂移推迟到运行时才崩
  • Server/Client 必须同步发版
  • 测一段序列化得拉起 DB+Server

选择：Client 不能 import Core

  • Core 重构不破坏 Client 编译
  • Server 实现可整体替换
  • 演化边界固化在类型系统

不这么做的代价

  • Core 内部函数成事实 API，删不掉
  • "图省事"的快捷调用变成永久耦合
  • 每次重构被隐式依赖追着打

选择：Protocol 与 Core 平级、互不依赖

  • 换传输层（HTTP→WS）不碰 Core
  • 新增 provider 不动领域逻辑

不这么做的代价

  • 传输细节和领域逻辑缠在一起
  • 改一处影响范围不可预测
🔑 本质

分层的收益不是"整洁"，而是把变更的爆炸半径压缩到一层。好的分层让你改 A 不会炸到 B；坏的分层让每一次改动都变成全链路协同。前者让你敢重构，后者让你不敢动。

5面试双视角

这题看着基础，其实考的是系统设计成熟度——你是否把"依赖方向"当成一等设计约束，还是只当文件夹整理。

🎙️ 面试官为何问这题

  1. 探你有没有"耦合成本"直觉——知不知道反向依赖会让重构成本爆炸。
  2. 探你对"演化"的预判——能不能预见 Server 实现会被替换、Client 会独立演进。
  3. 探你区分"运行时依赖"与"编译期契约"——前者是技术细节，后者是设计决策。
  4. 埋雷：很多人答"为了职责分离"就停了。面试官会追问"职责分离是结果，约束在哪？"——看你能不能答出"编译期依赖方向 + 独立 Schema"。

🧑‍💻 面试者拆解（五段式）

  1. 抽象定位：分层本质是用依赖方向把演化边界固化成编译期错误，不是文件夹整理。
  2. 讲约束：箭头单向，Schema 零依赖做地面真理，Client 不能向上够到 Core/Server。
  3. 讲收益：契约变更编译期可见、Server/Client 独立发版、单测不必起整链路。
  4. 主动讲代价：代价是多一层 Schema 维护、跨层重构要走契约变更流程——但这代价远小于反向耦合的爆炸半径。
  5. 给未来演化：独立 Schema + 单向依赖是后续做版本化 API、多语言 Client、Server 替换（如换 RPC 框架）的前置条件。
✅ 加分项

主动提"生成代码"：Client 的生成代码也只依赖 Schema/Protocol，所以契约变更能自动驱动 Client 重生（AGENTS.md："After changing the public Protocol or Server HttpApi, run bun run generate"）。这把"契约优先"从口号落到工程流程。
