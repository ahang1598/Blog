工具契约与双层权限门

模型看到的工具（name/description/输入 JSON Schema）和它看不到的东西（execute 函数、权限字符串）必须严格分离。而权限要在两层施加：① 物化时把全禁的工具从模型视野里彻底删掉（whollyDisabled，模型连尝试入口都没有）；② 调用时按具体输入逐次授权（allow/deny/ask）。少了任一层——要么模型对着禁用工具瞎调，要么"bash 全开或全禁"失去精细控制。

① 定位 ② 问题先于方案 ③ 设计拆解 ④ 生产级取舍 ⑤ 双视角 🎯 面试追问

1一句话定位

ToolDefinition 是模型看得到的契约（name、description、inputSchema），execute/permission 是模型看不到的实现。materialize(权限) 在物化工具集时，把 whollyDisabled（resource=* 且 effect=deny）的工具整个删掉，模型视野里不存在它。调用时，工具的 execute 内部对这次的具体输入做 permission.assert，走 allow（直接执行）/ deny（立即失败）/ ask（发 Asked 事件、阻塞等用户回复）。

🔑 一句话

模型看得到才会调。所以禁用工具要从视野里删除（layer 1），而不是让它调了再拒绝；资源相关的精细授权（bash 的每条命令）留到调用时（layer 2）。

2问题先于方案

如果只有一层权限（要么全禁删工具、要么调用时检查），生产里会怎样？

痛点 A · 模型对着禁用工具瞎调

只有调用时检查（layer 2），禁用的工具仍出现在工具列表。模型看到 write 就会尝试调，被拒后换种方式再调，循环浪费 token、污染上下文。模型不知道"这工具根本不该用"。

痛点 B · 失去精细控制

只有物化时删工具（layer 1），bash 要么全开要么全禁。无法表达"bash 允许，但 rm -rf 要审批"——因为删 bash 就全没了，留 bash 就全放行。

痛点 C · 模型看到实现细节

execute 函数、permission 字符串漏给模型。模型可能基于"这个工具内部怎么实现"来决策，耦合了实现，换个 execute 实现模型行为就变。

痛点 D · 权限决策无法交互

只有 allow/deny，没有 ask。危险操作（rm -rf）要么静默放行（危险）要么静默拒绝（卡住）。没有"问用户"的中间态。

⚠ 共同病根

把"工具可见性"和"调用授权"混为一层。但它们解决不同问题：前者是模型该不该知道这个能力存在，后者是这次具体调用该不该执行。

3设计拆解

契约分离 + 双层权限门。模型看到的和看不到的，各归各位。

删除，模型视野里不存在 → 否：保留，模型看得到、能调 Layer 2 · 调用时（execute 内 assert） 按这次具体输入逐次授权： allow — 直接执行 deny — 立即失败（DeniedError） ask — 发 Asked 事件，阻塞等用户回复 为什么必须两层 无 layer 1：禁用工具仍在视野，模型循环瞎调浪费 token、污染上下文 无 layer 2：bash 要么全开要么全禁，无法"允许 bash 但 rm -rf 审批" 两层协作：layer 1 管"该不该知道存在"，layer 2 管"这次该不该执行"

三种权限动作（deny > ask > allow）

动作触发时机行为
allow匹配的规则允许 / 用户曾选"always"并持久化放行，无交互
deny匹配的规则禁止立即抛 DeniedError，不问用户（权威静默）
ask无 allow/deny 匹配（默认）发 Asked 事件，阻塞 Deferred 等回复（once/always/reject）
📌 优先级：deny > ask > allow

跨所有合并的规则集，deny 永远赢。这保证安全策略单调——任何一层加了 deny，就不会被别处的 allow 覆盖。和 iv-09 子 agent 权限收窄的"父 deny 下传"是同一原则。

4生产级取舍

两层门 + 契约分离有维护成本，但守护的是模型行为可控和安全精细度。

选择：契约分离 + 双层门

  • 禁用工具从视野消失，模型不瞎调
  • bash 可见但 rm -rf 审批（精细）
  • 实现细节不漏给模型（解耦）
  • ask 提供人机交互中间态

单层/混合的代价

  • 禁用工具在视野，循环浪费
  • 或全开全禁，失去精细度
  • 实现细节漏给模型，耦合
  • 危险操作无法交互确认

选择：deny > ask > allow 单调优先级

  • 安全策略不被 allow 覆盖
  • 子 agent 继承父 deny（iv-09）
  • 行为可预测、可审计

allow 可覆盖 deny 的代价

  • 安全策略可被绕过
  • 委派时父限制失效
  • 审计困难，行为不可预测
🔑 本质

工具权限的核心是区分"能力存在性"和"能力使用权"。layer 1 控制"模型知不知道这个能力"（存在性），layer 2 控制"这次用不用得了"（使用权）。两者正交，缺一不可。

5面试双视角

这题考的是安全建模 + LLM 行为理解——你懂不懂"模型看得到就会调"这个 LLM 特性，懂不懂精细授权。

🎙️ 面试官为何问这题

  1. 探 LLM 行为直觉——知不知道模型看到工具就会尝试调，禁用必须从视野删除。
  2. 探精细授权——bash 该全开还是全禁？能不能"允许但 rm -rf 审批"？
  3. 探契约设计——模型该看到工具的什么？execute 该不该漏？
  4. 埋雷：很多人答"调用前检查权限"。追问"那模型看到禁用工具反复调怎么办？"——看你能不能答出"layer 1 删工具"。

🧑‍💻 面试者拆解（五段式）

  1. 抽象定位：契约分离（模型可见 vs 实现）+ 双层权限门（存在性 vs 使用权）。
  2. 讲约束：layer 1 whollyDisabled 删工具；layer 2 按输入 assert（allow/deny/ask）；deny>ask>allow 单调。
  3. 讲收益：模型不瞎调；精细授权（bash 可见、危险命令审批）；实现解耦；人机交互。
  4. 主动讲代价：两层逻辑更复杂；权限规则维护成本。但远小于"瞎调浪费/全开全禁/无法交互"的代价。
  5. 给未来演化：权限规则是声明式配置——未来加"按用户/按项目/按时间"的动态授权，只扩 layer 2 的 assert 逻辑，不动 layer 1 和契约。
✅ 加分项

主动收束全系列："这套工具权限和 iv-08（agent 是约束包）、iv-09（子 agent 减法收窄）是同一个安全哲学的三个层次：agent 定义'人格有什么能力上限'，子 agent 收窄'委派时减到最小'，工具权限门控制'每次调用该不该执行'。三层合力 = 从身份到委派到调用的完整 capability 链。这就是 opencode 安全设计的整体观。"
