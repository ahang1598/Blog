持久化执行：admission vs execution 分裂

为什么"记下用户说了什么"和"真的去调模型"必须拆成两件事？因为前者要毫秒级返回且永不丢，后者要几十秒且随时会崩。把它们绑在一起，等于把"可靠性"和"脆弱性"焊死——崩一次丢一条 prompt。opencode 的解法：两条车道，中间一条 durable log，用 wake 这条虚线把它们解耦。

① 定位 ② 问题先于方案 ③ 设计拆解 ④ 生产级取舍 ⑤ 双视角 🎯 面试追问

1一句话定位

admission（接纳）只做一件事：把 prompt 写进 durable event log，毫秒返回。execution（执行）是另一个完全独立的进程级服务，负责真正去调模型、跑工具、写回事件。两者只通过 durable log + 一条 wake 通信。

🔑 一句话

正确性住在 log 里，性能住在 execution 里。wake 是"建议你去干活"，不是"你必须干活"——丢了 wake 不影响正确性，因为活儿已经躺在 log 里了。

2问题先于方案

如果"接收 prompt"和"调模型"是同一个函数、同一个调用栈，生产里会发生什么？

痛点 A · 崩溃即丢数据

用户发了 prompt，函数开始等 LLM 返回（可能几十秒）。这期间进程崩了/OOM/被杀——prompt 没了，用户不知道，重发还是不重发？不可靠。

痛点 B · 调用方被长流绑死

HTTP/TUI 处理器要 hold 住这个请求几十秒。客户端断网了？请求死了，prompt 也死了。不能边等边干别的。

痛点 C · 没法排队/打断

第一条还在流，用户又发第二条。第二条得等第一条函数返回才能进——没有"先记下再调度"的中间态。打断也没干净的窗口。

痛点 D · 崩溃后无法续跑

执行到一半崩了，已经产生的部分 assistant 文本、已经跑完的工具——这些状态在内存里，进程没了就没了。没法从断点恢复。

⚠ 共同病根

把"记录意图"（快、必须可靠）和"执行意图"（慢、必然脆弱）焊成了一个原子操作。前者的可靠性被后者的脆弱性拖垮。

3设计拆解

解法是经典的"durable log + ephemeral wakeup"模式：先快速把意图落盘（admission），再异步慢慢处理（execution）。

四个关键设计决策

① admission 永不碰 provider

admit = 一次 DB 写。不调模型、不开流。所以它毫秒级返回且永不失败（除非 DB 挂了，那是另一层问题）。

② execution 是进程级服务，按 ID 寻址

"会话 X 现在在跑吗？"是进程的运行时属性，不是任何 Location 服务的属性。用进程级 Map<SessionID, Entry> 做 O(1) 查找。

③ wake 是合并的、可丢的

用户连发 5 条 steer → 5 次 wake 合并成 1 次后续 drain。wake 丢了也没事——活儿在 log 里，下次 resume 扫一遍 hasPending 就捞回来。

④ drain 是 advisory，无持久身份

"一次 drain"不写进 log（没有 DrainStarted 事件）。它是纯优化："你正好醒着，顺便看看有没有新活"。正确性不依赖 drain。

4生产级取舍

"两车道"不是免费的——它引入了 eventual consistency 和调度复杂度。但换来的可靠性收益远大于此。

崩溃时序：为什么这套能扛住

T1 · 用户发 prompt
admit 写一行 PromptAdmitted，返回 seq，HTTP 立即 200。用户已确认"收到了"。
T2 · wake 触发 execution
runner 开始 drain，调 llm.stream，边流边把 AssistantPart 写进 log。
T3 · 💥 进程崩了
部分 assistant 文本已经持久化。wake 没了，drain 没了——但PromptAdmitted 在 log 里。
T4 · 重启恢复
resume 触发 run，hasPending 看到"有 admitted 但没 promoted 的输入"，重新 drain，从 log 重投影历史继续。用户无感知。
🔑 关键：admission 是"已确认"的边界

T1 返回 200 的那一刻，prompt 就绝对不会丢了——哪怕 T2 都没开始就崩。这是把"可靠性边界"从"模型返回"提前到"DB 写成功"的设计。

反例：如果 admission 阻塞在 LLM 调用上

调用方 hold 几十秒

HTTP/TUI 要跨一个多秒到多分钟的流 hold 请求。客户端断开=prompt 死。

第二条进不来

第一条还在流，第二条无法被"记下"，只能等。无法排队、无法打断。

崩溃=丢 prompt

没有先落盘，崩了就没了。用户不知道该不该重发。

中断没干净窗口

"还没开始"和"已经在流"没有清晰分界，中断语义混乱。

5面试双视角

这题考的是抗失败设计 + 并发与一致性直觉——你是否理解"可靠记录"和"脆弱执行"必须分离。

🎙️ 面试官为何问这题

  1. 探你有没有"可靠性边界"直觉——知不知道该把"已确认"提前到哪一步。
  2. 探你对"建议 vs 必须"的理解——能不能区分 wake（性能优化）和 admit（正确性）。
  3. 探并发直觉——同一个 session 多次 wake 怎么办？不同 session 能不能并发？
  4. 埋雷：很多人答"用消息队列"。追问"队列消费者崩了呢？"——看你能不能答出"正确性在 log 不在消费者"。

🧑‍💻 面试者拆解（五段式）

  1. 抽象定位：这是"durable log + ephemeral wakeup"模式，把记录意图和执行意图解耦。
  2. 讲约束：admit 永不碰 provider（毫秒返回），execution 进程级按 ID 寻址，wake 可丢可合并。
  3. 讲崩溃恢复：admit 落盘=可靠性边界；崩溃后 resume 扫 hasPending 自愈，drain 无持久身份所以不脏。
  4. 主动讲代价：引入 eventual consistency（admit 到真正执行有延迟）、调度复杂度（合并/串行化）。但远小于"崩了丢 prompt"的代价。
  5. 给未来演化：进程级 + ID 寻址是集群化的接缝——"会话 X 的 owner"从"本地 fiber map"换成"分布式 lease"时，只动这一个服务。
✅ 加分项

主动提"给 layer 传 Session ID 是反模式"：Location-scoped 服务（ToolRegistry、Permission、Model）从 Location 解析，不该收 Session ID。ID 只在边缘（admission、execution 路由）出现。引入第二个维度（ID 路由）要和 Location 路由保持一致，是隐式耦合温床。

🎯面试追问 · 模拟面试官深挖

drain 为何无持久身份？给 layer 传 Session ID 会怎样？唤醒丢了怎么办？一层层追到答不出。
