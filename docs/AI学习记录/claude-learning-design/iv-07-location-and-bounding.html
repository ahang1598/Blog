Location 隔离 + 工具输出有界

为什么 opencode 的工具注册表、权限、模型解析、FS 都是按工作目录隔离的，而不是进程级单例？因为单例会锁死未来——多工作区、多 worktree、集群化全都做不了。而工具输出必须有界，是因为一次 cat huge.log 的几兆字节会同时撑爆上下文、打挂缓存、淹没信号。这两个设计分别守护可扩展性和成本可控性。

① 定位 ② 问题先于方案 ③ 设计拆解 ④ 生产级取舍 ⑤ 双视角 🎯 面试追问

1一句话定位

Location 隔离：几乎所有有状态的核心服务（ToolRegistry、Permission、Model、FileSystem、Watcher、Pty…）都注册成 location 标签的 LayerNode。给一个 Location.Ref，系统 hoist 出该目录专属的服务树，编译出一个隔离的运行时。工具输出有界：每个工具输出有 MAX_LINES / MAX_BYTES 上限，超出就把全文落盘，只在上下文里留 head+tail 预览 + 文件路径。

🔑 一句话

Location 隔离让"一个进程同时服务 N 个工作区"和"未来把 session 迁到别的节点"都成为可能；输出有界把"一次坏工具调用"的成本封顶在一个常数。

2问题先于方案

如果这些服务是进程级单例、工具输出无界，生产里会怎样？

痛点 A · 多工作区互相污染

单例 ToolRegistry 服务所有目录。session A 在 /repo1，session B 在 /repo2，但它们共享同一套工具注册表——A 注册的工具 B 能看到，反之亦然。配置/MCP 串了。

痛点 B · worktree 无法隔离

同一个仓库的多个 git worktree，文件快照/变更检测本该独立。单例会让它们共享 FS watcher 和权限状态，变更归属混乱。

痛点 C · 集群化无接缝

未来想把 session 迁到别的节点执行。如果服务是进程单例，迁移=把每个注册表都拆开重装。没有干净的接缝，集群化变成大重构。

痛点 D · 工具输出撑爆一切

用户让 agent cat huge.log（10MB）。无界输出：① 撑爆上下文窗口（provider 413 / overflow）；② 进入历史后每轮全价计费；③ 99% 无关日志淹没真正的错误信号。

⚠ 共同病根

把"作用域"和"边界"当成事后考虑。作用域（哪个目录的运行时）和边界（一次调用最多多少字节）必须在设计时就钉死，否则会被坏输入和未来需求同时打穿。

3设计拆解

两个正交的设计：作用域的隔离（Location）和输出的封顶（ToolOutputStore）。

Location 隔离的四个收益

① 多工作区今天就能用

一个 opencode 进程同时服务 N 个目录，各自独立的工具/FS/权限。不互相污染。

② 多 worktree VCS 隔离

每个 git worktree 独立的快照/变更/权限状态，因为它们是 Location-scoped 而非进程单例。

③ 集群化接缝

整个 per-session 运行时是 LayerMap 里按 Location.Ref 寻址的值。迁节点 = 在 LocationServiceMap 边界做路由，不重构每个服务。

④ 可测/可替换

测试可注入假 FileSystem，hoist/compile 走显式依赖图，切片替换干净。

工具输出有界的三个理由

① 防上下文爆炸

一次 cat huge.log 几兆字节。无界会 provider 413 / context-overflow，直接杀死 turn。

② 防缓存打挂

大输出进历史后每轮重发；非确定输出（时间戳/PID）让前缀每轮漂移，缓存全 miss。

③ 防信号淹没

99% 无关日志里找错误，模型推理质量下降。head+tail 预览保留开头和结尾（错误通常在这）。

4生产级取舍

隔离和有界都有成本（多实例的内存、预览的信息损失），但守护的是可扩展性和成本可控性。

选择：Location-scoped 而非进程单例

  • 多工作区/多 worktree 互不污染
  • 集群化有干净接缝（换 map 即可）
  • 依赖图显式，可测可替换

进程单例的代价

  • 多工作区串配置/MCP
  • worktree 变更归属混乱
  • 集群化=大重构，无接缝
  • 测试必须起整个进程

选择：工具输出 head+tail + 落盘

  • 单次调用成本封顶常数
  • 模型可按需 read 全文（路径已给）
  • 保留错误最常出现的首尾

无界输出的代价

  • 撑爆上下文 → turn 死
  • 每轮全价重发 → 成本爆炸
  • 非确定输出 → 缓存全 miss
  • 噪声淹没 → 推理质量降
🔑 本质

这两个设计的共同主题是给"坏情况"封顶。Location 隔离给"未来需求"封顶（集群化不必大重构）；输出有界给"坏输入成本"封顶（一次坏调用不会拖垮整个 session）。成熟的系统设计总是问"最坏会怎样，怎么封顶"。

5面试双视角

这题考的是可扩展性设计 + 成本控制——你懂不懂"作用域"和"边界"是一等设计约束。

🎙️ 面试官为何问这题

  1. 探可扩展性直觉——知不知道进程单例会锁死多租户/集群化。
  2. 探"作用域"思维——能不能区分"进程级"和"位置级"服务。
  3. 探成本意识——工具输出无界会撑爆上下文 + 打挂缓存，双重成本。
  4. 埋雷：很多人答"加个 limit 就行"。追问"limit 之后模型怎么看全文？"——看你能不能答出"head+tail 预览 + 落盘 + 按需重读"。

🧑‍💻 面试者拆解（五段式）

  1. 抽象定位：作用域（Location）和边界（输出封顶）是一等设计约束，给"坏情况"封顶。
  2. 讲约束：有状态服务按 Location.Ref 隔离成独立服务树；工具输出有 MAX_BYTES，超出落盘 + head+tail 预览。
  3. 讲收益：多工作区/集群化/可测；上下文不爆 + 缓存稳定 + 信号清晰。
  4. 主动讲代价：多实例的内存开销；预览丢中间信息（但模型能 read 全文）。代价远小于"污染/爆炸"的代价。
  5. 给未来演化：LocationServiceMap 是接缝——从本地 map 换分布式 lease 即可集群化；MAX_BYTES 可按文档配置调，不同场景不同阈值。
✅ 加分项

主动收束全系列："Location 隔离是空间维度的边界（哪个目录的运行时），输出有界是字节维度的边界（一次调用最多多少）。加上 iv-02 的时间维度边界（admission vs execution）、iv-05 的轮次边界（一轮一次 stream）——这整套设计都是在给不同维度的坏情况封顶。这是贯穿 opencode 的统一哲学。"
