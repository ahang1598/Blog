Chapter 8 · 智能体与工具（1/4）

智能体架构：把约束打成一个人格

在 opencode 里，"智能体（agent）"不是一个有行为的类，而是一个命名的正交约束包：系统提示 + 权限 + 模型 + 采样参数 + 步数预算，五者焊成一个可点名的人格。这个设计不是图整洁——它让"只读探索者""规划者""通用助手"成为可审查、可复用、可委派的整体，而不是用户用一堆散件临时拼出的危险拼装。

① 定位 ② 问题先于方案 ③ 设计拆解 ④ 生产级取舍 ⑤ 双视角 🎯 面试追问

1一句话定位

agent = 一个名字 + 五个绑死的正交维度：prompt（系统提示）、permission（权限规则集）、model+variant（模型与变体）、sampling（temperature/topP）、steps（步数预算）。选中一个 agent，就一次性提交了这一轮的整个请求形状（system prompt、工具集、模型、温度、上限）。

🔑 一句话

agent 把"该用什么人格干活"做成一个 token 就能选定的整体（父 agent 调 task(subagent_type="explore")），而不是让调用方每次手动拼温度+权限+提示。约束的不可分性 = 人格的连贯性。

2问题先于方案

如果把 prompt、permission、model、temperature 拆成几个独立的配置轴，让用户自由组合，生产里会出什么事？

痛点 A · 危险的拼装

用户能配出"高温 + 能写文件 + 探索者提示"这种自相矛盾的人格：提示说"只搜索"，权限却允许 bash/write。模型一旦幻觉出写命令，就直接改了仓库。人格不自洽 = 安全缺口。

痛点 B · 不可复用

没有命名人格，每次委派"只读搜索"都得重新拼一套（提示+权限+只读工具集）。能力无法被点名复用，父 agent 没法 task(explore) 一个 token 就拿到只读探索。

痛点 C · 不可审查

散件配置下，"这个会话到底有什么权限、跑在什么模型上"得翻多个文件拼出来。没有单一可审查的整体，安全审计和回归测试都难做。

痛点 D · 默认值缺失

新 session 没指定 agent，系统不知道该用哪个提示、哪个模型、哪些工具。冷启动无法构造第一个请求。

⚠ 共同病根

把本应作为整体起作用的约束拆成独立旋钮。可组合 ≠ 该组合——某些维度组合是危险的、不自洽的，必须焊死成预审过的人格。

3设计拆解

agent 是五个维度的命名打包。选中它 = 一次性提交整轮请求的形状。

默认 agent 目录（命名的、预审过的人格）

agentmodehidden特征
buildprimary否原生默认。全权限 + question/plan_enter。通用编码 agent。
planprimary否只读规划：除 .opencode/plans/*.md 外禁止 edit/write。只能写自己的计划文件。
generalsubagent否并行多步工作的通用子 agent（仅禁 todowrite）。
exploresubagent否只读探索者：全禁，只允许 grep/glob/list/bash(只读)/webfetch/websearch/read。
compactionprimary是上下文压缩助手（全禁工具，自定义提示，从不面向用户）。
title / summaryprimary是生成标题/摘要（全禁，title 用 temperature:0.5 求确定）。
📌 默认选择链（保证冷启动不崩）

未指定 agent 时的回退链：① 配置的 default（若可选）→ ② build → ③ 第一个可选的 agent。每条都保证非 subagent 且非 hidden。没有这条链，新 session 无法构造第一个请求。

4生产级取舍

"约束打包"牺牲了灵活性（不能任意组合维度），换来安全性和可复用性。

选择：约束焊死成命名人格

  • 人格自洽：探索者物理上不能写
  • 可点名复用：task(explore) 一个 token
  • 可审查：一个 agent = 一个整体
  • 默认链保证冷启动

散件自由组合的代价

  • 危险拼装（高温+写权限+探索提示）
  • 能力无法复用，每次重拼
  • 不可审查，审计难
  • 冷启动无默认，崩

选择：mode 区分调用者

  • hidden 助手不进用户菜单
  • subagent 不被用户直选
  • all 给自定义 agent 合理默认

无 mode 区分的代价

  • compaction 进用户菜单（混乱）
  • 模型能 spawn compaction（无意义）
  • 自定义 agent 要显式声明才能见
🔑 本质

agent 设计的核心是把"权限"从运行时检查提升为编译期身份。不是"运行时判断能不能写"，而是"这个人格压根不存在写的维度"。安全从动态防护变成静态属性。

5面试双视角

这题考的是系统设计成熟度 + 安全建模——你懂不懂"能力（capability）"应该是一等公民，而不是散件配置。

🎙️ 面试官为何问这题

  1. 探你的安全直觉——知不知道"提示说只读"和"物理上不能写"是两件事。
  2. 探抽象能力——能不能看出 agent 是"约束包"而非"行为类"。
  3. 探默认值思维——冷启动怎么不崩？默认链如何保证可选。
  4. 埋雷：很多人答"用配置文件定义 agent"。追问"那用户能配出高温+写权限+探索提示吗？"——看你能不能答出"约束应焊死成预审人格"。

🧑‍💻 面试者拆解（五段式）

  1. 抽象定位：agent 是命名的正交约束包（prompt+permission+model+sampling+steps），不是行为类。
  2. 讲约束：五维度焊死；选中即提交整轮请求形状；mode 区分调用者；默认链保冷启动。
  3. 讲收益：人格自洽（安全）；可点名复用；可审查；冷启动不崩。
  4. 主动讲代价：牺牲维度自由组合的灵活性。但远小于"危险拼装/不可复用"的代价。
  5. 给未来演化：agent 是注册的（registry）——加新人格（如"测试专家""重构专家"）只需定义约束包注册，不动 runner。
✅ 加分项

主动联系安全设计："这和 OS 的 capability-based security 是一个思想——权限不是运行时查询，而是身份的一部分。一个进程没有 'write' capability，就不存在 write 的代码路径；一个 explore agent 没有 write 维度，模型连尝试的入口都没有。" 能把 agent 设计和经典安全模型挂钩，是高级信号。
