一 · 设计问题:核心流程怎么被扩展

Agent 的核心流程(解析模型→拼 prompt→调工具→回复→结束)是固定的。但生产中,各种定制需求都想往这个流程里"插一脚":

  • 安全审计:工具调用前检查是否危险,危险就拦。
  • 日志/监控:记录每次模型调用、工具执行,供分析。
  • 权限控制:某些用户/场景禁用某些工具。
  • 定制 prompt:在系统 prompt 前后加自己的内容。
  • 结果改写:工具结果回来后做脱敏/转换。
  • 会话事件:会话开始/结束时做初始化/清理。

如果这些定制都写死在核心流程里,核心会变成打满 if/else 的怪兽,且每个用户/部署要改核心代码才能定制。不可维护,也不可扩展。

demo 级做法:在核心里散落调用点 if (config.enableAudit) auditLog(...)。生产中这会爆炸:每加个定制加个 if,核心越来越乱,且不同定制的执行顺序、错误处理、相互影响无法管理。

二 · 分层设计:各阶段钩子点

┌──────────────────────────────────────────────────────────────────────┐ │ Agent 生命周期 · 各阶段钩子点 │ └──────────────────────────────────────────────────────────────────────┘ [会话级] ┌──────────────────────────────────────────────────────────┐ │ session_start ─→ (会话进行) ─→ session_end │ └──────────────────────────────────────────────────────────┘ │ 每个 turn(第②篇的 turn 循环): ▼ [turn 级钩子链] ┌──────────────────────────────────────────────────────────┐ │ ① before_model_resolve "用哪个模型"之前(可改模型) │ │ ↓ │ │ ② before_prompt_build 拼 prompt 之前/之后(可改 prompt) │ │ ↓ │ │ ③ [调模型 · stream] │ │ ↓ │ │ ④ before_tool_call 工具执行前(可拦截/改参数) 🔒阻塞 │ │ ↓ │ │ ⑤ [执行工具] │ │ ↓ │ │ ⑥ after_tool_call 工具结果回来(可改结果/脱敏) 🔒阻塞 │ │ ↓ │ │ ⑦ before_agent_reply 给用户回复前(可改回复) │ │ ↓ │ │ ⑧ turn_end / agent_end 回合/任务结束(观察/清理) │ └──────────────────────────────────────────────────────────┘ 🔒阻塞 = hook 可阻止后续流程(如拦截工具) 👁观察 = hook 只看不能改(如日志)

两类 hook 的本质区别

阻塞型(blocking)可终止流程

能阻止后续动作。典型:before_tool_call 可拦截危险工具,before_prompt_build 可改 prompt。返回"终止"决策让核心停下或改变行为。这是决策权——hook 参与流程控制。

观察型(observing)只读不改

只观察不改变流程。典型:turn_end 记日志,agent_end 做统计。这是旁路——hook 不影响核心,只消费事件。

三 · 为何这么设计:三个核心决策

决策 1:为什么区分阻塞型和观察型

如果所有 hook 都能改流程,会出现:① 顺序依赖混乱——多个 hook 都改 prompt,谁后改谁覆盖,结果不确定;② 性能损耗——观察型(日志)本不需等,却要串行过 hook 链;③ 核心不可预测——核心不知道哪些 hook 会改东西,难以推理自身行为。区分后:阻塞型明确声明"我要参与决策",按注册顺序串行执行,每个都能看到前一个的结果;观察型只读,可并行/异步,不影响核心。这让核心的行为可推理(只有阻塞型 hook 影响它),且性能可控。

决策 2:为什么阻塞型 hook 的决策要有"终止语义"

阻塞型 hook 返回的不该是布尔值(true/false),而是有语义的决策:

决策含义典型场景
proceed继续(可能带修改)正常,或改了参数后继续
block阻止此动作危险工具被拦截
cancel取消整个 turn/run严重违规,中止任务
modify修改后继续参数脱敏、prompt 注入

为什么不是简单 true/false?因为"阻止这个工具"和"取消整个任务"是不同力度的干预,核心需要对每种决策有明确响应。布尔值表达不了"阻止但继续 turn"vs"取消整个 run"的区别。终止语义让 hook 的干预力度可表达、可组合、可推理。

决策 3:为什么 hook 按注册顺序串行(阻塞型)

多个阻塞型 hook 都想改 prompt(如安全过滤 + 内容注入)。如果并行执行,谁的结果算数不确定。串行 + 顺序让结果确定:hook A 改完,hook B 基于 A 的结果改,可预测。注册顺序就是优先级(后注册的覆盖先注册的,或反之,要明确)。这是确定性优先于性能——hook 链的可预测性比并行快重要。

核心取舍:hook 系统带来执行顺序管理、决策语义、错误传播的复杂度,换来的是核心流程保持纯净、定制可插拔、行为可推理。替代方案(if 散落)的失败模式是"核心打满特判,每个定制要改核心,行为不可预测"。接受 hook 链管理的复杂度,因为它是核心保持 plugin-agnostic(第⑱篇)的关键机制——没有 hook,所有定制都会侵蚀核心。

四 · 完整示例:安全审计 hook 拦截危险工具

部署一个企业 agent,要求 exec 工具调用前必须经过安全审计。注册一个 before_tool_call 阻塞型 hook:

[turn N · 模型决定调用 exec("rm -rf /tmp/old")] ↓ [before_tool_call hook 触发] · hook: SecurityAuditHook · 类型: 阻塞型 · 输入: toolName=exec, params={cmd: "rm -rf /tmp/old"} · 审计逻辑: 检测到 "rm -rf" 高危模式 · 决策: block(返回"阻止此工具调用,原因:高危命令") ↓ [核心响应 block 决策] · 不执行 exec · 合成 tool_result: "工具调用被安全策略阻止:高危命令" · 喂回模型,模型据此换方案 ↓ [模型推理] "rm 被拦了,我换个安全的清理方式..." ↓ [turn 继续] 模型改用安全命令,通过审计,执行成功
关键洞察:安全审计 hook 没改核心代码就实现了拦截。核心只负责"调 hook、响应决策",具体审计逻辑在 hook 里。换企业、换策略,只换 hook 不动核心。这就是 hook 的价值——核心保持纯净,定制通过组合 hook 实现。同时 block 决策不是简单拒绝,而是合成失败结果喂回模型,让模型自己换方案(而非任务崩)。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点需求:"核心流程固定,但定制需求多(安全/日志/权限/改写)。写死在核心会变怪兽且不可扩展。"
  2. 给 hook 系统:"在各阶段暴露钩子:before_model/before_prompt/before_tool/after_tool/before_reply/end。hook 注册进来,核心在对应点调用。"
  3. 主动谈两类:"分阻塞型和观察型。阻塞型可终止/改流程(如拦截工具),观察型只读(如日志)。这让核心行为可推理(只有阻塞型影响它)。"
  4. 主动谈终止语义:"阻塞型返回有语义的决策(proceed/block/cancel/modify),不是布尔。表达不同干预力度。"
  5. 主动谈串行确定性:"阻塞型按注册顺序串行,结果可预测。确定性优先于性能。"
  6. 收口在核心纯净:"hook 是核心保持 plugin-agnostic 的关键——定制通过组合 hook,不动核心。"
