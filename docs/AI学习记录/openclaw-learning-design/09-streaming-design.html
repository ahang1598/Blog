一 · 设计问题:为什么不能 token 流直送

模型 API 支持 SSE 流式输出:生成一个 token 就推一个 token。直觉做法:收到 token 就立即转发给聊天 channel(Telegram/Discord/CLI),让用户实时看到字一个一个蹦出来。

听起来自然,但聊天协议不是 token 协议。直送会引发:

  • API 限流:Telegram/Discord 的消息编辑 API 有速率限制(每秒几次),token 流每秒几十上百个,直送瞬间被封号。
  • 协议错配:聊天协议是"发一条消息 + 可选编辑",不是"推一个字符"。token 流要硬塞进消息编辑模型,极别扭。
  • 无法成块:token 是碎片(半个词、半个 markdown 标记),直送用户看到的是乱码般的碎片,不是可读文本。
  • 代码块撕裂:模型输出代码块时,token 流可能在 ```` ``` ```` 中间被切断,channel 端渲染出错。
  • 工具调用混乱:thinking/text/toolcall 三种 block 的 token 混在一起,直送无法区分。

本质矛盾:模型流是 token 粒度的连续流,channel 是消息粒度的离散协议。两者粒度和语义都错配。

二 · 分层设计:模型流 vs channel 流

┌──────────────────────────────────────────────────────────────────────┐ │ 流式架构 · 两层独立流 │ └──────────────────────────────────────────────────────────────────────┘ [层 1] 模型流 · token 粒度(内部) ┌──────────────────────────────────────────────────────────┐ │ 模型 SSE → 归一化事件流: │ │ text_start/delta/end │ │ thinking_start/delta/end │ │ toolcall_start/delta/end │ │ done / error │ │ · 内部消费,用于: │ │ - 折叠(fold)成 AssistantMessage │ │ - 驱动 block chunker │ │ - preview 流(可选,见下) │ └──────────────────────────────────────────────────────────┘ │ block chunker 缓冲+切分 ▼ [层 2] channel 流 · block 粒度(对外) ┌──────────────────────────────────────────────────────────┐ │ block chunker 把 token 流聚合成"完成的块": │ │ · 最小/最大字符边界(minChars/maxChars) │ │ · 切分优先级链:段落 → 换行 → 句子 → 空格 → 硬切 │ │ · 永不在代码块中间切(切了要重开 ``` 标记) │ │ · 受 channel 文本上限钳制(如 Telegram 4096) │ │ → 每个 block 成为一条 channel 消息(发送或编辑) │ └──────────────────────────────────────────────────────────┘ │ 可选 ▼ [层 3] preview 流(用户体验) ┌──────────────────────────────────────────────────────────┐ │ 生成过程中,用一条"预览消息"实时更新: │ │ · 发一条草稿消息,随生成不断 edit │ │ · 模式:off / partial / block / progress │ │ · progress 模式显示工具进度,完成后替换为最终答案 │ │ → 用户看到"正在思考..."的实时反馈,不被速率限制打爆 │ └──────────────────────────────────────────────────────────┘

两层流的职责

模型流(内部)

• 粒度:token

• 消费者:agent loop(fold 成消息)、chunker、preview

• 协议:SSE / 异步迭代器

• 关注:正确折叠、block 类型区分

channel 流(外部)

• 粒度:block(一段完整文本)

• 消费者:聊天协议(Telegram 等)

• 协议:发消息 / 编辑消息

• 关注:速率限制、可读性、不撕裂

三 · 为何这么设计:三个核心决策

决策 1:为什么两层分离

模型流和 channel 流的粒度、协议、消费者、关注点都不同。混在一起(直送 token)必然在某一边崩——要么模型流被 channel 速率限制拖死,要么 channel 被模型流碎片淹没。分离后,模型流专注"正确折叠消息",channel 流专注"合规且可读地呈现",各跑各的节奏。中间的 block chunker 是适配器,把 token 粒度转成 block 粒度。

决策 2:为什么 block chunker 要切分优先级链

不能等模型全部生成完再发(用户等太久),也不能每 token 发(限流)。要在"足够长才发"(可读、省 API 调用)和"足够快发"(用户看到进展)间平衡。切分优先级链段落 → 换行 → 句子 → 空格 → 硬切让 chunker 优先在自然边界切(用户看到完整段落/句子),只有凑不够最小长度才退到下一级。这是用户体验工程:在自然边界切让阅读流畅,硬切让文本支离破碎。

决策 3:为什么永不在代码块中间切

代码块被 ```` ``` ```` 包裹。如果 chunker 在代码块中间切(发了前半,后半在下个 block),channel 端的 markdown 渲染会把前半当代码、后半当普通文本,显示混乱。所以 chunker 必须识别代码块边界,要么等代码块完整再发,要么切了之后在下个 block 重新打开 ```` ``` ```` 标记(告诉 channel"这是代码块的继续")。这是对 channel 渲染语义的尊重——不能只管发不管对方怎么显示。

preview 流的取舍

preview(草稿消息实时更新)给用户"正在生成"的反馈,但:① 占用 channel 编辑 API(有速率限制);② 完成后要替换/删除草稿(多一次操作);③ 不同 channel 支持度不同(有的不能编辑,有的有限制)。所以 preview 是可选的,按 channel 能力和用户偏好开关。

核心取舍:双层流 + chunker 带来适配层的复杂度(切分逻辑、代码块识别、速率钳制、preview 协调),换来的是模型流和 channel 流解耦、用户体验流畅、不被限流封号、渲染不撕裂。替代方案(token 直送)的失败模式是"API 被封 + 用户看到碎片 + 代码块撕裂"。接受复杂度,因为 token 直送在生产中根本跑不起来——这是协议错配的硬约束,不是优化项。

四 · 完整示例:一次回答的双层流时间线

模型生成一段含代码块的回答。双层流如何处理:

[模型流 · token 粒度] t0 text_delta: "这个函数有个 bug。" t1 text_delta: "问题在于空值检查。" t2 text_delta: "修复如下:" t3 text_delta: "```typescript\nfunction f(x) {" t4 text_delta: " if (!x) return 0;" t5 text_delta: " return x.length;" t6 text_delta: "}\n```" t7 done │ block chunker 缓冲 + 切分 ▼ [channel 流 · block 粒度] b0 [段落边界] "这个函数有个 bug。问题在于空值检查。修复如下:" → 达到 minChars 且在段落边界 → 发送(第 1 条消息) b1 [代码块完整] "```typescript\nfunction f(x) {...}\n```" → 检测到代码块,等完整再发 → 发送(第 2 条消息) │ 可选 preview 同时进行 ▼ [preview 流 · 用户看到的] 生成中:草稿消息"正在思考..." → "这个函数..."(随 edit 更新) 完成:草稿替换为最终答案 / 删除草稿发正式消息
关键洞察:模型流是 7 个 token delta,channel 流只有 2 个 block。chunker 把 7 个碎片聚合成 2 个可读块,在自然边界(段落、代码块)切分。用户看到的是 2 条流畅消息,不是 7 个碎片。同时 API 调用从 7 次(token 直送会被限流)降到 2 次(合规)。这就是双层流的价值:粒度适配 + 体验 + 合规。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点协议错配:"模型流是 token 粒度,channel 是消息粒度,直送会被限流封号 + 用户看碎片 + 代码块撕裂。"
  2. 给双层方案:"分两层——模型流(内部 token,用于 fold 成消息)、channel 流(外部 block,发给聊天协议)。中间 block chunker 适配。"
  3. 主动谈切分:"chunker 用切分优先级链:段落 → 换行 → 句子 → 空格 → 硬切,优先自然边界。永不在代码块中间切(切了要重开 ``` 标记)。"
  4. 主动谈速率钳制:"block 受 channel 文本上限钳制(如 Telegram 4096),超长自动拆多条但保持可读性。"
  5. 主动谈 preview:"可选的 preview 流用草稿消息实时更新给用户反馈,完成后替换/删除。按 channel 能力开关。"
  6. 收口在解耦:"两层分离让模型流专注正确性,channel 流专注合规体验,各跑各节奏。"
