一 · 设计问题:失败不可避免,重试不是万能

生产环境故障是常态:网络抖、限流、凭据过期、模型超载、provider 宕机。demo 级做法:失败就重试,重试 N 次还不行就报错。听起来简单,但有两个致命问题:

  • 不是所有失败都该重试:发邮件失败重试 = 发两封;支付失败重试 = 扣两次。非幂等操作的重试是生产事故源。
  • 无差别重试浪费资源:模型不兼容(永远失败)还重试 N 次,白等白花钱。瞬态故障(一次就好)和永久故障(永远不行)要区分。
  • 没有回退只能硬死:只用一个 provider,它宕了整个 agent 就瘫。生产需要多 provider/凭据回退。
  • 重试风暴:所有客户端同时重试(如 provider 短暂宕机恢复瞬间)打爆它。

故障容忍不是"加重试",而是一套分层的、有判断的、有回退的、有节流的系统。

三 · 为何这么设计:三个核心决策

决策 1:为什么 attempt 和 run 重试边界要分开

呼应第②篇三层循环。attempt 重试是"同候选内的瞬态故障重试"——便宜(同模型同凭据),但要限制次数(防永久故障白等)。run 回退是"换候选重试整个 run"——贵(换模型/凭据,可能丢上下文要重建),但能救永久故障。边界在"同候选是否还有希望":有(瞬态)→ attempt 重试;没(永久/耗尽)→ run 换候选。这个边界让重试成本可控——不会一个 400 错误也触发换模型的昂贵回退。

决策 2:为什么凭据要轮转(多 auth profile)

单凭据的致命问题:限流/过期就死。生产中,provider 限流是按 API key 的(每个 key 每分钟 N 次)。单 key 撞限流整个 agent 瘫。多凭据轮转:① 分散限流——多个 key 轮流用,整体吞吐 N 倍;② 容错——一个 key 过期/被禁,自动换下一个;③ 多账户——不同账户配额独立。attempt 重试时如果遇 401(凭据失效),先尝试刷新 token;刷新失败上抛 run 层,run 换下一个 auth profile。这是"不要把鸡蛋放一个篮子"在凭据上的体现。

决策 3:为什么非幂等操作绝不自动重试

这是安全事故的红线。发邮件、支付、下单、发消息这类操作有外部副作用且不可撤销。自动重试的判断逻辑("这次失败是真的没发,还是发了但响应丢了")无法在客户端可靠判断——网络超时可能是"请求没到服务器"(重试安全)也可能是"服务器处理了但响应丢了"(重试=重复操作)。这种不确定性意味着自动重试有重复风险。正确做法:非幂等操作失败时,① 不自动重试,返回失败给模型/用户;② 提供幂等键(idempotency key)让服务器端去重(带了相同 key 的请求服务器只处理一次);③ 让模型/用户决定是否手动重试。呼应第④篇的工具幂等性声明。

核心取舍:分层故障容忍带来故障分类、退避算法、候选管理、幂等性建模的复杂度,换来的是瞬态故障自动恢复、永久故障优雅降级、副作用安全。替代方案(无差别重试)的失败模式是"重复扣款/发邮件、永久故障白等、单点故障全瘫"。接受复杂度,因为在生产中'失败处理'比'成功路径'更能决定产品可靠性——demo 只测成功,生产全在测失败。

四 · 完整示例:凭据耗尽的回退链

用户用 agent,主凭据是 OpenAI 的 key-A,备选 key-B 和 claude。请求过程中 key-A 限流了:

[RUN 启动] 候选列表:[(gpt-5, key-A), (gpt-5, key-B), (claude, key-C)] · 选候选 1:(gpt-5, key-A) [ATTEMPT 1 · key-A] · 调模型 → 429(限流) · attempt 重试:退避 1s → 重试 → 又 429 · 退避 2s → 重试 → 429(限流持续) · attempt 上限(3次)耗尽 → 上抛 [RUN 回退] 判定:key-A 限流,换候选 · 选候选 2:(gpt-5, key-B) [ATTEMPT 1 · key-B] · 调模型 → 200 成功 ✅ · run 完成 [如果 key-B 也失败] · 选候选 3:(claude, key-C)—— 跨 provider 回退 · 重试整个 run(重建上下文适配 claude) [如果全部失败] · 终端 failed · 告知用户"所有 provider 暂时不可用" · 告警运维(provider 级故障)
关键洞察:用户感受到的只是"agent 正常工作了",背后的 key-A 限流被 attempt 重试+run 回退静默吞掉。这是故障容忍的目标——对用户透明。多凭据轮转 + 多 provider 回退让单点故障不致命。同时退避+抖动避免所有用户同时重试打爆 provider。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点本质:"故障容忍不是'加重试',是分层、有判断、有回退、有节流的系统。重试不是万能——非幂等操作重试是事故源。"
  2. 给三层:"attempt 级(瞬态,退避重试)、run 级(永久,换候选回退)、用户级(全失败,降级告知)。边界在'同候选是否还有希望'。"
  3. 主动谈故障分类:"瞬态(网络/限流)→ 重试;凭据过期 → 刷新;永久错误(400)→ 不重试;模型不兼容 → 换模型。分类决定策略。"
  4. 主动谈凭据轮转:"多 auth profile,限流/过期自动换。分散限流、容错、多账户。"
  5. 主动谈幂等红线:"非幂等操作(发邮件/支付)绝不自动重试——客户端无法可靠判断'发了没'。用幂等键让服务端去重,或问用户。"
  6. 主动谈防风暴:"退避+随机抖动,防所有客户端同时重试打爆 provider。"
  7. 收口在透明:"目标是故障对用户透明——静默恢复。生产全在测失败路径。"
