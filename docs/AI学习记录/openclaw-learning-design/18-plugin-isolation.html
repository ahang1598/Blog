一 · 设计问题:扩展不能侵蚀核心

第⑰篇讲了核心必须 plugin-agnostic。但"核心不依赖插件"只是一 半。完整的问题是:插件系统要既能加载第三方扩展,又不让扩展搞坏核心。

第三方插件是不受信任的代码——它可能有 bug、可能不兼容、可能恶意。如果直接加载运行:

  • 崩溃传染:插件抛未捕获异常,核心跟着挂。
  • 状态污染:插件乱改全局状态,影响其他插件/核心。
  • 资源泄漏:插件持有连接/文件不释放,累积拖垮系统。
  • 不兼容混入:插件声明支持某能力但实现不对,运行时才崩。
  • 加载顺序混乱:插件间有依赖,乱序加载半崩状态。

同时,插件加载还要快——启动不能慢,又要灵活——运行时增删。这些需求互相打架。

二 · 分层设计:控制面 + 运行时面

┌──────────────────────────────────────────────────────────────────────┐ │ 插件系统 · 控制面 + 运行时面 │ └──────────────────────────────────────────────────────────────────────┘ [控制面 · 不执行插件代码] ┌──────────────────────────────────────────────────────────┐ │ ① 发现:扫描插件包,读 manifest(元数据) │ │ · manifest = openclaw.plugin.json(声明能力,非代码) │ │ · 不 import 插件代码,纯元数据解析 │ │ ② 校验:manifest 合法性(格式、依赖、版本兼容) │ │ · 不兼容直接拒绝,不加载 │ │ ③ 激活规划:决定哪些插件启用、顺序、冲突处理 │ │ · 基于元数据,无副作用 │ └──────────────────────────────────────────────────────────┘ │ 规划好 ▼ [运行时面 · 执行插件代码] ┌──────────────────────────────────────────────────────────┐ │ ④ 加载:import 插件代码,执行 register(api) │ │ · 在注册事务里(失败回滚全局副作用) │ │ ⑤ 注册:插件通过 api 声明能力(我能提供 X) │ │ · 写入注册表,核心后续查表使用 │ │ ⑥ 隔离执行:插件代码在受限环境跑 │ │ · 异常捕获不传染核心 │ │ · 不能 import 核心内部 │ └──────────────────────────────────────────────────────────┘

manifest 是什么(关键概念)

manifest(openclaw.plugin.json)是插件的静态声明文件,描述:插件叫什么、提供什么能力(provider/channel/tool/hook)、依赖什么、版本号、配置 schema。它纯是元数据,不含代码。控制面只读 manifest 就能做大量决策(校验、激活规划),不必执行插件代码。

三 · 为何这么设计:三个核心决策

决策 1:为什么 manifest 先于代码加载

这是性能和安全的关键。如果加载插件就要执行代码(import 触发执行),那:① 慢——每个插件启动都要执行,几十个插件启动几秒;② 不安全——校验之前代码已执行,恶意插件可在校验拒绝前搞破坏;③ 无法规划——不知道插件提供啥能力之前就加载,无法决定启用顺序。manifest 先行:只读元数据(快、无副作用)就能校验+规划,通过了才执行代码。这是"先看说明书再开机"——避免盲目加载不兼容/恶意插件。

决策 2:为什么注册要事务化(失败回滚)

插件 register 时会产生全局副作用——往注册表写能力、可能初始化资源。如果中途失败(插件第 3 个能力注册时崩),前面 2 个已写入注册表,留下半残状态——核心以为插件提供某些能力,但插件实际没初始化完,调用就崩。事务化:把整个 register 包成事务,失败时回滚所有已注册的能力(注册表恢复到插件加载前)。要么全成功,要么全没有,不留半残。这避免了"部分加载"的幽灵 bug。

决策 3:为什么插件不能 import 核心内部

这是隔离的硬约束。如果插件能 import 核心 src/internal,它就和核心实现细节耦合——核心重构内部,插件就崩。这:① 破坏核心演进能力——核心不敢重构怕搞坏插件;② 插件不可移植——绑死特定核心版本;③ 安全风险——插件能触及核心内部状态绕过限制。硬约束:插件只能通过公开 SDK seam(第⑰篇)接入,禁止 import 内部路径。这让核心内部可自由重构,插件只依赖稳定公开 API。接受这个约束,因为核心演进能力是长期可维护性的根基。

核心取舍:控制面/运行时面分离 + manifest + 事务 + 隔离约束带来加载管线、注册表、异常边界、SDK 设计的复杂度,换来的是第三方扩展安全、核心不被侵蚀、加载快且可靠。替代方案(直接加载)的失败模式是"崩溃传染、状态污染、半残加载、核心不敢改"。接受复杂度,因为插件系统是平台生命力的核心——没有隔离,第三方扩展会很快把核心搞成不可维护的泥潭。

四 · 完整示例:一个插件从安装到激活

用户安装了一个第三方 Notion 集成插件。完整流程:

[控制面] ① 发现:扫描插件目录,找到 notion-plugin/ 读 openclaw.plugin.json: · id: "notion" · 提供: tool("notion_search"), tool("notion_create") · 依赖: 无 · 版本: 1.2.0 ② 校验:manifest 格式合法、版本兼容核心、依赖满足 ✓ ③ 激活规划:notion 无冲突,启用 · 全程没执行 notion 代码,纯元数据决策 [运行时面] ④ 加载:import notion 代码 → 执行 register(api) · 进入注册事务 ⑤ 注册:notion 调 api.registerTool("notion_search", ...) api.registerTool("notion_create", ...) · 写入注册表 · 事务提交 ✓ ⑥ 隔离:后续 notion 工具被调用时,异常捕获不传染核心 [运行时使用] · agent 查注册表发现 notion_search 工具 · 模型决定调用 → 框架调 notion 插件的 execute · notion 执行(在隔离边界内)→ 返回结果
关键洞察:notion 插件从安装到使用,核心代码零修改——它通过 manifest 声明、SDK seam 接入、注册表登记、隔离执行,全程不需要核心"认识"它。这就是插件系统的目标:核心稳定,扩展可插拔。如果 notion 崩了,异常被隔离,不影响 agent 用其他工具。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点问题:"第三方插件是不受信代码,直接加载会崩溃传染、状态污染、半残加载。"
  2. 给两面:"控制面(读 manifest 元数据,不执行代码)→ 运行时面(import 执行 register)。先看说明书再开机。"
  3. 主动谈 manifest:"manifest 是静态声明文件,纯元数据。控制面只读它就能校验+规划,不必执行代码。快且安全。"
  4. 主动谈事务:"register 包成事务,失败回滚所有已注册能力。不留半残状态。要么全成功要么全没有。"
  5. 主动谈隔离:"插件只能通过公开 SDK seam 接入,禁止 import 核心内部。这让核心可自由重构。"
