一 · 设计问题:被动 agent 不够用

前面 15 篇讲的 agent 都是被动的——用户发消息,它才动。这在很多场景不够:

  • 定时巡检:agent 该定期检查项目健康(测试是否通过、依赖是否有漏洞),不等用户问。
  • 主动汇报:长任务跑完了,agent 该主动通知用户,而非等用户来查。
  • 后台巩固:记忆整理(第⑥篇 dreaming)该在后台定期跑,不占用对话。
  • 环境感知:检测到重要事件(如 CI 挂了、PR 被评论),主动告知/处理。
  • 持续任务:监控某网站价格、跟踪某 issue 状态,长期跑。

被动 agent 只能做"问答",做不了"助理"。生产级 agent 需要主动能力。但主动性又是危险的——一个会自己发消息、自己执行操作的 agent,如果失控(误判、幻觉、被恶意指令注入),后果比被动 agent 严重得多。自主性的核心矛盾:要有主动性,又要有严格的安全边界。

二 · 分层设计:三种自主机制

┌──────────────────────────────────────────────────────────────────────┐ │ 自主性 · 三种机制 + 安全边界 │ └──────────────────────────────────────────────────────────────────────┘ [机制 1] Heartbeat · 心跳驱动 ┌──────────────────────────────────────────────────────────┐ │ 定时(如每 5 分钟)给 agent 一个"心跳"消息 │ │ · agent 收到后自行决定:有该做的吗? │ │ · 有 → 执行巡检/汇报/跟进 │ │ · 无 → 静默,不打扰用户 │ │ · 把"被动响应"变成"周期性自检" │ └──────────────────────────────────────────────────────────┘ [机制 2] Cron · 定时任务 ┌──────────────────────────────────────────────────────────┐ │ 用户/系统配置 cron 表达式触发 agent │ │ · "每天早 9 点检查依赖漏洞" │ │ · "每周一生成上周总结" │ │ · 适合周期性明确任务 │ └──────────────────────────────────────────────────────────┘ [机制 3] Dreaming · 后台巩固(第⑥篇) ┌──────────────────────────────────────────────────────────┐ │ 离线批处理:短期记忆→长期记忆巩固 │ │ · light(去重)→ deep(高置信晋升)→ rem(模式提炼) │ │ · 不占对话,夜间/低峰跑 │ └──────────────────────────────────────────────────────────┘ ════════════ 安全边界(贯穿所有自主行为)════════════ [主动行为必须受限] · 默认只读/低危:巡检、汇报、记忆整理(无副作用) · 高危需授权:发消息、改文件、调外部 API(需用户预授权或确认) · 可审计:所有自主行为留日志,可追溯 · 可中止:用户能随时暂停/关闭自主性

自主行为的权限分级

级别例子需授权?
只读/内部巡检、记忆巩固、状态检查默认允许
低危外部给用户发通知消息预授权
高危外部改文件、提交代码、调支付 API必须显式确认
不可逆删除数据、发送不可撤回消息禁止自主,只被动

三 · 为何这么设计:三个核心决策

决策 1:为什么 heartbeat + cron 分开

heartbeat 是"周期性给 agent 一个自检机会"——间隔短(分钟级),agent 自己判断有没有该做的。适合环境感知(检测事件、跟进任务)。cron 是"定时执行特定任务"——时间明确(每天 9 点),任务明确。适合周期性固定任务(每日报告、每周总结)。分开是因为:heartbeat 灵活(agent 决定做啥)但可能空转(没该做的),cron 确定但要预定义任务。两者互补:heartbeat 处理"可能有事",cron 处理"确定有事"。

决策 2:为什么 dreaming 必须离线后台

呼应第⑥篇。记忆巩固(短期→长期)是计算密集且不紧急的:要算 embedding、算置信度、去重、合并。如果放对话路径(实时),用户每次对话都等多余计算;且刚说完时置信度信号不足(还没反复使用),判断不准。离线后台:低峰期统一跑,不抢对话资源,积累足够信号后判断更准,可批量优化。这是把"记忆巩固"从"实时负担"变成"离线资产"——用户感知不到,但 agent 的记忆质量持续提升。

决策 3:为什么主动行为必须分级授权

这是自主性的安全基石。一个能自主发消息、改文件的 agent,如果误判(幻觉说"用户让我提交代码"实际没有)或被注入(恶意指令"删除所有文件"),后果灾难。分级授权把风险约束在可控范围:

  • 只读默认允许:巡检不产生副作用,即使误判也不伤。
  • 低危需预授权:发通知类操作,用户提前授权过(允许 agent 主动汇报)。
  • 高危必须显式确认:改文件/提交/外部调用,每次都要用户确认(防误判和注入)。
  • 不可逆禁止:删数据、发不可撤回消息,永远不自主,只被动。

核心原则:自主权限遵循"可逆性"——越不可逆的操作,自主性越受限制。可逆的(只读、可撤回消息)可自主;不可逆的(删除、永久发送)绝不自主。

核心取舍:自主性带来调度系统、权限分级、审计日志、安全护栏的显著复杂度,换来的是agent 从问答工具变成主动助理。替代方案(纯被动)的局限是"做不到定时巡检、主动汇报、后台巩固"。接受复杂度和安全负担,因为主动性是 agent 价值跃迁的关键——但必须用严格的权限分级和可中止性约束它,否则自主 agent 是定时炸弹。

四 · 完整示例:定时巡检发现并修复问题

agent 配置了每日早 9 点 cron 巡检项目健康。某天发现了问题:

[cron 触发 · 早 9 点] "检查项目健康" ↓ [agent 自主执行 · 只读巡检] · 跑测试 → 发现 2 个测试失败 ❌ · 检查依赖 → 发现 lodash 有已知漏洞 ⚠️ · 检查 CI → 最近一次构建失败 ❌ ↓ (发现多个问题,决定汇报 + 部分修复) [主动汇报 · 低危,预授权] · 给用户发消息:"早,巡检发现 3 个问题:测试失败×2、lodash 漏洞、CI 挂了" · 这是预授权的(用户允许 agent 主动汇报) ↓ [尝试自主修复 · 高危,需确认] · agent 想自动升级 lodash 修漏洞 · 但"改文件 + 提交"是高危操作 · 不自主执行,而是问用户:"要我升级 lodash 修复漏洞吗?(会改 package.json)" · 等待用户确认 ↓ [用户确认后] · agent 执行升级 + 跑测试验证 + 提交 · 全程留日志(审计) ↓ [记忆巩固 · 离线] · 夜间 dreaming 把"用户项目用 lodash,曾因漏洞升级"巩固进记忆 · 下次相关场景 agent 记得这个上下文
关键洞察:整个自主流程分级授权——巡检(只读)自主跑、汇报(低危)预授权自主、改文件提交(高危)必须用户确认。agent 主动发现了问题(不等用户问),但危险操作不擅自做。这就是安全自主:主动性 + 可控性。用户感受到的是一个"会主动关心项目、但不越权的助理",而非"乱改东西的隐患"。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点需求:"被动 agent 只能问答,做不了助理。生产需要定时巡检、主动汇报、后台巩固。但自主性危险,必须配安全边界。"
  2. 给三机制:"heartbeat(周期自检)、cron(定时任务)、dreaming(离线记忆巩固)。各有适用场景。"
  3. 主动谈分级:"自主权限按可逆性分级——只读默认允许、低危预授权、高危必须确认、不可逆禁止自主。"
  4. 主动谈安全:"防误判(幻觉'用户让我做')、防注入(恶意指令)、可审计(留日志)、可中止(用户能关)。"
  5. 收口在矛盾:"自主性的核心矛盾是要主动又要安全。解法是把权限约束在可逆操作,高危永远要人确认。"
