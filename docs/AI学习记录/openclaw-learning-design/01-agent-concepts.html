一 · 设计问题:为什么人们总把这三者搅成一团

几乎所有 Agent 框架入门者的第一道坎,就是把"Agent"这个词当成一个模糊的整体。问一个新人"你怎么理解 Agent",答案通常是:"就是那个能调工具、能记住上下文、跟用户对话的东西"。

这个答案在 demo 级别没错,但在生产中是致命的。因为它把三个生命周期完全不同的东西,塞进了同一个概念里:

  • 用户的持续身份偏好(我喜欢 TypeScript、我的项目在哪个目录)——这个应该活很久,跨设备、跨月份。
  • 一次具体对话(今天下午我们讨论了那个 bug)——这个有头有尾,但应该能被回溯、分叉、压缩。
  • 一次模型推理执行(模型这一轮决定调用三个工具然后失败了)——这个可能只活几秒,可能要重试,可能被用户中途取消。

如果把它们当成一个对象,你会被迫回答这些无解的问题:

  • "用户中途取消了"——取消的是身份?是对话?还是这一次推理?三者该一起死吗?
  • "模型超时了要重试"——重试是把整个对话重来?还是只重试这一轮?
  • "同一用户在两个设备同时聊"——是两个 Agent 还是一个 Agent 两次会话?
  • "压缩上下文"——压缩是改了 Agent 的记忆?还是改了对话?还是改了这一轮的输入?

demo 里这些问题不存在,因为 demo 只有一个用户、一次对话、一次成功。生产中这三个生命周期错位时,所有"一个对象"的设计都会状态撕裂。

二 · 分层设计:三个生命周期的边界

正确的做法是把它们建模成三个独立但相关联的对象,各自有清晰的生命周期和职责:

┌──────────────────────────────────────────────────────────────────────┐ │ 三个独立生命周期 │ └──────────────────────────────────────────────────────────────────────┘ AGENT(身份层 · 最长寿命) ┌──────────────────────────────────────────────────────────┐ │ "这个 AI 助手是谁" │ │ · 人格/指令(你怎么称呼我、你的语气、你的能力边界) │ │ · 持久身份(跨所有对话都成立:我喜欢 TS、项目根目录) │ │ · 认证/凭据/模型配置(用哪个 API key、默认模型) │ │ · 寿命:数月~永久 · 一个 Agent 可有 N 个 Session │ └──────────────────────────────────────────────────────────┘ │ 拥有 ▼ SESSION(会话层 · 中等寿命) ┌──────────────────────────────────────────────────────────┐ │ "我们这次讨论的上下文" │ │ · 对话历史(transcript:谁说了什么) │ │ · 会话内状态(本轮用过的工具、待办事项) │ │ · 可被压缩/分叉/回溯(树形结构,不是线性列表) │ │ · 寿命:数小时~数天 · 一个 Session 可有 N 个 Run │ └──────────────────────────────────────────────────────────┘ │ 触发 ▼ RUN(执行层 · 最短寿命) ┌──────────────────────────────────────────────────────────┐ │ "模型这一轮推理的执行实例" │ │ · 一次完整的推理循环(可能多 turn,直到任务完成) │ │ · 可重试、可超时、可取消 │ │ · 终端状态机(running → completed/failed/cancelled/timeout)│ │ · 寿命:数秒~数分钟 · 失败不影响 Agent/Session 存活 │ └──────────────────────────────────────────────────────────┘

三者的职责边界(记住这张表)

维度Agent(身份)Session(会话)Run(执行)
回答的问题"你是谁""我们在聊什么""这一轮在干什么"
典型寿命数月~永久数小时~数天数秒~数分钟
状态内容人格、长期偏好、凭据对话历史、会话内状态推理步骤、工具调用、终端状态
能否被取消极少(删账号)能(结束对话)能且频繁(用户点停止)
能否被重试不适用不适用能且必须设计
失败影响整个助手不可用这次对话中断只这一轮,可重试
数量关系1 Agent → N Sessions1 Session → N Runs1 Run → N turns

三 · 为何这么设计:把"调用 Agent"这件事拆成三层

动机 1:让"失败"成为局部事件

如果三者合一,一次模型超时会带走整个对话上下文(因为"对象"死了)。拆开后,Run 失败只是"这一轮没跑成",Session 完好,用户可以重发消息触发新 Run,前面的讨论一字不丢。这是生产可用性的最低门槛。

动机 2:让"并发"成为可能

同一用户在手机和电脑上同时聊,如果是单一对象,两个请求会互相覆盖状态。拆开后,这是同一 Agent 的两个 Session,各自独立。更进一步,同一 Session 里如果允许并发 Run,就需要会话级串行化(见第⑬篇),但至少身份和会话状态不会被并发撕裂。

动机 3:让"压缩/分叉/回溯"有归属

对话历史是 Session 的属性。压缩改的是 Session 的 transcript(把旧的部分总结掉),不动 Agent 身份。用户想"回到刚才那个分叉点重新讨论"——这是 Session 的树形结构操作,Agent 不需要知道。如果把历史塞进 Agent,每次压缩都在改"Agent 的记忆",跨对话的稳定身份就被破坏了。

动机 4:让"重试"有清晰边界

重试发生在 Run 层(这一轮重新跑),不会是 Session 层(整个对话重来)或 Agent 层(重建身份)。这个边界一旦划清,重试逻辑、超时设计、终端状态机(第⑫篇)才有地方放。

备选方案对比

方案demo 能跑吗生产会崩在哪
单一 Agent 对象(三者合一)能超时=对话丢失;并发=状态撕裂;压缩=身份漂移
两层(Agent + 对话)能重试边界模糊;终端状态无处归属;并发对话内推理 race
三层(Agent/Session/Run)能概念多但边界清晰,每个失败/并发/重试都有归属
核心取舍:三层带来了概念复杂度(用户要理解"我在跟谁聊、聊到哪、这一轮"),换来的是每个生产故障都有清晰的作用域——这是 Agent 框架能否上生产的分水岭。接受这个复杂度是值得的,因为替代方案(单层)的失败模式是数据丢失和状态不一致,不可恢复。

四 · 完整示例:同一用户的三种"调用"语义

用户 Alice 在用她的 coding agent。我们看三个场景,体会"调用 Agent"在不同语境下指代哪一层:

场景 A:"我把 agent 配置成用 Claude"

操作层:Agent 身份

改了什么:这个 AI 助手的默认模型偏好

影响范围:Alice 之后所有对话都用 Claude

不动的:已有的对话历史、当前正在跑的推理

场景 B:"开个新对话聊聊那个 bug"

操作层:Session 会话

做了什么:在 Alice 的 Agent 下新建一个 Session

影响范围:这个对话有自己的历史,与之前讨论无关

不动的:Agent 身份;其他 Session

场景 C:"这次回复太慢,停掉重来"

操作层:Run 执行

做了什么:取消当前 Run,新发消息触发新 Run

影响范围:只这次推理;前面的对话历史完整保留

不动的:Agent;Session;已确认的工具结果

关键洞察:同一个用户操作("点停止""换模型""新对话")落在不同层,语义天差地别。框架必须让每一层都能独立被操作而不污染其他层。这就是为什么要拆三层。

五 · 面试官视角:这题在考察什么

面试官问"你怎么理解 Agent / Session / Run"时,真正想听的不是定义背诵,而是想确认你有没有生产经验的分水岭:
回答层次面试官的判断
把三者说成同义词 / 模糊带过"没做过生产 Agent,只玩过 demo"
能背出"Agent 是身份、Session 是对话、Run 是执行""看过文档,但还没遇到真实问题"
能说清三者生命周期不同,并举出"失败该归哪层""并发怎么不撕裂""有生产意识,及格"
能主动谈到"压缩改的是 Session 不动 Agent""重试只发生在 Run 层""取消的语义取决于取消哪层""做过,深挖有料"

这题是暖场题也是筛人题:答得浅,后面的问题会越来越难答出生产味;答得深,面试官知道可以往深问压缩、并发、终端状态这些硬骨头。

六 · 面试者视角:如何答出生产洞察

结构化作答模板(按这个顺序,主动展现深度):
  1. 先划边界:"我把这三者理解为三个生命周期不同的对象——Agent 是身份(数月级),Session 是会话(数小时级),Run 是单次推理执行(数秒级)。"
  2. 立刻给生产动机:"这样拆的核心价值是让失败成为局部事件。一次模型超时只是 Run 失败,Session 和 Agent 完好,用户能立刻重试而对话不丢。"
  3. 主动举并发场景:"同一用户多设备同时聊,是同一 Agent 的两个 Session,各自独立。如果不拆,两个请求会互相覆盖状态。"
  4. 主动举压缩场景:"压缩改的是 Session 的 transcript,不动 Agent 身份。这样长期偏好(我喜欢 TS)不会被某次对话的压缩影响。"
  5. 收口在取舍:"代价是概念复杂度,但替代方案(单层)的失败模式是数据丢失和状态不一致,不可恢复,所以这个复杂度是必须接受的。"
要主动展现的生产洞察(不要等问):
  • "取消"的语义取决于取消哪层——取消 Run vs 取消 Session vs 删 Agent 完全不同
  • 重试只发生在 Run 层,不会是 Session 或 Agent 层
  • 三者关系是树形(1 Agent → N Sessions → N Runs),不是线性
