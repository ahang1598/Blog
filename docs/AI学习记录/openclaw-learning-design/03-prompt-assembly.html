一 · 设计问题:Prompt 拼接不是字符串相加

demo 级 Prompt 拼接就是字符串拼接:system = 指令 + 工具描述 + 用户档案 + 当前时间 + ...。能跑就行。

但生产中,Prompt 拼接是整条推理链路最贵的操作之一,因为现代模型 API 有提示词缓存(prompt cache):如果两次请求的 Prompt 前缀完全相同,后端可以复用已计算的注意力,跳过那一大段的重复计费和延迟。一个 Agent 在长对话中要发几十上百次请求,如果每次前缀都变了,缓存永远 miss,成本和延迟翻几倍。

缓存命中是按字节的前缀匹配:只要前缀有一个 token 不同,后面全部 miss。所以"什么内容放前面、什么内容放后面"不是排版问题,是经济学问题。

同时,Prompt 还要满足一堆互相打架的需求:

  • 身份/指令要稳定(跨 turn 不变,享受缓存)
  • 当前时间/工具进度/用户消息要实时(每 turn 都变)
  • 不同 provider 要能注入自己的调优(语气、工具调用风格)但不能污染核心指令
  • 插件/skills/记忆要能动态注入但不能无序(无序=缓存爆)
  • 截断(内容太长)与保持身份稳定冲突

二 · 分层设计:稳定前缀 vs 易变后缀

核心设计原则:把 Prompt 切成两段,用一条明确的缓存边界分开。边界以上是跨 turn 几乎不变的内容(享受缓存),边界以下是每 turn 必变的内容(认了 miss)。

┌──────────────────────────────────────────────────────────────────────┐ │ 最终 Prompt 的概念结构 │ └──────────────────────────────────────────────────────────────────────┘ ┌─ 稳定前缀(STABLE · 缓存命中区)────────────────────────┐ │ · 核心身份/人格("你是 X,一个 coding agent") │ · 工作区上下文(项目根目录、技术栈、AGENTS 指令) │ · 工具清单(name + 一句话摘要,按字典序排序) │ · Skills 元数据清单(只放名字+版本,不放全文) │ · 长期记忆种子(MEMORY.md 内容) │ → 这些跨 turn 几乎不变,provider 可缓存整段 └──────────────────────────────────────────────────────┘ ════════════ 【缓存边界 CACHE BOUNDARY】 ════════════ ┌─ 易变后缀(VOLATILE · 每 turn 必变)────────────────────┐ │ · 当前时间/时区(精确到秒,每次都不同) │ · 运行时环境(活跃进程、节点状态、当前通道) │ · 本轮的工具进度/heartbeat 提示 │ · 模型身份行(用哪个模型,通常放这里以保前缀稳定) │ · Provider 注入的动态后缀(语气调优等) │ → 接受 miss,但体量小、改动可预测 └──────────────────────────────────────────────────────┘ ↓ 之后是 messages 数组(对话历史 + 本轮用户消息) 历史本身也可能有独立缓存策略(见第⑤篇)

三个关键切分决策

决策放哪为什么
核心身份/人格/工作区指令稳定前缀跨 turn 不变,缓存价值最大
工具清单 + Skills 元数据稳定前缀(且排序)不排序则顺序漂移致缓存 miss
模型身份("你是 gpt-5")易变后缀(边界下)换模型很频繁,放前面会让整段缓存失效
当前时间易变后缀每秒都变,放前面 = 缓存永远死
Provider 私有调优通过具名 section 注入不污染核心,可替换三个固定 section

三 · 为何这么设计:缓存边界为何值钱

动机 1:经济学

大模型推理的预填充(prefill)成本和 Prompt 长度近似线性。一个 Agent 的稳定前缀如果有 8000 token,缓存命中后这 8000 token 几乎免费(折扣可达 10x);如果因为某个易变内容放错位置导致前缀崩了,每个 turn 都要重新预填充这 8000 token。长对话 100 turn,差距是 100 倍的预填充成本。缓存边界的位置直接决定产品能不能挣钱。

动机 2:延迟

预填充也是延迟的主要来源(首 token 时间 TTFT)。缓存命中能让 TTFT 从秒级降到百毫秒级,用户体验天差地别。

动机 3:Provider 注入不污染核心

不同 provider(OpenAI/Anthropic/Google)对"怎么调优模型表现"有不同偏好(语气、工具调用风格、执行偏好)。如果这些散落在核心 Prompt 各处,核心就provider-specific 了,失去通用性。设计上用三个具名 section(如 interaction_style / tool_call_style / execution_bias)让 provider 替换或追加固定位置,核心只声明 section 槽位,不写 provider 内容。这样核心保持纯净,provider 调优隔离可替换。

动机 4:确定性排序

工具列表、skills 列表、记忆条目——这些必须排序再序列化。如果用哈希表遍历顺序(语言 runtime 不保证),同一组内容两次序列化顺序不同,字节级前缀就不同,缓存 miss。生产设计强制确定性的排序(字典序、版本序)。

核心取舍:严格的前缀切分让 Prompt 拼接从"字符串相加"变成"缓存优化的数据结构",代价是任何想加入前缀的内容都要论证它确实跨 turn 稳定。这个论证负担是值得的——它逼着你把"易变"和"稳定"分开建模,避免某个随手加的"当前时间"毁了整个对话的缓存。接受这个纪律,因为替代方案(随意拼接)的成本是不可控的。

备选方案对比

方案demo 能跑生产崩点
字符串拼接,顺序随意能缓存永远 miss;成本和延迟翻数倍
分两段但不强制排序能哈希顺序漂移致前缀字节不同,缓存偶尔 miss 难排查
严格切分 + 确定性排序 + 具名 section 注入能缓存稳定命中,成本可控,核心纯净

四 · 完整示例:一次完整拼接的概念产物

下面是一个 coding agent 某次请求最终拼接出的系统 Prompt 概念结构(只展示形态,不展示具体措辞):

[STABLE] 核心身份 "你是 OpenClaw,一个专注于编程协作的 agent。你的工作方式是..."(人格 + 工作纪律,跨 turn 不变)
[STABLE] 工作区上下文 仓库:/Users/alice/myproject · 技术栈:TypeScript + React · AGENTS.md 指令(项目编码规范、提交流程)
[STABLE] 工具清单(字典序) read · write · exec · web_search · ...(每个工具一行:名字 + 一句话摘要 + 参数 schema 引用)
[STABLE] Skills 元数据(只放索引) code-review(v1, sha256:abc...) · git-helper(v2, sha256:def...) · doc-summary(v1, sha256:ghi...) → 告诉模型"需要时 read 完整定义",不塞全文(见第⑦篇)
[STABLE] 长期记忆种子 MEMORY.md 内容:"用户偏好 TypeScript、用 pnpm、不喜欢 any 类型..."
══════ 缓存边界 · 以上跨 turn 稳定,以下每 turn 变 ══════
[VOLATILE] 当前时间 2026-08-02 14:23:07 UTC+8(精确到秒)
[VOLATILE] 运行时环境 活跃进程:无 · 节点状态:1 个本地节点在线 · 通道:CLI
[VOLATILE] 模型身份 "你当前以 gpt-5 运行"(放这里是为了换模型时不破坏上面的缓存)
[VOLATILE] Provider 注入(gpt-5 family overlay) interaction_style / tool_call_style / execution_bias 三个具名 section 的内容
关键洞察:换模型只动"模型身份行"和"Provider 注入"——都在缓存边界以下。所以同一对话里换 gpt-5 为 claude,稳定前缀(身份/工作区/工具/skills/记忆)的缓存依然命中。如果把"模型身份"放最前面,换模型就让整段缓存失效——这是新手最常犯的错。

五 · 面试官视角:这题在考察什么

回答层次面试官的判断
"就是把指令、工具、用户消息拼一起""只做过 demo,没考虑成本"
知道有 prompt cache 这回事"听过但没生产经验"
能说"稳定内容放前面,易变放后面""有意识,及格"
能谈缓存边界、确定性排序、provider 具名 section 注入、模型身份为何放后面"生产经验扎实,懂经济学"

这题特别能区分"调过 API"和"做过产品"。前者只知道拼接能跑,后者知道拼接的位置决定成本和延迟。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点经济学:"Prompt 拼接不是字符串相加,是缓存优化问题。现代 API 有 prompt cache,前缀字节级相同可复用注意力,缓存命中能让成本和延迟降一个数量级。"
  2. 给切分原则:"所以我把 Prompt 切成稳定前缀和易变后缀,中间一条明确的缓存边界。身份、工作区、工具清单、skills 索引、长期记忆这些跨 turn 不变的放前面;当前时间、运行时状态、模型身份、provider 调优放后面。"
  3. 主动谈确定性排序:"前缀里的列表(工具、skills、记忆条目)必须确定性排序再序列化,否则哈希表遍历顺序漂移会让字节级前缀不同,缓存偶发 miss,极难排查。"
  4. 主动谈 provider 隔离:"不同 provider 的调优通过具名 section 注入(interaction_style 等固定槽位),核心只声明槽位不写 provider 内容,这样核心保持纯净、provider 可替换。"
  5. 主动谈陷阱:"最常犯的错是把'模型身份'放最前——换模型就让整段缓存失效。正确做法是放缓存边界之后,这样同对话换模型也不破坏前缀缓存。"
主动展现的生产洞察:
  • 缓存是字节级前缀匹配,一个 token 差就全 miss
  • 排序纪律不只是美观,是经济学
  • 截断(bootstrap 文件太长)与稳定身份有张力,需要 per-file 限额 + 截断标记
