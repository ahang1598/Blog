一 · 设计问题:复杂任务一个 agent 干不动

现实任务往往需要并行或分工:"调研三个竞品并对比"——一个 agent 串行查三个慢;"写代码同时跑测试"——一个 agent 串行做效率低;"主任务进行中分出一个子任务深挖某个点"——主任务不该被阻塞。

直觉解法 A:在一个 agent 内并发调工具。但这只是工具并行(第④篇),不是任务分工——还是同一个 agent、同一份上下文、同一个推理循环,无法让"子任务"有独立的上下文、独立的模型选择、独立的工具策略。

直觉解法 B:开多个独立 agent 进程。但这样它们互不知道彼此——没有父子关系,无法自动通知完成,无法继承父的策略,无法协调共享资源(同一工作树)。

生产需求其实是:一个 agent 能在运行中派生出"另一个 agent 实例"来完成子任务,完成后自动通知,且子 agent 继承父的部分策略但有自己的独立上下文。

二 · 分层设计:子 agent = 另一个 session

┌──────────────────────────────────────────────────────────────────────┐ │ 子 Agent · 递归 session 模型 │ └──────────────────────────────────────────────────────────────────────┘ [父 Session · 主任务] ┌──────────────────────────────────────────────────────────┐ │ 父 agent 正在跑主任务,决定委派一个子任务 │ │ · 调 sessions_spawn 工具 │ │ · 参数:子任务描述、可选模型/工具策略/是否等待 │ └──────────────────────────────────────────────────────────┘ │ spawn ▼ [子 Session · 独立 agent 实例] ┌──────────────────────────────────────────────────────────┐ │ 创建一个新 Session(不是更小的运行时!) │ │ · 有自己的 session key、上下文、推理循环 │ │ · 用完整运行时(和父一样的能力栈) │ │ · 但 prompt mode = minimal(精简,聚焦子任务) │ │ · 工具策略从父继承并可收紧(不能放宽) │ │ · 记录 parentSessionKey + spawnedBy(父子树可查) │ │ · 独立 lane(不阻塞父,见第⑬篇) │ └──────────────────────────────────────────────────────────┘ │ 完成时 ▼ [push-based 完成通知] ┌──────────────────────────────────────────────────────────┐ │ 子 agent 完成后 主动推送结果给父 session │ │ · 父不需要轮询 sessions_list 等结果 │ │ · 完成事件作为"steering 消息"注入父的下一轮 │ │ · 父据此继续主任务 │ └──────────────────────────────────────────────────────────┘

两种 spawn 模式

模式语义用途
run(一次性)子 agent 跑完即结束,返回结果独立子任务("查个东西")
session(持久)子 agent 是持久会话,可后续交互长期助手(需绑定 thread)

两种模式都可配 collect=true(父同步等待)或异步(父继续干别的)。

三 · 为何这么设计:三个核心决策

决策 1:为什么子 agent 是"另一个 session"而非"更小的运行时"

这是最关键的设计选择。把子 agent 实现为完整的 session(用完整运行时),而不是阉割版的迷你 agent。原因:① 能力对等——子任务可能和父任务一样复杂(调研某竞品可能比主任务还重),用阉割版会让子任务能力不足;② 递归性——子 agent 自己也能再派生子 agent(任务的子任务),只有用完整 session 才能无限递归;③ 统一性——一套运行时代码跑所有层级,不必维护"主 agent 运行时"和"子 agent 运行时"两套。子 agent 的"精简"体现在 prompt mode(minimal)和工具策略(收紧),而非运行时阉割。

决策 2:为什么 push-based 完成而非轮询

轮询(直觉做法)

父 spawn 后循环查"子好了吗"

• 浪费父的 turn(每个 turn 查一次)

• 占父的上下文(查询历史堆积)

• 延迟高(平均等半个轮询间隔)

• 父被"看孩子"占住,干不了别的

push-based 完成通知

子完成主动推消息给父

• 父不浪费 turn 查询

• 父上下文干净(只有结果)

• 零延迟(完成即通知)

• 父可并行干别的(异步 spawn)

push 的实现:子完成时,把结果作为 steering 消息(导向消息)注入父的下一轮推理。父在下一个 turn 自然看到"子任务 X 完成,结果是 Y",据此继续。这是把"父等子"从同步轮询变成事件驱动,大幅提升并行效率。

决策 3:为什么工具策略"只继承可收紧,不能放宽"

父 agent 可能被授予了某些工具权限(如 exec 命令)。派生子 agent 时,子继承父的策略,但只能收紧不能放宽——父能给子更严的限制(禁用某危险工具),但不能给子比自己更宽的权限(父没有的权限不能凭空给子)。

这是权限单调性:权限只能沿父子树下降或保持,不能上升。原因:① 安全——防止子 agent 通过派生绕过父的限制(父禁用 exec,子不能给自己开 exec);② 可预测——父知道子的能力边界是自己的子集,不会失控;③ 责任链清晰——某子 agent 做了危险操作,能追溯到授权链。

核心取舍:递归 session + push 通知 + 策略单调继承带来调度和协调的复杂度(父子树管理、steering 注入、策略传递),换来的是真正的任务分工能力——并行、独立上下文、递归委派、自动通知。替代方案(单 agent 工具并行)无法提供独立上下文和任务级分工;(多独立进程)无法协调。子 agent 模型让 agent 能像团队一样工作,这是从"工具"到"团队"的跃迁。

四 · 完整示例:父 agent 派发调研任务

用户让主 agent "调研 React、Vue、Svelte 三个框架并对比"。父 agent 决定并行派发三个子 agent:

[父 Session · t0] 收到"调研三框架对比" · 推理:这能并行,派 3 个子 agent · spawn(子A: "调研 React", mode=run, collect=false) ← 异步 · spawn(子B: "调研 Vue", mode=run, collect=false) · spawn(子C: "调研 Svelte",mode=run, collect=false) · 父告诉用户"已派出 3 个子任务,完成后汇总" · 父可以继续干别的(不被阻塞) [子 Session A · 并行跑] · 独立上下文,跑完整推理循环(查资料、调用工具) · 工具策略 = 父的策略子集(只读,不能 exec 危险命令) · prompt mode = minimal(聚焦"调研 React") [子 A 完成 · t5] · push 通知父:"子A完成,React 调研结果是..." · 作为 steering 消息注入父下一轮 [子 B 完成 · t6] · push 通知父 [子 C 完成 · t7] · push 通知父 [父 Session · t8] 三个 steering 消息都到了 · 父推理:基于三个结果,生成对比报告 · 输出给用户
关键洞察:三个子任务并行跑(总耗时 ≈ 最慢的一个,而非三个之和),父在此期间不被阻塞(可响应用户别的问题),完成后自动汇总(steering 消息驱动)。这就是 push-based 委派的效率——相比父串行查三个(耗时 3x)或父轮询等(浪费 turn),这是数量级的提升。

五 · 面试官视角:这题在考察什么

回答层次面试官的判断
"开多线程调工具""没理解任务级分工"
知道要派子 agent,但用轮询"有意识但效率差"
能说独立 session + push 通知"及格"
能谈递归性、完整运行时、策略单调继承、steering 注入"生产经验扎实"

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点需求:"复杂任务要分工——独立上下文、并行、递归。单 agent 工具并行做不到任务级分工。"
  2. 给递归模型:"子 agent 实现为另一个 session(完整运行时,不是阉割版),有独立上下文、独立模型、独立推理循环。父子关系记录成树。"
  3. 主动谈 push:"完成通知用 push 而非轮询——子完成主动推 steering 消息给父下一轮。父不浪费 turn 查询,零延迟,可异步并行干别的。"
  4. 主动谈策略继承:"工具策略从父继承,只能收紧不能放宽(权限单调性)。安全:子不能通过派生绕过父的限制。"
  5. 主动谈递归性:"子 agent 用完整运行时,所以自己也能派生子 agent——无限递归。一套代码跑所有层级。"
