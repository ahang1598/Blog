一 · 设计问题:接 10 个厂商怎么不烂

生产 Agent 要支持多家模型厂商:OpenAI、Anthropic、Google、Mistral、Azure、本地 Ollama、vLLM... 每家的 API 都不同:

  • 端点不同:不同 baseUrl、不同认证(Bearer/OAuth/API key)
  • 请求格式不同:messages 结构、tool 定义、stream 格式
  • 能力不同:有的支持 thinking,有的不支持;tool schema 容忍度不同
  • 错误码不同:同样的"限流"各家返回不同

demo 级做法:在核心里写 if (provider === 'openai') {...} else if (provider === 'anthropic') {...}。10 个厂商就 10 个分支,核心臃肿,加新厂商改核心,核心和厂商绑死。

更隐蔽的问题:很多新厂商其实和某家老厂商 API 兼容(如 DeepSeek、Moonshot 都兼容 OpenAI API)。如果按 provider-id 路由,即使 DeepSeek 用的是 OpenAI 格式,也得为它单独写一套适配——重复劳动。

二 · 分层设计:API family 注册表

┌──────────────────────────────────────────────────────────────────────┐ │ Provider 路由 · API family 抽象 │ └──────────────────────────────────────────────────────────────────────┘ [关键洞察] 按协议家族路由,不按厂商 ┌──────────────────────────────────────────────────────────┐ │ 很多厂商共用同一套 API 协议: │ │ · openai-completions 家族:OpenAI/DeepSeek/Moonshot/... │ │ · anthropic-messages 家族:Anthropic │ │ · openai-responses 家族:新版 OpenAI/Azure │ │ · google-generative-ai:Google │ │ · 路由按家族,适配器按家族写一遍,多厂商复用 │ └──────────────────────────────────────────────────────────┘ [三层路由] ┌──────────────────────────────────────────────────────────┐ │ ① 模型声明其 family │ │ Model { id, api: "openai-completions", baseUrl, ... } │ │ ② api-registry 按 family 注册适配器 │ │ Map │ │ ③ 运行时按 model.api 查 registry 找适配器 │ │ 不问"哪个厂商",只问"说哪种协议" │ └──────────────────────────────────────────────────────────┘ [厂商 specifics 在插件] ┌──────────────────────────────────────────────────────────┐ │ 每个厂商插件管自己的:认证、模型目录、特殊兼容、错误分类 │ │ · 但都用所属 family 的通用 stream 适配器发请求 │ │ · 厂商差异隔离在插件,核心只懂 family │ └──────────────────────────────────────────────────────────┘

API family 抽象的价值

做法加新厂商(兼容 OpenAI API)
按 provider-id 路由核心加分支 + 写全套适配(重复)
按 API family 路由新厂商插件声明 family=openai-completions,复用现有适配器,只写厂商特定(认证/目录)

三 · 为何这么设计:三个核心决策

决策 1:为什么按 API family 而非 provider-id

这是解耦点的选择。如果按 provider-id,解耦点在"厂商边界"——每个厂商一套逻辑,即使两家 API 完全相同也得分别写。按 API family,解耦点在"协议边界"——共用协议的厂商复用同一适配器。这抓住了市场的真实结构:很多厂商是"兼容某主流 API 的替代品"(OpenAI 兼容生态特别大),按协议家族抽象让适配器数量 ≈ 协议家族数(几个),远小于厂商数(几十)。加新厂商(兼容已有协议)几乎零成本。

决策 2:为什么 harness 选择要 fail-closed

harness(运行时实现)可能有多个来源:OpenClaw 自带、第三方(如 Codex app-server)。选择 harness 时,如果用户配置了"用 codex harness"但 codex 不可用,fail-closed(失败关闭)——明确报错而非静默回退到自带 harness。为什么:① 用户意图明确——用户指定 codex 是有原因的(可能依赖它的特定行为),静默回退会让用户以为在用 codex 实际不是,行为不符预期,难调试;② 避免隐式行为——生产要可预测,配置了啥就是啥,不可用就报错让用户知道。例外:"auto" 模式允许回退(用户没指定具体 harness,系统自动选最合适的)。核心原则:显式配置 fail-closed,自动模式可回退。

决策 3:为什么厂商 specifics 隔离在插件

虽然两家厂商用同一家族协议(如 openai-completions),但仍有厂商特定差异:① 认证方式(OpenAI 用 Bearer,某厂商用自定义头);② 模型目录(各自支持的模型列表);③ 特殊兼容(某厂商的 tool schema 有怪癖要预处理);④ 错误分类(同样 429,一家可重试一家是硬限)。这些不能强行塞进通用适配器(会污染家族逻辑),也不能塞进核心(违背 plugin-agnostic)。放厂商插件:每个厂商插件管自己的 specifics,通过钩子注入到通用流程(如"发请求前预处理认证""收到错误后分类是否可重试")。家族适配器管通用,插件管特定,核心只懂 family——三层清晰。

核心取舍:API family 抽象 + harness 选择 + 插件 specifics 带来家族识别、适配器复用、插件钩子设计的复杂度,换来的是加厂商低成本、核心不被污染、协议演进灵活。替代方案(按厂商 if/else)的失败模式是"核心臃肿、重复适配、加厂商改核心"。接受复杂度,因为模型生态正在爆发式增长,按 family 抽象是控制复杂度的唯一可持续方式。

四 · 完整示例:"用 gpt-5"的解析全过程

[用户/配置] "用 gpt-5" ↓ [模型解析] gpt-5 → Model 对象 · id: "gpt-5" · api: "openai-responses"(声明协议家族) · baseUrl: "https://api.openai.com/v1" · provider 插件: openai ↓ [路由 · 按 family] · 查 api-registry["openai-responses"] · 找到通用 stream 适配器(负责构造请求/解析流) ↓ [openai 插件 specifics] · 认证:用用户的 OpenAI key 注入 Bearer · 模型目录:gpt-5 在目录里 ✓ · 错误分类:429 可重试(退避),401 凭据过期(刷新) ↓ [发请求] · 通用适配器 + openai 插件 specifics 组合 · POST /v1/responses(家族协议) + Bearer(厂商认证) ↓ [对比:加 DeepSeek(兼容 openai-completions)] · DeepSeek 插件声明 api: "openai-completions" · 复用 openai-completions 家族的 stream 适配器 ✓ · 只写 DeepSeek specifics:认证(它的 key)、baseUrl、模型目录 · 核心/适配器零改动
关键洞察:加 DeepSeek 这种"OpenAI 兼容"厂商,核心和适配器都不用改——DeepSeek 插件声明它用 openai-completions 家族,复用现有适配器,只写自己的 specifics(认证/目录)。这就是 family 抽象的威力:加兼容厂商近乎零成本。如果按 provider-id,DeepSeek 要从核心到适配器全套重写。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点问题:"多家厂商 API 不同,if/else 会核心臃肿。且很多厂商兼容同一协议,按厂商路由重复劳动。"
  2. 给 family 抽象:"按 API family(协议家族)路由——openai-completions/anthropic-messages 等。模型声明 family,registry 按 family 注册适配器,复用。"
  3. 主动谈解耦点:"解耦点在协议边界而非厂商边界。加兼容厂商(DeepSeek 兼容 OpenAI)近乎零成本,只写 specifics。"
  4. 主动谈 specifics 隔离:"厂商特定(认证/目录/兼容怪癖)在厂商插件,通过钩子注入通用流程。家族管通用,插件管特定。"
  5. 主动谈 fail-closed:"显式配置 harness 失败 fail-closed(报错不静默回退),auto 模式可回退。生产要可预测。"
