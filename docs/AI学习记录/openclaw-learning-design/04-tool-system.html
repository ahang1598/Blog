一 · 设计问题:工具不是"函数调用"

demo 级工具系统:定义几个函数,模型说调哪个就调哪个,把返回值塞回消息。简单。

但生产中,"工具"承载了远超函数调用的复杂度。一次工具交互要回答这些问题,而每个都藏坑:

  • 契约:模型传的参数怎么知道对不对?模型常把数字传成字符串、JSON 传成转义字符串。
  • 派发:模型一次要调 5 个工具,哪些能并行哪些必须串行?一个改文件一个读同一文件,顺序错了结果错。
  • 配对:工具调用(tool_use)和工具结果(tool_result)怎么严格对应?漏配会让 provider 报错甚至崩溃。
  • 副作用:工具失败了,已经写的文件回滚吗?重试会重复写吗?
  • 权限:哪些工具模型能调?子 Agent 能不能调危险工具?
  • 取消:工具执行到一半用户取消,怎么干净停止不留半成品?

把这些都塞进"调个函数"的心智,生产必崩。

二 · 分层设计:契约、派发、配对三个子系统

┌──────────────────────────────────────────────────────────────────────┐ │ 工具系统 · 三个子系统 │ └──────────────────────────────────────────────────────────────────────┘ [1] 契约子系统 · 工具怎么定义 ┌──────────────────────────────────────────────────────────┐ │ AgentTool = { │ │ name, label, │ │ parameterSchema: │ ← 模型可见,定义合法参数形态 │ outputSchema: <类型契约,描述返回值> │ │ executionMode: "sequential" | "parallel" │ ← 派发策略声明 │ execute(callId, params, signal, onUpdate): Promise │ ← 实际执行 │ } │ └──────────────────────────────────────────────────────────┘ │ ▼ [2] 派发子系统 · 一次工具调用怎么跑 ┌──────────────────────────────────────────────────────────┐ │ 模型返回 N 个 tool_use │ │ ├─ 扫描:任一工具声明 sequential? → 整批串行 │ ← 一个 sequential 降级整批 │ ├─ 否则:并行 prepare(顺序) + 并行 execute │ │ ├─ prepare 四阶段: │ │ │ resolve(找工具) → prepareArgs → validate(契约) │ │ │ → beforeCall(hook) │ │ └─ 结果按模型原始顺序排成 ToolResultMessage │ ← 保 provider 消息顺序 └──────────────────────────────────────────────────────────┘ │ ▼ [3] 配对子系统 · tool_use ↔ tool_result 不变量 ┌──────────────────────────────────────────────────────────┐ │ 每个 tool_use 必须有且仅有一个 tool_result 回应 │ ← 硬不变量 │ · 漏配 → provider 报错("unexpected tool_use_id") │ │ · 压缩/截断历史时必须修复孤儿配对 │ │ · 中断后合成"失败 tool_result"防止悬空 tool_use │ └──────────────────────────────────────────────────────────┘

三个关键设计点

设计点做法不这么做的后果
类型契约(TypeSchema)每个工具有正式的类型 schema 描述参数模型传错参数只能运行时炸;无法自动校验/纠偏
executionMode 声明工具自己声明 sequential 或 parallel框架瞎猜并行性,副作用工具并发写文件竞态
结果按原始顺序并行执行但结果按模型给的顺序回排provider 报"tool_use_id 顺序不符"

三 · 为何这么设计:类型契约、降级策略、硬不变量

动机 1:为什么用类型 schema 而非自由字符串

模型不是程序,它会传错参数:让它传数字它传 "42"(字符串),让它传对象它传 JSON 字符串。如果工具只接受"自由参数",这些错误只能运行时炸,且模型不知道哪里错了。用正式的类型 schema 后:1)框架能在调用前校验并纠偏(字符串数字转数字、JSON 字符串解析成对象);2)校验失败能返回结构化错误给模型让它重试;3)schema 本身就是给模型看的契约文档,模型据此组织参数。这是把"祈祷模型别传错"变成"防御性契约"。

动机 2:为什么"一个 sequential 降级整批"

并行执行是为了快,但副作用工具不能乱并行。比如"写文件 A"和"写文件 B"看似独立,但若它们改的是同一项目,顺序可能影响结果(后写覆盖先写)。设计上让每个工具自己声明是否必须串行,一旦批里有一个声明 sequential,整批退化为串行执行。这是个保守策略——宁可慢也别错。为什么是"整批"而非"只串行那一个"?因为工具间可能有隐式依赖(都改同一文件),保守地全串行最安全。接受这个保守,因为并行写坏文件的排查成本远高于串行的延迟成本。

动机 3:为什么 tool_use/tool_result 配对是硬不变量

provider API 强制要求每个 tool_use 必须恰好有一个 tool_result 回应。少一个,下次请求 provider 报"unexpected tool_use_id"直接崩;多一个,也被拒。这不是建议是硬约束。所以:1)工具执行失败也要合成一个"失败 tool_result"(不能漏);2)压缩历史时若删了 tool_use 必须同时删对应 result,反之亦然(孤儿修复);3)用户中途取消,正在执行的 tool_use 要合成中断结果。这个不变量贯穿压缩、中断、重试所有路径。

动机 4:为什么 prepare 要分四阶段

"调用工具"其实有四步:resolve(工具存不存在/有没有权限)→ prepareArgs(注入运行时上下文如当前路径)→ validate(契约校验)→ beforeCall(hook 拦截/审计)。分开是因为每步可能短路失败:resolve 失败说明工具不可用,validate 失败说明参数错,这些都要返回不同的结构化错误给模型,而不是混在一起报"调用失败"。也便于 hook 在 beforeCall 统一拦截(如安全审计)。

核心取舍:类型契约 + executionMode 声明 + 配对不变量带来定义工具时的纪律负担(每个工具要写 schema、声明模式、保证幂等可重试),换来的是校验/纠偏/审计/并行安全都成为框架统一能力。替代方案(自由函数)的失败模式是"模型传错参数运行时炸、副作用工具并发竞态、压缩后 provider 报错崩"。接受纪律,因为它把不可控的运行时炸点变成可控的编译期契约。

四 · 完整示例:三个工具的混合派发时间线

模型这一轮返回了三个 tool_use。我们看派发子系统如何处理:

[模型返回 3 个 tool_use] ├─ read(package.json) ← 声明 parallel ├─ write(config.ts, "...") ← 声明 sequential(副作用) └─ web_search("best practices") ← 声明 parallel [派发扫描] write 声明了 sequential → 整批退化为串行 (虽然 read 和 web_search 本可并行,但保守全串行) t0 [prepare read] resolve✓ prepareArgs(注入工作区)✓ validate✓ beforeCall✓ t1 [execute read] → 返回 package.json 内容 ✅ t2 [prepare write] ... (四阶段全过) t3 [execute write] → 文件写入 ✅ t4 [prepare web_search] ... t5 [execute web_search] → 返回搜索结果 ✅ [结果回排] 按模型原始顺序:[read 结果, write 结果, web_search 结果] → 组成 ToolResultMessage 喂回模型 → 模型基于三个结果继续推理
关键观察:即使 read 和 web_search 本可以并行跑(省时间),因为 write 声明了 sequential,整批串行。这是保守换取安全。如果三个都声明 parallel,prepare 仍顺序(快),但 execute 会 Promise.all 并发,结果依然按模型原始顺序回排——并发执行不破坏 provider 消息顺序契约。

回答层次面试官的判断

知道有 schema 校验"有意识但浅"

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点三个子系统:"我会把工具系统拆成契约、派发、配对三个子系统。契约用类型 schema 定义参数,派发决定串并行,配对保证 tool_use/result 对应。"
  2. 立刻给契约动机:"用类型 schema 而非自由参数,是因为模型常传错(字符串数字、JSON 字符串)。schema 让框架能在调用前校验纠偏,失败返回结构化错误让模型重试,而不是运行时炸。"
  3. 主动谈降级策略:"派发上让工具自己声明 executionMode,批里有一个 sequential 就整批串行。这是保守策略——副作用工具并发竞态的排查成本远高于串行延迟。"
  4. 主动谈配对不变量:"tool_use/tool_result 配对是 provider 的硬约束,少一个多一个都会让下次请求崩。所以工具失败也要合成失败结果,压缩历史要修复孤儿配对,中断要合成中断结果。"
  5. 收口在取舍:"代价是定义工具时要写 schema、声明模式、保证幂等,换来的是校验/审计/并行安全都成框架统一能力。"
主动展现的生产洞察:
  • "并行 execute 但结果按模型原始顺序回排"是 provider 契约要求,不是可选优化
  • prepare 分四阶段是为了每步能短路返回不同结构化错误
  • 幂等性是工具能否安全重试的前提(非幂等工具如发邮件绝不能自动重试)
