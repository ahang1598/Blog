一 · 设计问题:并发会让 agent 状态撕裂

生产中,同一个 agent 会面临并发:

  • 用户连发两条消息(第二条在第一条还没跑完时到达)
  • 用户在手机和电脑同时发消息(同一 session 或不同 session)
  • 子 agent 正在跑,父 agent 又接到新消息
  • 多个定时任务(cron)同时触发同一 agent

demo 级做法:无并发控制,每个请求各跑各的。生产中这会撕裂状态:

[Race 场景 · 同 session 并发两个 run] Run A (消息1): 读 config.ts → 看到 version=1 Run B (消息2): 同时读 config.ts → 看到 version=1 Run A: 改成 version=2 → 写入 Run B: 改成 version=3(基于它读到的 version=1)→ 写入 结果:version=3,Run A 的修改被覆盖丢失 ❌ [更糟:transcript 撕裂] Run A 和 Run B 都往同一 session 的 transcript 追加消息 → 历史顺序错乱,模型下次看到的是交错的对话 → 上下文不一致,推理质量崩

并发不是性能优化问题,是正确性问题。无控制的并发会让 agent 的状态(文件、transcript、会话上下文)撕裂,产生不可恢复的不一致。

二 · 分层设计:session-key 维度的 lanes

┌──────────────────────────────────────────────────────────────────────┐ │ 并发模型 · lanes(串行化通道) │ └──────────────────────────────────────────────────────────────────────┘ [核心原则] 按 session-key 串行化 ┌──────────────────────────────────────────────────────────┐ │ 同一 session 的 run 必须串行(一个跑完再跑下一个) │ │ 不同 session 的 run 可并行(互不影响) │ │ → 串行化粒度 = session-key(会话标识) │ └──────────────────────────────────────────────────────────┘ [lane 类型] ┌──────────────────────────────────────────────────────────┐ │ · session lane:按 session-key 串行(默认,防 race) │ │ · global lane:全局串行(必要时,如跨 session 共享资源) │ │ · subagent lane:子 agent 独立 lane(不阻塞父) │ └──────────────────────────────────────────────────────────┘ [跨进程保护] ┌──────────────────────────────────────────────────────────┐ │ session 写锁(文件锁): │ │ · 跨进程互斥(防多进程/多设备同时改同一 session) │ │ · acquire 超时(默认 60s,避免无限等) │ │ · 写 transcript 必须持有锁 │ └──────────────────────────────────────────────────────────┘

三层并发控制

层保护什么机制
session lane(进程内)同 session 的 run 顺序内存队列,按 session-key 串行
session 写锁(跨进程)transcript 文件写入文件锁,acquire 超时
子 agent lane子 agent 不阻塞父独立 lane 隔离

三 · 为何这么设计:三个核心决策

决策 1:为什么按 session-key 而非 agent-id 串行

如果按 agent-id 串行(整个 agent 一次只跑一个 run),那子 agent(第⑩篇)会阻塞父 agent,多 session 用户排队等。粒度太粗。按 session-key 串行是精确的:同一 session 的 run 会改同一 transcript/上下文,必须串行;不同 session 互不影响,可并行。这是最小串行化原则——只在必须串行的地方串行(共享同一 session 状态),其他都并行。

决策 2:为什么需要跨进程写锁

session lane 只保护进程内并发。但生产中,同一 session 可能被不同进程访问:多设备同步、gateway 重启、水平扩展的多实例。内存队列管不到跨进程。所以需要文件级的写锁——任何进程写 transcript 前必须 acquire 锁。这保证了即使两个进程同时想写同一 session,也会排队而非撕裂文件。acquire 超时避免死锁(某进程持锁崩溃,其他进程不会无限等)。

决策 3:为什么子 agent 用独立 lane

父 agent 派出子 agent(第⑩篇)。如果子和父在同一 lane,子 agent 跑的时候父被阻塞——这就失去了委派的并行价值。所以子 agent 用独立 lane,父子并行跑。但注意:父子可能共享工作树(同一项目文件),这时文件写锁(决策 2)兜底——子写文件时如果父也在写,锁让他们排队,不撕裂。lane 隔离的是 session 级顺序,文件锁保护的是共享资源,两者互补。

核心取舍:lanes + 跨进程锁带来队列管理、锁超时、死锁预防的复杂度,换来的是并发下的状态一致性。替代方案(无并发控制)的失败模式是"文件覆盖丢失、transcript 撕裂、上下文不一致"——这些都是静默的数据损坏,比崩溃更可怕(崩溃能发现,损坏藏得深)。接受串行化的延迟代价(同 session 请求排队),因为不一致是不可恢复的,延迟是可接受的。

四 · 完整示例:同会话并发请求的排队

用户在 CLI 连发两条消息(消息2 在消息1 跑到一半时发):

[t0] 用户发消息1 "读 package.json" · 进入 session lane(S1),acquire 成功 · Run A 开始跑 [t3] 用户发消息2 "读 README.md"(Run A 还在跑) · 进入 session lane(S1),发现被 Run A 占用 · 排队等待(不并行跑) [t8] Run A 完成,释放 session lane · Run B(消息2)acquire 成功,开始跑 · 看到的是 Run A 已更新的 transcript(一致状态) [t12] Run B 完成 [对比:不同 session 并行] 用户在另一 session(S2)同时发消息 · S2 的 run 不受 S1 阻塞,并行跑(不同 transcript,互不影响)
关键洞察:消息2 等消息1 跑完才开始(同 session 串行),保证 Run B 看到的是 Run A 完成后的一致状态,而非 Race。同时另一 session 的 run 不等,并行跑(最大化吞吐)。这是"正确性 + 吞吐"的平衡——只在必要时(同 session)串行。

五 · 面试官视角:这题在考察什么

回答层次面试官的判断

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点正确性:"并发不是性能问题是正确性问题——无控制的并发会撕裂 transcript、覆盖文件、上下文不一致。"
  2. 给 lane 模型:"按 session-key 串行化——同 session 的 run 排队(共享 transcript 必须串行),不同 session 并行(互不影响)。最小串行化。"
  3. 主动谈跨进程:"session lane 只管进程内,跨进程(多设备/多实例)靠文件写锁。写 transcript 必须 acquire 锁,有超时避免死锁。"
  4. 主动谈子 agent:"子 agent 用独立 lane,不阻塞父(保并行价值)。父子共享工作树时,文件锁兜底防撕裂。"
  5. 收口在取舍:"代价是同 session 请求排队(延迟),但不一致不可恢复,延迟可接受。这是正确性的硬要求。"
