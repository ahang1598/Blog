一 · 设计问题:token 不够用了怎么办

对话越长,历史消息越多,塞进 Prompt 的 token 越多。迟早撞上模型的上下文窗口上限。这是所有长对话 Agent 的核心生产难题。

最直觉的解法是滑动窗口:只保留最近 N 条消息,丢掉最旧的。听起来简单合理。但在生产中它会引发灾难:

  • 失忆重复:丢掉了"我们已否定了方案 A"的旧消息,模型重新提议方案 A,用户崩溃。
  • 工具配对断裂:丢掉了一个 tool_use 但留下 tool_result(或反过来),provider 报错崩(见第④篇)。
  • 关键决策丢失:重要的"我们为什么选 B 而不是 C"被丢了,后续推理失去依据。
  • 身份漂移:早期建立的工作约定(用某编码规范)被丢,agent 行为逐渐跑偏。

滑动窗口的本质问题是无差别丢弃——它不区分"这条消息重要吗",只看新旧。生产需要的是有信息保真度的丢弃:旧内容可以被压缩,但关键信息要保留。

二 · 分层设计:摘要式压缩的四步管线

┌──────────────────────────────────────────────────────────────────────┐ │ 上下文压缩 · 摘要式管线 │ └──────────────────────────────────────────────────────────────────────┘ [触发] token 用量接近窗口上限? │ 公式:contextTokens > contextWindow - reserveTokens │ (留 reserveTokens 给模型生成本轮回复) ▼ [1] 找切点(cut point) │ 从后往前累计 token,直到累计够 keepRecentTokens(保留原文的尾巴) │ ↓ 关键:切点必须 snap 到 turn 边界(不能切断一个 turn 中间) ▼ [2] 分割 │ messagesToSummarize = 切点之前的所有消息 │ recentTail = 切点之后的消息(保留原文) ▼ [3] 生成摘要(迭代更新) │ 把 messagesToSummarize + 上一次的 previousSummary 喂给模型 │ → 输出更新后的 structured summary(Goal/Progress/Decisions/...) │ ↓ 不是从头重算,是基于上一版增量更新 ▼ [4] 替换 + 修复 │ 新上下文 = [摘要消息] + [recentTail 原文] │ 修复:删 tool_use 时连删 tool_result(配对不变量) │ 保存边界标记(下次压缩从这里续) ▼ 后续 turn 模型看到的是:[结构化摘要] + [最近 N 条原文]

两个核心数字

参数含义典型值
reserveTokens给模型本轮回复预留的空间~16000
keepRecentTokens保留原文的"尾巴"大小~20000

三 · 为何这么设计:四个关键决策

决策 1:为什么摘要式而非滑动窗口

滑动窗口 truncation

• 优点:实现极简

• 失忆重复:丢掉否定结论,模型重新提议

• 配对断裂:无差别删破坏 tool_use/result

• 关键决策丢失

• 适合:无状态问答

摘要式 compaction

• 代价:多一次模型调用(成本)

• 信息保真:关键决策/进展被结构化保留

• 配对安全:摘要消息不含原始 id,不破坏

• 连续性:模型知道"我们到哪了"

• 适合:长任务、协作、生产

决策 2:为什么"迭代更新旧摘要"而非"从头重算"

对话很长时,要总结的旧消息可能本身就有几万 token。两种做法:

  • 从头重算:每次把所有旧消息重新总结。问题:① 越往后旧消息越多,成本爆炸;② 每次重新总结会丢失上一版摘要里已提炼的精华。
  • 迭代更新:只总结"自上次压缩后的新消息",和上一版摘要合并成新摘要。① 成本恒定(只处理增量);② 连续性更好(基于上一版增量更新);③ 可控的误差累积。

接受"误差累积"的代价,因为重算成本不可接受,且结构化模板(见下)的锚点机制能控制累积。

决策 3:为什么切点必须 snap 到 turn 边界

一个 turn = 模型一次推理 + 它的工具调用 + 工具结果。如果切点落在 turn 中间(比如切在一个 tool_use 后但 tool_result 前),会破坏配对不变量。所以切点必须 snap 到 turn 的边界——要么整个 turn 进摘要,要么整个 turn 留原文。这要求找切点时检测"分割的 turn"并整段处理。

决策 4:为什么故障容忍是设计前提

压缩本身要调模型,模型可能失败(超时、畸形返回、摘要质量差)。如果压缩失败就让对话崩,生产不可用。所以压缩必须是渐进降级的:

压缩尝试失败 ↓ 降级 1:丢弃超大消息后再试(可能是某条 tool_result 太大撑爆摘要 prompt) ↓ 还失败 降级 2:只总结能总结的,无法总结的部分用占位符 ↓ 连续 N 次都失败 降级 3:熔断(停止压缩,接受 token 溢出或截断),不让无限重试拖死对话
核心取舍:摘要式压缩带来额外的模型调用成本和实现复杂度(切点、迭代更新、修复、降级链),换来的是信息保真度和连续性。替代方案(滑动窗口)的失败模式是"模型失忆、配对断裂、决策丢失"——这些在生产中直接表现为 bug 和用户投诉。接受成本,因为它把不可恢复的信息丢失变成可控的渐进降级。

四 · 完整示例:一次压缩的结构化摘要产物

假设对话已经讨论了一个 bug 修复任务,跑了 30 turn。压缩触发,摘要消息长这样(结构化模板,不是自由文本):

## Goal 修复 package.json 里 dependencies 版本冲突导致的安装失败 ## Progress - Done:复现了问题(npm install 报 ERESOLVE);定位到是 react@18 和 react-dom@17 冲突 - In Progress:把 react-dom 升级到 18 以匹配 - Blocked:无 ## Key Decisions - 决定升级 react-dom 而非降级 react(用户偏好最新版) - 否决用 overrides 强制版本(会掩盖未来的真实冲突) ## Next Steps - 升级后跑测试确认无回归 - 检查是否还有其他依赖 react-dom 17 的包 ## Critical Context - 项目用 pnpm(不是 npm) - 用户上次说过不喜欢 any 类型,改类型要精确 - 文件 src/App.tsx 已经改过一处,不要重复改
关键洞察:摘要不是"把对话缩写一下",而是用结构化模板锚定关键信息——Goal/Progress/Decisions/Next/Critical Context。这些锚点是防误差累积的机制:即使迭代更新多次,只要每次都填这些槽位,关键信息(决策、否决理由、用户偏好)就不会漂移丢失。模型看到这个摘要 + 最近原文,就能无缝继续,不重复已废方案。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先否定滑动窗口:"token 不够不能简单截旧的——会失忆重复、配对断裂、决策丢失。"
  2. 给摘要式方案:"我用摘要式压缩:把旧消息总结成结构化摘要,保留最近 N 条原文。模型看到 [摘要] + [最近原文]。"
  3. 主动谈迭代更新:"长对话下不从头重算(成本爆炸),而是基于上一版摘要增量更新——只处理自上次压缩后的新消息。代价是误差累积,用结构化模板锚点控制。"
  4. 主动谈 turn 边界:"切点必须 snap 到 turn 边界,不能切断 turn 中间破坏 tool_use/result 配对。"
  5. 主动谈故障容忍:"压缩本身要调模型,会失败。设计成渐进降级:丢超大消息→部分总结→熔断,不让压缩失败拖死对话。"
主动展现的生产洞察:
  • 结构化摘要模板(Goal/Progress/Decisions)是防误差累积的锚点机制
  • reserveTokens + keepRecentTokens 是两个核心数字
  • 压缩改的是 Session,不动 Agent(见第①篇)
