一 · 设计问题:记忆不是压缩,也不是数据库

很多人把"agent 记住东西"理解成三件事之一,但都错了:

  • "记忆 = 压缩":压缩是会话内的(第⑤篇),记忆要跨会话——你关掉对话重开,agent 还该记得你。
  • "记忆 = 数据库":数据库是精确查询(查用户 ID=123),记忆是语义召回("用户上次提过喜欢 TS,这次相关")——不是查,是联想。
  • "记忆 = 把所有对话存起来":存了不等于记得——下次要用时,如果不主动召回,存了等于没存;全量塞 prompt 又会爆。

生产中"记忆"要同时满足这些互相打架的需求:

  • 跨会话存活:这次对话说的,下次(甚至下周)还该影响 agent。
  • 不爆 prompt:不能把所有历史塞进 system prompt。
  • 语义召回:用户没明说时,agent 该联想相关记忆("你之前说过用 pnpm")。
  • 区分重要度:不是所有信息都值得长期记(随口一句 vs 明确偏好)。
  • 不污染:这次讨论的临时 bug,不该让 agent 永久记住这个 bug。

二 · 分层设计:四层栈 + 离线巩固

┌──────────────────────────────────────────────────────────────────────┐ │ 多层记忆架构 · 四层栈 │ └──────────────────────────────────────────────────────────────────────┘ [L1] 文件记忆(种子层 · 最稳定) ┌──────────────────────────────────────────────────────────┐ │ MEMORY.md:用户/项目级显式记忆文件 │ │ · 人写的或 agent 显式写的长期偏好 │ │ · 每次启动注入 system prompt 稳定前缀 │ │ · 优先级最高,但容量小 │ └──────────────────────────────────────────────────────────┘ │ [L2] 检索记忆(语料层 · 跨会话) ┌──────────────────────────────────────────────────────────┐ │ 混合检索 store(vector + FTS): │ │ · 索引"memory 文件" + "历史会话 transcript" │ │ · chunked + embedded │ │ · 运行时按当前 query 检索 top-k 相关片段注入 prompt │ │ · 不是全量塞,是按需召回 │ └──────────────────────────────────────────────────────────┘ │ [L3] 插件记忆(扩展层) ┌──────────────────────────────────────────────────────────┐ │ 第三方记忆插件(如 wiki、知识库、CRM) │ │ · 通过统一契约接入 │ │ · 各自 own 存储/检索逻辑 │ └──────────────────────────────────────────────────────────┘ │ [L4] Active Memory(工作集 · 短期) ┌──────────────────────────────────────────────────────────┐ │ 当前任务相关的活跃记忆条目 │ │ · 高优先级,显式注入 prompt │ │ · 任务结束可清理或晋升到长期 │ └──────────────────────────────────────────────────────────┘ ════════════ 离线巩固管道 ════════════ Dreaming(定时后台批处理) 把短期/低置信的 L4/L2 条目,按召回频率和置信度, 晋升(promote)到长期稳定记忆 三阶段:light(去重) → deep(高置信晋升) → rem(模式提炼)

记忆 vs 压缩(关键对比)

维度压缩(第⑤篇)记忆(本篇)
作用域会话内(单 Session)跨会话(整个 Agent)
触发token 接近上限显式写 / 召回 / 后台巩固
存活Session 结束就丢Agent 存在就活
形态结构化摘要(替换历史)独立语料(不替换历史)
注入成为对话历史一部分按需检索注入或种子注入

三 · 为何这么设计:三个核心决策

决策 1:为什么不抄经典 episodic/semantic 记忆图

学术上的记忆架构是 episodic(事件记忆)+ semantic(语义知识)的图结构。看起来优雅,但生产中:

  • 图结构维护成本高:节点/边/类型要人工或复杂逻辑维护。
  • 召回不可靠:图遍历召回容易漏(查不全)或泛(查太多)。
  • 与 LLM 不匹配:LLM 擅长处理自然语言片段,不擅长图查询。

生产选择混合检索 store(vector + 全文检索)——把记忆当成"可检索的文本片段语料",而非图。这和 RAG 思路一致:简单、召回可靠、和 LLM 天然契合。接受放弃了图的表达力,换取工程可靠性和与 LLM 的兼容。

决策 2:为什么是检索召回而非全量注入

记忆越多,全量塞 prompt 越不现实。生产选择按需召回:运行时用当前 query(用户消息+上下文)去检索 top-k 最相关的记忆片段,只注入这几条。这要求:1)embedding 索引(语义相似);2)混合排序(vector 相似度 + 全文匹配 + 时间衰减);3)MMR 去冗余(避免召回 k 条说同一件事的)。代价是可能漏召回(相关记忆没被检索到),用 L1 种子记忆(关键偏好强制注入)兜底。

决策 3:为什么 dreaming 是离线批处理

短期记忆→长期记忆的"晋升"判断(这条值不值得长期记)是计算密集且不急的:要算置信度、召回频率、去重。如果实时做,拖慢对话;不做,短期记忆堆积无序。生产借鉴睡眠/梦的机制——定时后台批处理:

light dreaming(频繁,如每天):去重(相似度 > 0.9 的合并) ↓ deep dreaming(定期):高置信条目(召回 ≥3 次、跨多查询)晋升长期 · 带 recency decay(14 天半衰期,旧记忆降权) · 有恢复模式(低于健康阈值时重新晋升) ↓ rem dreaming(深度):模式提炼(高频模式提升为强记忆)
核心取舍:四层栈 + 检索召回 + 离线巩固带来显著的工程复杂度(embedding 索引、混合排序、定时任务、晋升逻辑),换来的是跨会话、不爆 prompt、语义召回、区分重要度全部满足。替代方案(全量塞 / 简单数据库 / 图结构)都在某个维度崩:全量爆 prompt,数据库无语义召回,图不可靠。接受复杂度,因为没有更简单的方案能同时满足这五个需求。

四 · 完整示例:"记住我喜欢 TypeScript"的全生命周期

用户在某个对话里说了句"我喜欢 TypeScript,别用 JavaScript"。我们追踪这条信息如何流过记忆系统:

[T0 · 对话中] 用户说"我喜欢 TypeScript" ↓ [短期落地] 进入当前 Session 的 transcript(L2 语料被增量索引) · 同时可能进 L4 Active Memory(当前任务相关) ↓ [T1 · 同会话后续 turn] 用户问"帮我写个脚本" · 检索召回:query="写脚本" → 召回"用户喜欢 TS" → 注入 prompt · agent 用 TS 写(无需用户再说) ↓ [T2 · 跨会话(次日新对话)] · 新 Session 启动,L1 MEMORY.md 若已记录则种子注入 · 若未显式记录,下次相关 query 时 L2 检索召回 · 但若召回频率低,可能"忘"(未召回) ↓ [T3 · 后台 dreaming(夜间)] · light:去重(用户多次说类似话,合并) · deep:这条被召回 ≥3 次、跨多查询 → 高置信 → 晋升长期记忆 · 写入 L1 MEMORY.md 或标记为长期条目 ↓ [T4 · 之后所有会话] · 这条已是长期记忆,稳定注入或高频召回 · agent 永久"记住"用户喜欢 TS(除非用户明确说改)
关键洞察:一条信息从"随口一提"到"agent 永久记住"经过了置信度筛选——不是说了就记,而是被反复召回使用(说明真有用)才晋升长期。这模拟了人类记忆:听过的很多,记住的是反复用到的。这避免了"随口一句临时 bug 被永久记住"的污染问题。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先划清边界:"记忆和压缩完全不同——压缩是会话内的(替换历史),记忆是跨会话的(独立语料,按需召回)。"
  2. 给四层栈:"我用四层:L1 文件种子(强制注入关键偏好)、L2 检索语料(vector+FTS)、L3 插件扩展、L4 Active 工作集。"
  3. 主动谈为什么不抄图:"不抄经典 episodic/semantic 图,因为图维护成本高、召回不可靠、和 LLM 不匹配。用混合检索 store 更可靠。"
  4. 主动谈检索而非全量:"不全量塞 prompt,按当前 query 检索 top-k 注入。混合排序:vector 相似 + 全文 + 时间衰减 + MMR 去冗余。"
  5. 主动谈 dreaming:"短期→长期晋升靠离线批处理 dreaming,模拟睡眠。light 去重→deep 高置信晋升→rem 模式提炼。带 recency decay。"
  6. 收口在置信度:"不是说了就记,是被反复召回使用才晋升长期——这避免了临时信息污染长期记忆。"
主动展现的生产洞察:
  • 记忆注入要防跨 run 泄漏(用 AsyncLocalStorage 隔离 run-scoped 快照)
  • embedding 索引要增量更新(压缩后强制重索引)
  • 召回漏了用 L1 种子兜底;召回了错的用置信度过滤
