一 · 设计问题:"这次 run 到底怎么结束的"

一个 run(第①篇)可能因为多种原因结束:

  • 正常完成:模型说任务做完了。
  • 用户取消:用户点了停止。
  • 超时:硬超时(run 级)或空闲超时。
  • 失败:模型连续失败、凭据耗尽。
  • 预算耗尽:token/费用预算用完。
  • 外部中止:系统关机、父 agent 取消子。

demo 级做法:用几个布尔字段记录——aborted、timedOut、failed、completed。听起来够用,但生产中这些会同时为真:

用户在 run 快完成时点了取消,但取消信号还没传到,run 已经完成了——completed 和 aborted 都可能为真。到底算完成还是取消?

硬超时触发的同时,attempt 因为网络失败——timedOut 和 failed 都为真。算超时还是失败?

更糟的是,这些字段会被不同代码路径并发设置:取消信号处理设置 aborted,超时定时器设置 timedOut,attempt 循环设置 failed。每个调用点各自判断"该设哪个",必然不一致。"这次 run 怎么结束的"这个本该确定的问题,变成了一团乱麻。

二 · 分层设计:终端状态优先级格

核心设计:把终端状态建模成闭式优先级格(lattice),而非一组布尔字段。

高优先级(主导,sticky) ╔══════════════════════════════════════╗ ║ hard_timeout(硬超时) ║ ← run 级硬约束,不可恢复 ║ cancelled(用户/外部取消) ║ ← sticky,后续不能降级 ╚══════════════════════════════════════╝ ▲ 合并时高的覆盖低的 ╔══════════════════════════════════════╗ ║ aborted(中止,如清理 yield) ║ 中优先级 ╚══════════════════════════════════════╝ ▲ ╔══════════════════════════════════════╗ ║ failed(失败) ║ ║ blocked(阻塞,如缺凭据) ║ 中低 ║ abandoned(放弃) ║ ╚══════════════════════════════════════╝ ▲ ╔══════════════════════════════════════╗ ║ completed(正常完成) ║ 低优先级(默认) ╚══════════════════════════════════════╝ 合并规则:多个状态并存时,取优先级最高的。 sticky:cancelled / hard_timeout 一旦设定,后续事件不能降级它们。 例外:completedBeforeOrAtTimeout(完成证据早于超时时间戳 → 完成优先)

三个关键性质

性质含义为什么
闭式状态是有限集合(联合类型),非任意布尔组合让"可能的终端状态"可枚举、可推理
优先级状态有全序,合并取最高并发多源设置时结果确定
sticky高优先级状态不被后续降级取消/硬超时是"终局决定",不被清理事件覆盖

三 · 为何这么设计:三个核心决策

决策 1:为什么用优先级格而非 if/else 链

如果每个调用点自己判断"现在是 completed 还是 cancelled",会出现判断不一致——取消处理代码觉得是 cancelled,完成处理代码觉得是 completed,同一个 run 在不同地方状态不同。优先级格把这些判断集中成一个合并函数:所有状态变更都经过它,按格的规则合并,结果全局唯一确定。这是单一真相源——"run 怎么结束的"只有一个权威答案,各处引用它而非自己推。

决策 2:为什么 cancelled / hard_timeout 要 sticky

用户取消是一个终局决定——"我不想再等了"。即使取消信号到达前 run 碰巧完成了,从用户语义看,这个结果也是不可信的(用户已经放弃,不该被当作成功交付)。如果允许"完成事件覆盖取消",会出现:用户取消后还收到完成通知,困惑。sticky 保证:一旦 cancelled,后续任何事件(完成、失败、清理 abort)都不能把它降级成 completed/failed。取消是用户意图,凌驾于系统状态之上。

同理 hard_timeout:硬超时意味着"这个 run 超出可接受时间,必须终止",这是运维约束,不该被"刚好在超时后完成了"覆盖——否则硬超时形同虚设。

决策 3:为什么有 completedBeforeOrAtTimeout 例外

这是 sticky 规则的精确例外:如果有证据证明 run 在超时时间戳之前就完成了(完成事件的时间戳 ≤ 超时触发时间戳),那么完成优先。为什么:这种情况下"完成"是真实发生的(在超时前就成功了),只是完成通知和超时通知因为并发而同时到达。忽略完成会让用户看到一个"明明成功却被判超时"的 run,体验灾难且可能重试造成副作用。证据优先于时间戳——这是为了避免假阴性(把成功的当失败的)。

核心取舍:优先级格带来状态建模的抽象成本(要定义状态集、优先级、合并规则、sticky、例外),换来的是并发多源终止的一致性和可推理性。替代方案(布尔字段)的失败模式是"状态不一致、各处判断不同、取消/超时被误覆盖"。接受抽象成本,因为在并发+重试+多取消源的系统里,'run 怎么结束的'必须有唯一确定的答案——这不是优化,是正确性的硬要求。

四 · 完整示例:并发多取消源的合并

一个 run 经历了这些事件(时间顺序):

[t0] run 启动,状态 = running [t5] 模型连续失败 3 次,attempt 设置 failed · 合并:running + failed → failed [t8] 用户点取消,取消处理设置 cancelled · 合并:failed + cancelled → cancelled(优先级高,覆盖 failed) · sticky:cancelled 锁定,后续不能降级 [t9] 超时定时器触发,设置 hard_timeout · 合并:cancelled + hard_timeout → hard_timeout(更高优先级) · 注意:此时 hard_timeout 主导 [t10] 清理代码尝试设置 aborted(yield cleanup) · 合并:hard_timeout + aborted → hard_timeout(sticky,不被降级) · aborted 被忽略 [最终] 终端状态 = hard_timeout · 单一真相源:所有引用处看到同一个答案 · 用户看到"超时",运维看到"超时",日志记录"超时"
关键洞察:尽管 failed/cancelled/hard_timeout/aborted 四个事件都发生了,最终状态唯一确定 = hard_timeout。没有任何调用点需要自己判断"这么多状态哪个算数"——合并函数按格规则统一决定。这就是单一真相源的价值。如果用布尔字段,这四个字段会都为 true,每个消费者自己解释,必然不一致。

五 · 面试官视角:这题在考察什么

回答层次面试官的判断
"用 aborted/timedOut 布尔字段""没考虑并发一致性"
知道要排序,if/else 判断优先级"有意识但分散,易错"
能说集中合并 + 优先级"及格"
能谈闭式联合、sticky、单一真相源、证据例外"生产经验扎实,有状态机设计深度"

这题是区分"写过并发代码"和"设计过并发状态机"的分水岭。前者会用布尔字段加锁,后者知道布尔字段在多源并发下根本不对。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点问题:"run 可能因完成/取消/超时/失败多种原因结束,且这些会并发同时发生。布尔字段会让多个为真,各处判断不一致。"
  2. 给优先级格:"把终端状态建模成闭式优先级格——有限状态集(completed/failed/aborted/cancelled/hard_timeout)+ 全序优先级 + 合并函数。多状态并存取最高。"
  3. 主动谈 sticky:"cancelled 和 hard_timeout 是 sticky——一旦设定不被后续降级。因为取消是用户终局意图,硬超时是运维硬约束,都不该被'刚好完成了'覆盖。"
  4. 主动谈单一真相源:"所有状态变更经过合并函数,结果全局唯一。各消费者引用它而非自己推,避免不一致。"
  5. 主动谈证据例外:"completedBeforeOrAtTimeout:有证据证明完成早于超时,完成优先。避免把成功的当失败的(假阴性)。"
