一 · 设计问题:大框架怎么切分才不烂

一个生产级 Agent 平台要同时管:推理循环、工具、上下文、记忆、channels(Telegram/Discord/...)、多个 provider、插件、持久化、并发、用户身份... 如果全堆在一起,会变成无法维护的怪兽——改一处影响处处,测试不可能,扩展靠改核心。

demo 级做法:一个 monolith,所有功能写一起。能跑,但:

  • 核心被污染:接 Telegram 要改核心,接 Discord 还要改核心,核心越来越臃肿。
  • 无法复用:推理循环和 OpenClaw 业务绑死,换个场景要重写。
  • 测试地狱:测推理要起 Telegram,测 Telegram 要真模型,耦合死。
  • 扩展靠改核心:加个新功能(provider/channel/tool)必须改核心代码。

生产需要清晰的分层:每层职责单一,通过明确接口交互,核心稳定,扩展在外。

二 · 分层设计:三层 + Gateway 中枢

[层 3] 插件层(extensions/ · 可替换)

· provider 插件:OpenAI/Anthropic/Google... 各自管认证、模型目录、API 适配

· channel 插件:Telegram/Discord/Slack... 各自管传输、消息格式、回调

· 能力插件:memory/browser/canvas... 各自管特定能力

· 特点:独立、可增删、不互相依赖;通过 SDK seam 接入核心

[层 2] 编排层(core src/ · OpenClaw 自有)

· agent 编排(embedded runner、harness、lanes、hooks)

· gateway(WebSocket 服务、协议、路由)

· 状态管理、持久化、并发控制

· 插件加载/注册/隔离机制

· 特点:plugin-agnostic(不知道具体插件,只知通用契约)

[层 1] 可复用库(packages/ · 框架无关)

· agent-core:纯推理循环(turn/attempt/run、工具派发、消息折叠)

· ai / llm-core:provider API 归一化、流式、校验

· gateway-protocol:协议 schema/校验

· 特点:不知道 OpenClaw 存在,可被任何框架复用

Gateway:编排层里的单中枢

┌──────────────────────────────────────────────────────────────────────┐ │ Gateway · 单守护进程中枢 │ └──────────────────────────────────────────────────────────────────────┘ 控制面客户端 Node 设备 (macOS app / CLI / Web) (暴露 caps/commands) │ │ └──────────┬─────────────────┘ ▼ WebSocket ┌─────────────────┐ │ GATEWAY │ ← 单守护进程,owns: │ (编排层核心) │ · 所有 channels(TG/Discord/...) │ │ · 所有 agent 实例 │ │ · 状态/持久化 │ │ · 插件加载 └─────────────────┘ │ ┌──────────┴──────────┐ ▼ ▼ Provider API 工具执行(本地/远程)

三 · 为何这么设计:三个核心决策

决策 1:为什么分三层(库/编排/插件)

层 1(可复用库)剥离出来,是为了复用和测试:纯推理循环不依赖 OpenClaw 业务,任何框架能用,且能独立测试(不启 gateway/channel)。层 2(编排)是 OpenClaw 自有逻辑,负责把库、插件、状态、并发粘合起来。层 3(插件)是可替换的扩展点。分层让每层可独立演进:库升级不破坏编排,编排重构不动插件,插件增删不改核心。关键边界:层 1 不知道 OpenClaw,层 2 不知道具体插件,层 3 通过 seam 接入。

决策 2:为什么核心必须 plugin-agnostic

核心(src/)如果"知道"某个具体 provider/channel(如硬编码 OpenAI 逻辑),会引发:① 核心膨胀——接 N 个 provider 就在核心塞 N 套逻辑;② 无法替换——想换掉 OpenAI 要改核心;③ 测试耦合——测核心要 mock 具体 provider。plugin-agnostic 设计:核心只定义通用契约(provider 是什么形态、channel 是什么接口),具体实现由插件提供,核心通过注册表发现。这让核心稳定、可测试、可扩展——加新 provider 不动核心,只写插件。这是大型框架可维护的基石。

决策 3:为什么 Gateway 是单守护进程中枢

生产中,channels(Telegram 长连接)、agent 实例、状态、插件都要长期存活。如果分散成多个进程,协调成本高(状态同步、进程通信、崩溃恢复)。单 Gateway 守护进程 owns 所有:一个进程管所有 channels、所有 agent、所有状态。好处:① 状态一致——所有 agent 状态在同一进程,内存共享无需分布式同步;② 插件加载一次——启动扫描插件,所有 agent 复用;③ 协调简单——lanes/hooks/并发都在进程内。代价:单点是可用性风险(进程挂全挂),用持久化(状态存 SQLite,重启恢复)+ 多实例(水平扩展,每实例独立 agent 集)缓解。

核心取舍:三层 + 单中枢带来接口设计、插件注册、单点风险缓解的复杂度,换来的是可复用、可测试、可扩展、状态一致。替代方案(monolith)的失败模式是"核心被污染、无法复用、测试地狱、扩展靠改核心"。接受分层复杂度,因为大型框架的生命线是'核心稳定 + 扩展在外'——没有这个,框架活不过几次大改。

四 · 完整示例:一次请求穿越三层

[用户在 Telegram 发消息] ↓ [层 3 · channel 插件] Telegram 插件接收 · 长连接收到消息 → 归一化成内部 envelope · 通过 SDK seam 传给编排层 ↓ [层 2 · 编排层 Gateway] · Gateway 路由:这个消息属于哪个 agent/session? · 触发 agent run(lanes 排队、hook 链) · 加载身份(第⑮篇)、拼 prompt(第③篇) ↓ [层 1 · 可复用库 agent-core] · runLoop:调模型 → 工具循环 → 折叠消息 · 调用层 3 的 provider 插件(OpenAI)发请求 ↓ [层 3 · provider 插件] OpenAI 插件 · 认证、构造请求、发 HTTP、解析 SSE 流 · 归一化事件返回给 agent-core ↓ [层 1 · agent-core] 继续循环直到完成 ↓ [层 2 · 编排层] 流式回复 · 通过 block chunker(第⑨篇)转 channel 流 ↓ [层 3 · channel 插件] Telegram 插件发送 · 适配 Telegram 消息格式 → 发送
关键洞察:一次请求穿越三层多次——channel 进、provider 调用、channel 出。每层只做自己擅长的(库做推理、编排做协调、插件做对接),通过明确 seam 交互。换 channel(改用 Discord)只换层 3 的 Telegram→Discord,层 1/2 不动。换 provider 同理。这就是分层的价值——变更局部化。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点三层:"分可复用库(纯推理)、编排层(OpenClaw 自有)、插件层(provider/channel/能力)。"
  2. 给核心边界:"层 1 不知道 OpenClaw(可复用),层 2 不知道具体插件(plugin-agnostic),层 3 通过 seam 接入。"
  3. 主动谈 plugin-agnostic:"核心只定义通用契约,具体 provider/channel 由插件实现。加新 provider 不动核心。这是可维护基石。"
  4. 主动谈单中枢:"Gateway 单守护进程 owns 所有,状态一致、插件加载一次、协调简单。单点风险用持久化+多实例缓解。"
  5. 收口在变更局部化:"分层让变更局部——换 channel/provider 只换插件,核心不动。"
