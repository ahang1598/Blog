一 · 设计问题:思维链不是普通文本

新一代推理模型(o1/Claude thinking/GPT-5 reasoning)会输出思维链:在给最终答案前,先输出一段"思考过程"(分析问题、考虑方案、自我纠错)。这段思考是模型推理质量的关键。

demo 级做法:把 thinking 当普通文本处理——和最终答案一起塞进消息,存历史,下次请求带回去。听起来自然,但生产中引发一堆问题:

  • 预算爆炸:thinking 可能比最终答案长 10 倍(模型要想很久)。全保留 = 上下文瞬间被 thinking 吃光。
  • 缓存命中差:thinking 是模型每次重新生成的,内容不稳定,塞进历史会让 prompt 缓存难以命中。
  • 不该回传给模型:上一轮的 thinking 通常是"中间过程",回传给下一轮的模型可能干扰它(让它沿旧思路走而非重新想)。
  • 跨 provider 不一致:不同 provider 的 thinking 格式/语义不同(有的有独立字段,有的混在文本里),不归一化没法通用。
  • 用户可见性:thinking 有时要给用户看(显示推理过程增加信任),有时要隐藏(内部推理不该暴露),需要可控。

三 · 为何这么设计:四个核心决策

决策 1:为什么 thinking 要独立字段而非混在文本

如果 thinking 混在最终文本里:① 无法分别处理(不能"只丢 thinking 保答案");② 用户可见性不可控(无法选择性显示);③ 跨 provider 无法归一(格式各异)。独立字段让 thinking 成为有独立生命周期的对象——可以单独预算、单独压缩、单独控制可见性、单独归一化。这是后续所有策略的前提。

决策 2:为什么默认不透传上轮 thinking

thinking 是"得到答案的中间过程"。如果回传给下一轮模型,模型可能沿旧思路走而非重新评估——比如上轮 thinking 排除了方案 X,下轮遇到新信息本该重新考虑 X,但因为旧 thinking 还在,它继续排除 X。默认不透传让模型每轮基于当前完整上下文重新思考,避免被历史推理锁死。例外:某些多步推理任务确实需要连贯性,这时按 provider 契约选择性透传。这个"默认不传"是反直觉但正确的——直觉是"多给模型信息更好",但对 thinking 而言,多给反而可能误导。

决策 3:为什么压缩时优先丢 thinking

thinking 是过程,最终 text 和 toolCalls 是结论。压缩的目标是保留任务进展,而进展在结论里。thinking 的价值在它被生成的那一轮(帮模型得出好答案),一旦答案得出,thinking 的使命就完成了。所以压缩时优先丢 thinking 保 text/toolCalls,能在不损失任务信息的前提下大幅省 token。但要尊重 provider 契约——个别 provider 要求同一消息的 thinking 和 text 必须成对存在,丢 thinking 就要连 text 一起处理,不能只丢一半。这要求压缩逻辑理解 provider 的配对契约(类似第④篇的 tool_use/result 配对)。

决策 4:为什么不能为省 token 直接全剥离

thinking 虽然可以丢,但不能在生产管道的早期就全剥离。原因:① 用户可能要看——显示推理过程增加信任(尤其重要决策如医疗/法律);② 调试需要——出问题时,thinking 是理解模型为何这么答的关键;③ 某些下游消费——比如提取 thinking 做质量评估或训练数据。所以 thinking 要保留到足够晚的阶段(至少存进 transcript),只在确实不需要时(如压缩、回传 prompt)才丢。"可丢"不等于"尽早丢"——保留它的可观测价值。

核心取舍:thinking 作为一等公民带来消息结构的复杂度(独立字段、独立预算、独立压缩策略、provider 契约对齐),换来的是预算可控、缓存友好、推理质量不被旧思路锁死、可观测可调试。替代方案(当普通文本)的失败模式是"预算爆炸 + 缓存失效 + 模型沿旧思路走 + 跨 provider 不通用"。接受复杂度,因为推理模型是当前主流,thinking 处理不当直接决定产品能用与否。

四 · 完整示例:一次推理的消息结构

用户问"这个函数有 bug 吗"。推理模型(high reasoning)的一轮输出,归一化后的结构:

[AssistantMessage · turn 1] [ThinkingBlock] "用户给了个函数让我找 bug。先看签名:接受 array 返回 number。 看逻辑:遍历 array 累加。但没检查 array 是否为 null... 等等,如果 array 是 undefined 会抛 TypeError。这是 bug。 还有什么?返回值如果 array 为空返回 0,合理。 结论:主要 bug 是没做空值检查。" [TextBlock] "这个函数有一个潜在 bug:没有对入参做空值检查。 如果传入 null 或 undefined,for 循环会抛 TypeError。 建议在函数开头加:if (!array) return 0;" (无 ToolCallBlock,纯文本回答)
关键洞察:thinking(紫色斜体)和最终 text 是独立字段。下次请求时,默认只回传 text 不回传 thinking(让模型基于答案重新思考,而非被上轮思考锁死)。压缩时优先丢 thinking 保 text。但 thinking 存进了 transcript——用户要"看模型怎么想的"或开发者调试时,可以回放。这就是"一等公民":有独立结构、独立策略、独立保留价值,而非混在文本里随波逐流。

五 · 面试官视角:这题在考察什么

回答层次面试官的判断
"thinking 就是模型多输出的文字""没理解推理模型的特殊性"
知道 thinking 占 token 要省"有意识但没系统设计"
能说独立字段 + 透传策略"及格"
能谈预算分级、默认不透传、压缩优先丢、provider 契约对齐"生产经验扎实"

这题是考察你是否跟上了推理模型时代。还在用"文本统一处理"思路答的,说明对当前主流模型的生产特性没经验。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点特殊性:"推理模型的 thinking 不是普通文本——它可能比答案长 10 倍、不稳定、不该简单回传。要当一等公民处理。"
  2. 给独立字段:"thinking 归一成独立的 ThinkingBlock 字段,有独立生命周期。这样能分别预算、分别压缩、分别控制可见性、跨 provider 归一。"
  3. 主动谈透传:"默认不透传上轮 thinking——避免模型沿旧思路走。让它每轮基于完整上下文重新想。这是反直觉但正确的。"
  4. 主动谈压缩:"压缩时优先丢 thinking 保 text/toolCalls——过程已凝结成结论,过程可丢。但要尊重 provider 契约(有些要求 thinking 和 text 成对)。"
  5. 主动谈预算:"给 thinking 独立预算和 reasoning_effort 分级——不能让它无限想吃光上下文。"
  6. 收口在'可丢不等于尽早丢':"thinking 要保留到足够晚(至少进 transcript),因为用户要看、调试要查、下游要消费。只在确实不需要时才丢。"
