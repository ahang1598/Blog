一 · 设计问题:单层循环为何在生产中崩

demo 级 Agent 的循环很简单:while 没完成: 调模型 → 模型要工具? → 调工具 → 把结果塞回去。一个 while 搞定一切。跑起来没问题。

但生产中,这一个循环要同时处理三类完全不同的"再来一次":

  • turn 级别再来:模型这一轮用了工具,要把工具结果喂回去让它继续——这是正常循环,不是错误。
  • attempt 级别再来:模型这次调用整体失败了(认证过期、网络抖动、返回了无法解析的格式)——这是同一次尝试内部的重试。
  • run 级别再来:连重试都救不回来,要换模型/换凭据重新跑整个任务——这是执行实例级的兜底。

如果用单层循环处理这三类:

  • "模型要工具"和"模型认证失败"会被混进同一个 retry 计数器——工具调用次数限制了你的故障重试次数。
  • "换模型重试"必须清空整个对话状态,但单层循环没有"执行实例"概念,无处重置。
  • 超时、取消、空闲等不同来源的"该停了"无法分层判定,互相覆盖。
  • 每个故障都得加 if 特判,循环体迅速变成不可维护的状态怪兽。

二 · 分层设计:三层循环的职责切分

┌──────────────────────────────────────────────────────────────────────┐ │ 推理循环 · 三层嵌套 │ └──────────────────────────────────────────────────────────────────────┘ 外层 · RUN 循环(执行实例级) ┌──────────────────────────────────────────────────────────┐ │ while 还有可用的模型/凭据候选: │ ← owns:模型回退、凭据轮转、 │ ├─ 选一个 (model, authProfile) 候选 │ run 级超时、最终终端状态 │ ├─ 中层 · ATTEMPT 循环(可重试尝试级) │ │ │ while 重试次数未耗尽 且 未达硬约束: │ ← owns:网络重试、认证刷新、 │ │ ├─ 准备这一轮 prompt + 工具 + 上下文 │ 格式错误重试、空回复重试、 │ │ ├─ 内层 · TURN 循环(单步推理级) │ attempt 级空闲超时 │ │ │ while 模型还在用工具(未到终点): │ │ │ │ ├─ 调模型(stream token) │ ← owns:工具调用循环、 │ │ │ ├─ 模型要工具? → 执行工具 → 喂结果回去 │ turn 级中断、工具失败、 │ │ │ └─ 模型说"完成"或"继续用工具" │ 软性停止决策 │ │ ├─ 这一次 attempt 跑完了 → 看结果 │ │ │ └─ 失败? → 判断该重试(attempt)还是上抛(run) │ │ ├─ attempt 全失败 → 看能否换候选(run) │ │ └─ 候选耗尽 → 终端状态(completed/failed/timeout/cancelled)│ └──────────────────────────────────────────────────────────┘

三层各自 owns 什么

层owns 的"再来一次"owns 的故障类型owns 的停止决策
Turn(内层)模型用工具后继续(正常推进)单个工具执行失败、模型空回复软性:模型说完成/不再用工具
Attempt(中层)同一次尝试的重试网络抖动、认证过期、格式错误、空闲中等:attempt 重试上限、attempt 超时
Run(外层)换模型/凭据的兜底所有 attempt 耗尽、模型不兼容硬性:run 级硬超时、用户取消、预算耗尽

三 · 为何这么设计:每层 owns 什么故障

Turn 层 · 为什么单独拎出来

"模型决定用工具,把工具结果喂回去继续"是正常工作流,不是错误。如果把它和"模型失败了要重试"混在同一个 while,你会用工具调用次数耗尽来误判任务失败。Turn 层独立后,工具循环是纯粹的"模型-工具乒乓",工具失败只是这一步的事,模型可以自行决定重试还是换方案。

Attempt 层 · 为什么需要"可重试的尝试"这个粒度

一次模型调用可能因为瞬态故障(网络抖、限流、认证 token 过期)失败,这些值得重试但不该影响整个任务。Attempt 层封装"一次完整的推理尝试 + 它的本地重试"。重试上限耗尽才上抛到 Run 层。这样,大多数瞬态故障被吞在 attempt 层,Run 层只看到"这次尝试彻底没救了"。

Run 层 · 为什么需要执行实例级兜底

当所有 attempt 都失败,可能不是运气差,而是模型本身不兼容(这个 provider 不支持某工具格式)或凭据整体失效。Run 层拥有"候选列表"(备选模型、轮转凭据),可以换一个候选重新跑。Run 层还 owns 硬约束:用户取消、总预算耗尽、硬超时——这些是不可重试的停止信号,必须高于重试逻辑。

核心取舍:三层带来调试和心智复杂度(出问题时要先定位是哪层),换来的是每类故障有清晰归属和上限。替代方案(单层)的失败模式是"重试逻辑和正常循环纠缠,某个 if 漏判就死循环或误终止"。生产中前者可维护,后者不可维护。接受这个嵌套,因为它让故障处理从"到处特判"变成"分层归责"。

备选方案对比

方案demo 能跑生产崩点
单层 while(所有重试混一起)能工具调用计数 = 故障重试计数;无法换模型重置;特判爆炸
两层(turn + retry)能换模型无处重置;硬超时/取消无处归属;终端状态撕裂
三层(turn/attempt/run)能边界清晰,每类故障有上限和归属

四 · 完整示例:一次"工具失败 → 重试 → 成功"穿越三层

用户让 agent "读取远程 API 并总结"。我们追踪这个请求如何穿越三层循环:

[RUN 层启动] 选定候选:模型=gpt-5,凭据=profile-A │ ▼ [ATTEMPT 1 启动] │ ├─ [Turn 1] 模型:"我要调 fetch_api 工具" │ ├─ 执行 fetch_api → 网络超时 ❌ │ ├─ 工具失败,结果喂回模型:"fetch 超时了" │ └─ 模型:继续(决定重试 fetch) │ ├─ [Turn 2] 模型:"再试一次 fetch_api" │ ├─ 执行 fetch_api → 认证 401 ❌(token 过期) │ ├─ 工具失败喂回 │ └─ 模型:放弃这个 API,换思路总结 │ ├─ [Turn 3] 模型调用 stream → 返回了畸形 JSON ❌❌ │ └─ attempt 级故障:模型返回无法解析 │ ▼ [ATTEMPT 1 判定] 畸形返回 = 可重试的瞬态? │ 是 → 重试(同 attempt 内) │ [ATTEMPT 2 启动](仍在 RUN 内,同候选) │ ├─ [Turn 1] 重新组装 prompt → 调模型 │ ├─ 模型:"调 fetch_api"(这次带刷新后的 token) │ ├─ 执行 → 成功 ✅ 数据返回 │ └─ 模型:基于数据继续 │ ├─ [Turn 2] 模型输出总结文本,不再要工具 │ └─ 软性停止:模型说完成 │ ▼ [ATTEMPT 2 完成] → 上抛给 RUN │ [RUN 判定] attempt 成功 → 终端状态 = completed ✅
关键观察:工具超时和 401 是 Turn 层吞掉的(模型自己决定换思路);畸形 JSON 是 Attempt 层重试的(同候选内);整个任务从头到尾没动 Run 层(没换模型)。如果畸形 JSON 重试两次还不行,才会上抛到 Run 层考虑换候选。三层各司其职,故障被就近吞掉,不会一个网络抖动就毁掉整个任务。

五 · 面试官视角:这题在考察什么

回答层次面试官的判断
"就是一个 while 循环,调模型调工具""只做过 demo"
"有重试,失败就重试""没区分重试的种类,生产会出乱子"
能说出 turn/attempt/run 三层及各自 owns 什么"有架构意识,及格"
能说清"工具循环不是错误""瞬态故障 attempt 吞""模型不兼容 run 换"的归责逻辑"生产经验扎实"

这题是核心架构题。答得浅,面试官会判断你对后续的压缩、并发、终端状态都答不深;答得深,面试官知道可以放心往这些深水区问。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点明三层:"我会把推理循环拆成 turn(单步)、attempt(可重试尝试)、run(执行实例)三层嵌套。"
  2. 立刻给归责逻辑:"这样拆的核心是让不同性质的'再来一次'有清晰归属——工具循环是正常推进(turn),瞬态故障是同次重试(attempt),模型不兼容是兜底(run)。"
  3. 主动举故障场景:"比如网络抖动,我希望它在 attempt 层被吞掉重试,不要因为一次 502 就放弃整个任务;但如果是模型根本不支持某个工具格式,attempt 重试多少次都没用,要上抛到 run 层换模型。"
  4. 主动谈停止决策:"停止信号也要分层——软性停止(模型说完成)在 turn 层;attempt 重试上限和 attempt 超时在中层;用户取消、硬超时、预算耗尽这些不可重试的硬信号在 run 层最高优先级。"
  5. 收口在取舍:"代价是调试时要先定位是哪层出问题,但换来的是故障处理可维护、有上限、不互相覆盖。"
主动展现的生产洞察:
  • 工具调用循环(turn)是正常工作流,不要和错误重试混计数
  • attempt 重试有上限,不能无限重试瞬态故障(否则用户等到天荒地老)
  • run 层 owns 硬约束(取消/预算/硬超时),这些信号压过所有重试逻辑
