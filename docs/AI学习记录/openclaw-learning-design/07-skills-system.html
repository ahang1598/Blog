一 · 设计问题:能力越多,prompt 越爆

Agent 的"能力"= 它能做什么的工具/技能。一个通用 Agent 可能要会:读写文件、执行命令、搜索网页、调用 GitHub API、操作 Notion、画图、跑测试……几十上百个能力。

demo 级做法:把所有能力的完整说明塞进 system prompt。能跑,但很快撞墙:

  • Prompt 爆炸:50 个能力每个 200 字说明 = 1 万字,塞进 system prompt 直接吃掉大量上下文预算。
  • 缓存失效:能力列表是稳定前缀的一部分,但能力一增删,整段前缀缓存全废(见第③篇)。
  • 模型困惑:50 个能力全展开,模型反而难选对——信息过载降低决策质量。
  • 无法动态扩展:运行时想加个新能力(用户刚授权了某个集成),要么重启要么改 prompt。

本质矛盾:能力越多越好(功能强) vs prompt 越短越好(性能/质量)。全量注入无法两全。

二 · 分层设计:索引注入 + 按需加载

借鉴人类技能的运作方式:你不需要时刻记得每项技能的完整操作手册,只要知道有哪些技能、什么时候该用,真要用时再去查手册。Skills 系统就是这个设计。

┌──────────────────────────────────────────────────────────────────────┐ │ Skills 系统 · 索引 + 按需加载 │ └──────────────────────────────────────────────────────────────────────┘ [1] 能力发现 · skill 是带版本的资源 ┌──────────────────────────────────────────────────────────┐ │ 每个 skill = 一个独立资源包: │ │ · name + version(sha256 内容指纹) │ │ · 触发条件描述(什么场景该用) │ │ · 完整定义文件(SKILL.md / 操作指南) │ │ · 装在某目录,可被扫描发现 │ │ · 可独立更新(改了版本号就重新发现) │ └──────────────────────────────────────────────────────────┘ │ [2] 索引注入 · system prompt 只放元数据 ┌──────────────────────────────────────────────────────────┐ │ system prompt 的稳定前缀里,只放: │ │ │ │ · code-review (v1) │ │ · git-helper (v2) │ │ · doc-summary (v1) │ │ ... │ │ │ │ + 一句话规则:"需要某 skill 时,read 它的定义文件" │ │ → 元数据极小(几十字),不爆 prompt │ └──────────────────────────────────────────────────────────┘ │ 模型决定用某 skill ▼ [3] 按需加载 · 运行时才读完整定义 ┌──────────────────────────────────────────────────────────┐ │ 模型:我要用 git-helper │ │ → 调 read 工具加载 git-helper 的 SKILL.md │ │ → 完整定义进入当前上下文(作为工具结果消息) │ │ → 模型据此执行 │ │ → 只在真用时占上下文,不用就不占 │ └──────────────────────────────────────────────────────────┘

三层 vs 全量对比

全量注入(demo)

• 50 能力 × 200 字 = 1 万字常驻

• 增删能力 = 改 prompt = 缓存全废

• 模型信息过载

• 无法运行时扩展

• 适合:能力少(几个)

索引 + 按需加载

• 索引常驻(几百字)

• 增删只改索引段(可缓存)

• 模型只看相关 skill

• 运行时动态发现新 skill

• 适合:能力多(几十上百)

三 · 为何这么设计:三个核心决策

决策 1:为什么按需激活而非全量注入

这是 prompt 经济学和模型质量的双重优化:① 不用的能力不占上下文预算(省 token、保缓存);② 模型只看到相关能力,决策更聚焦(信息过载会降低模型选择正确工具的概率)。代价是多一次 read 调用(加载 skill 定义),但相比常驻 1 万字,这点延迟和成本微不足道。

决策 2:为什么 skill 要版本化(sha256 指纹)

skill 是会更新的资源(改了操作流程、修了 bug)。版本化解决三个问题:① 缓存确定性——索引里带版本,模型知道用的哪个版本,结果可复现;② 失效检测——内容变了 sha256 就变,触发重新发现和索引更新;③ 避免歧义——同名的两个 skill(不同来源)用版本区分。skill 是"带版本的可发现资源",不是"全局函数表"——这是它能动态扩展的基础。

决策 3:为什么要有"触发条件描述"而非只给名字

光给 skill 名字,模型不知道什么时候该用哪个。所以索引里每个 skill 还要有一句话触发条件("当需要做代码审查时用 code-review")。这让模型在不加载完整定义的情况下,就能判断该不该激活。这又是经济学:触发描述极短(一句话),但避免了模型为了判断而频繁加载 skill 定义。

核心取舍:索引 + 按需加载带来多一次工具调用(加载 skill)的延迟和发现/版本管理的复杂度,换来的是prompt 不爆、缓存稳定、模型聚焦、动态扩展。替代方案(全量注入)的失败模式是"prompt 爆炸 + 缓存全废 + 模型困惑 + 无法扩展"。接受延迟和复杂度,因为它把'能力数量'和'prompt 大小'解耦——这是 Agent 能成为通用平台而非单功能工具的关键。

四 · 完整示例:模型按需激活一个 skill

用户让 agent "帮我 review 这段代码"。agent 的能力里有 code-review skill。完整流程:

[system prompt 里的索引段] <available_skills> - code-review (v1): 当需要审查代码质量/找 bug/给改进建议时使用 - git-helper (v2): 当需要 git 操作(提交/分支/合并)时使用 - doc-summary (v1): 当需要总结文档/提取要点时使用 </available_skills> 规则:需要某 skill 时,先 read 它的定义文件再执行。 [用户消息] "帮我 review 这段代码:[code]" [模型推理 · turn 1] 识别意图 → 匹配 code-review skill 的触发条件 → 调 read 工具加载 code-review/SKILL.md [read 返回] code-review 的完整定义: · 审查维度(正确性/可读性/性能/安全) · 输出格式(分级问题:critical/major/minor) · 常见反模式清单 → 作为工具结果消息进入上下文 [模型推理 · turn 2] 基于完整 skill 定义 + 代码,执行结构化审查 → 输出 review 报告 [结果] code-review skill 只在这次任务占上下文, 下次不相关任务时它不占——按需激活。
关键洞察:code-review 的完整定义(可能上千字)只在这次任务占上下文。如果下一个任务是"提交代码",模型激活 git-helper 而非 code-review——每个 skill 按需进出,互不常驻。这使得 agent 即使有 100 个 skill,prompt 也只比"无 skill"多一个几百字的索引段。

六 · 面试者视角:如何答出生产洞察

结构化作答模板:
  1. 先点矛盾:"能力越多 prompt 越爆,全量注入无法两全——要么砍功能要么爆 prompt。"
  2. 给按需方案:"借鉴人类技能——只知道有哪些、什么时候用,真用时再查手册。system prompt 只放 skill 索引(名字+版本+触发条件),模型需要时 read 完整定义。"
  3. 主动谈经济学:"这样不用的 skill 不占上下文(省 token 保缓存),模型只看相关 skill(信息聚焦决策更好)。代价是多一次 read,但相比常驻 1 万字微不足道。"
  4. 主动谈版本化:"skill 是带版本(sha256)的可发现资源,不是全局函数表。版本化解决缓存确定性、失效检测、同名消歧。"
  5. 主动谈动态扩展:"运行时新装的 skill 被扫描发现,索引更新即可用,不需重启或改 prompt——这让 agent 能成为通用平台。"
