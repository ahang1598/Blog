01 — 执行摘要

七条路线，一个目标

这七个项目都想解决同一个问题——让 LLM Agent 拥有跨会话的长期记忆——但技术赌注截然不同。差异不在"做不做记忆"，而在把记忆当成什么：事实库、时序图、活图谱、类脑分层、虚拟文件系统、进程内语义图，还是团队级一体化资产平台。这一根本分野决定了它们各自的引擎、数据库选型与适用场景。

mem0 事实抽取

最成熟、生态最广的记忆层。LLM 单次抽取原子事实 → 哈希去重 → 实体链接 → 混合检索。25 个向量库 / 18 个 LLM / 11 个 embedder，开箱即用。

→ 通用集成 · 快速接入

zep 时序知识图

唯一把"时间"作为一等公民。事实带 valid_at/invalid_at，矛盾时 latest-wins。引擎是独立的 Graphiti（Neo4j）。注意：本仓库是云版集成 + legacy CE（已废弃）。

→ 事实会随时间变化

supermemory 活知识图

"活图谱"+ 用户画像 + 混合搜索。HNSW 内嵌引擎、Cloudflare 边缘原生。但核心引擎闭源，此仓库只是 SDK / MCP / 前端。

→ 托管开箱 · 个人大脑

agentmemory 编码 Agent 记忆

专为 Claude Code / Cursor 等 30+ 编码 Agent 设计。通过 hooks 静默捕获工具调用，零外部数据库（iii-engine + SQLite），4 层类脑记忆。

→ 给编码 Agent 装记忆

OpenViking 上下文数据库

字节跳动出品。把记忆/资源/技能暴露为 viking:// 虚拟文件系统，Agent 用 ls/tree/grep 浏览，L0/L1/L2 三级渐进加载省 token。Rust+C+++Python 多语言。

→ 企业级 · 可观测检索

Mandol 研究 SOTA

长期对话的进程内分层记忆。统一 KV+FAISS+BM25+SPLADE+图，检索时无 LLM。自报 LoCoMo 92.21% / LongMemEval 88.40% SOTA。Python，研究阶段。

→ 论文复现 · 无 LLM 检索

TencentDB 团队平台

腾讯出品。Agent 团队的一体化记忆平台：4 资产（Chat Memory/Skills/Wiki/CodeGraph）+ L0–L3 分层 + 透明 LLM 代理（agent 零代码改动）。standalone 模式零锁定，service 模式绑腾讯云。

→ 团队级 · 一体化资产
读前须知：七个项目的基准分数（LoCoMo / LongMemEval / PersonaMem 等）并非同类对比——mem0 是 Platform-only 数字、agentmemory 是检索 R@5（对比项用不同数据集）、Mandol 是论文 SOTA、supermemory/OpenViking 为厂商自报、TencentDB 仅有单一 PersonaMem 基准。横向比较时请参考"横向专题"章节的标注。

每个项目的完整画像

PROJECT 01
PythonTypeScriptFastAPIApache-2.0YC S24

mem0

生态最广的通用记忆层。从对话中抽取离散事实/偏好，去重、链接实体，存为向量+关键词+实体索引，查询时只返回相关子集。同一引擎驱动托管云、自托管 server 与 SDK。arXiv:2504.19413

核心功能

  • Memory CRUD（add/get/search/update/delete/history）+ 同步与异步一等公民 API
  • LLM 单次 ADD 抽取原子事实，写路径仅 1 次 LLM 调用
  • MD5 哈希去重 + spaCy 实体抽取 → 实体链接（sidecar 向量集合）
  • 混合检索：语义 + BM25 + 实体 boost + 可选 reranker，支持 explain=True
  • 多租户隔离（user/agent/run/actor_id）+ 严格身份键剥离防注入
  • 过程记忆（procedural_memory）、TTL 过期、高级元数据过滤（eq/in/wildcard/AND-OR）
  • SQLite 历史账本（每次增改删留痕）、多模态 vision、CLI、浏览器扩展

引擎 · 数据库 · 技术栈

向量库25 种：Qdrant(默认库)/PGVector(默认server)/Chroma/Milvus/Pinecone/Weaviate/Redis/ES/OpenSearch/FAISS/Mongo/Supabase/Upstash/Azure/Vertex/Databricks/S3 Vectors/Neptune/Turbopuffer/Oracle/Cassandra…
图库OSS V3 已移除（旧 Neo4j/Memgraph → 实体链接；富图功能转 Platform-only）
关系库Postgres（server）SQLite历史账本
LLM18：OpenAI(默认 gpt-5-mini)/Anthropic/Azure/Gemini/Bedrock/Groq/Together/DeepSeek/xAI/Ollama/vLLM/LiteLLM…
Embed11：OpenAI(默认)/Ollama/HF/Gemini/Vertex/Together/Bedrock/FastEmbed…
部署SDK / 自托管 server（FastAPI+Postgres+pgvector+Dashboard+JWT）/ 托管 Platform / CLI

优点

  • 生态广度断层领先：25 向量库/18 LLM/11 embedder，工厂模式 + register_provider 扩展点
  • 写路径高效：单次 LLM 抽取 + 批量嵌入 + 批量持久化，写成本最低之一
  • 身份/安全模型成熟（多次 CVE 式修复），敏感字段遥测脱敏
  • Python 与 TS SDK 功能对等；server 端运维打磨（限流、审计日志、Dashboard）

缺点 / 限制

  • OpenAI 默认耦合：gpt-5-mini + text-embedding-3-small 硬编码默认，server 仅打包 OpenAI/Anthropic/Gemini
  • OSS 移除图支持是架构 U 型转弯，旧用户须迁移到实体链接或买 Platform
  • 写路径 append-only（无 UPDATE/DELETE），改写副本会重复累积，靠调用方清理
  • 混合检索非统一：不 override keyword_search 的库（FAISS/Pinecone/Supabase）静默降级为纯语义
  • spaCy 强依赖（不装则实体 boost 全失）；main.py 单文件 3852 行；遥测默认开（posthog）
PROJECT 02
GoPythonNeo4jpgvectorApache-2.0

zep

把"时间"做成一等公民的记忆平台。事实携带 valid_at / invalid_at，新事实与旧事实矛盾时按"最新有效时间"胜出，旧边失效而非删除——可做"某时刻为真"的时序查询。引擎是独立的 Graphiti 项目（Neo4j）。

核心功能

  • 时序知识图：实体为节点、事实为带时间区间的边，矛盾 latest-valid_at-wins
  • 情景记忆（原始消息，Postgres）+ 语义记忆（抽取的时序图，Neo4j）分离
  • LLM 事实抽取；支持显式事实三元组（绕过抽取）
  • 可配置本体（ontology）：节点/边类型（默认 User/Preference/Event/Organization…）
  • 向量搜索 + MMR + Reciprocal Rank Fusion 重排
  • 批量摄入管道（Slack/文档/转录/邮件/JSON/CSV），惰性生成器不爆内存
  • 只读 MCP server（13 工具）+ 13 个框架集成（LangGraph/CrewAI/AutoGen…）

引擎 · 数据库 · 技术栈

引擎Graphiti（独立项目 github.com/getzep/graphiti），Zep Go server 是其 thin HTTP client
向量库pgvector（消息+消息向量）
图库Neo4j 5.22（实体+时序事实边）Graphiti 自身也支持 FalkorDB，但本仓库未接
关系库PostgreSQL（sessions/messages/users）
LLMOpenAI 默认(gpt-4o-mini)/Anthropic/OpenAI-compatible(Ollama/vLLM/LiteLLM/OpenRouter)
部署Zep Cloud（主）/ CE 自托管已废弃（4 服务 Docker）/ SDK(Python/TS/Go)
注意本仓库非产品本体：是云版集成+工具+冻结的 legacy CE，无当前引擎源码

优点

  • 时序性独一无二：valid_at/invalid_at + latest-wins，论文背书（temporal KG）
  • 情景 vs 语义存储分离清晰，各司其职（pgvector 消息 / Neo4j 图）
  • 重排扎实（MMR + RRF，非朴素 top-k）
  • zep-ingest 工程质量高：惰性生成器、客户端逐项校验所有限制、preview() 零 API 调用
  • 3 语言官方 SDK + 13 框架集成，各自独立版本

缺点 / 限制

  • 自托管 OSS（CE）已废弃：只能用付费云或直接用较低层的 Graphiti
  • CE 是 4 服务运维（Zep + Postgres+pgvector + Graphiti + Neo4j），负担重
  • 本体不可追溯（改需重灌新图）；矛盾解决仅 latest-wins（无置信度/权威加权）
  • 异步摄入 → no read-after-write（当轮内刚加的事实立即可检索不到）
  • 实体合并基于名字（语义别名"ROBOT-202" vs "PROTOTYPE-202" 会产生重复节点）；缺 created_at 默认摄入时间会永久破坏时间线
  • 两个 MCP server 均标记废弃；硬限制多（10k episode / 250 fact）
PROJECT 03
TypeScriptPythonCloudflareHNSW闭核引擎

supermemory

活的知识图谱 + 用户画像，Cloudflare 边缘原生。不是朴素向量 RAG，而是抽取事实、维护带版本/矛盾/自动遗忘的"活图谱"，按用户动态生成画像。自报 LongMemEval/LoCoMo/ConvoMem #1。但核心引擎不开源——此仓库只有 SDK / MCP / 前端。

核心功能

  • 事实抽取 + 时序追踪 + 矛盾解决 + 自动遗忘（活图谱）
  • 自动维护用户画像（静态事实 + 动态近期活动，~50ms）
  • 混合搜索：searchMode: "hybrid" 一查询同时返回 RAG 文档 + 个性化记忆
  • 连接器（实时 webhook）：Google Drive/Gmail/Notion/OneDrive/GitHub/Web Crawler
  • 多模态抽取：PDF/图像(OCR)/视频(转录)/代码(AST 感知分块)
  • 三种关系：Updates（版本链）/ Extends（丰富上下文）/ Derives（推断）
  • 容器标签（spaces）多租户隔离；MemoryBench 开源评测框架
  • 开放 MCP（含交互式 "MCP App" widget + OAuth provider）

引擎 · 数据库 · 技术栈

引擎闭核：托管 api.supermemory.ai 或自托管二进制，源码不在此仓库
向量索引HNSW 内嵌（O(log n)，亚毫秒）
本仓库存储Cloudflare R2缓存 + Durable Objects(SQLite,极小)
LLMOpenAI 默认(gpt-5.1)/Anthropic/Gemini/Groq/CF Workers AI/Vertex/Ollama-compat；托管用专有模型
Embed本地默认 bge-base-en-v1.5(768)/OpenAI/Gemini/bge-m3(多语言)。维度锁定（改需重灌）
部署托管平台 / 自托管二进制(port 6767,可 Ollama 全离线) / MCP Worker / SDK(TS+Py)

优点

  • 边缘原生：Next.js 经 OpenNext 部署 Workers + Durable Objects，全球低延迟
  • DX 优秀：记忆 + RAG + 画像 + 连接器 + 文件处理，单一 API
  • "memory vs RAG" 论证扎实，活图谱模型设计成熟
  • 自托管可全离线（本地嵌入 + Ollama），BYOK 覆盖 7+ LLM
  • 开放 MCP 实现成熟（含交互式 widget + OAuth），非薄工具壳
  • monorepo 工具链成熟（Turbo + Bun + Biome + Sentry + PostHog）

缺点 / 限制

  • 核心引擎不开源——本仓库无图引擎/摄入/嵌入索引源码，引擎实质闭核
  • CLAUDE.md 部分过时/误导（描述的后端路由与绑定在此仓库不存在）
  • Cloudflare 强耦合：两个 app 硬绑 Workers/OpenNext/DO/R2，他处重部署非平凡
  • 嵌入维度锁定（换 provider/model/dims 须重建数据目录，不匹配则拒启动）
  • 默认本地嵌入仅英文；连接器等平台特有功能不给自托管 → 推向付费
  • 基准分数与指标厂商自报，MemoryBench 也是自家框架，独立复现未提供
PROJECT 04
TypeScriptiii-engine零外部DBMCP 54工具Apache-2.0

agentmemory

给编码 Agent 装持久记忆，零数据库运维。为 Claude Code / Cursor / Codex 等 30+ 编码 Agent 设计，通过生命周期 hooks 静默捕获每次工具调用，LLM 压缩为结构化事实，BM25+向量+知识图混合检索，下次会话自动注入。基于 iii-engine。

核心功能

  • 12 个生命周期 hooks 自动捕获工具使用（SessionStart/PreToolUse/PostToolUse/Stop…）
  • 4 层类脑记忆：工作→情景→语义→程序（灵感来自睡眠巩固）+ Ebbinghaus 衰减自动遗忘
  • 三流混合检索（BM25 + 向量 + 知识图）RRF(k=60) 融合
  • 隐私过滤：存前剥离 API key/密钥/<private> 标签
  • 知识图抽取 + BFS 遍历；SHA-256 去重（5 分钟窗口）
  • 实时查看器（:3113）+ 会话回放；双向 MEMORY.md 桥；Git 快照 + 审计 + 治理删除
  • 多 Agent 协调原语：action leases / signals / routines / checkpoints
  • 团队记忆（命名空间共享/私有）；130 REST 端点 + 54 MCP 工具 + 15 skills

引擎 · 数据库 · 技术栈

引擎iii-engine v0.11.2（预编译二进制，非 cargo crate）；三原语 Worker/Function/Trigger，~260 个 mem::* 函数
向量内存 Map 暴力余弦（非向量 DB，无 ANN/HNSW），持久化为 base64 JSON
图自建知识图（图节点/边 + BFS 遍历）
存储零外部 DB：iii-state KV（file-based SQLite ./data/state_store.db），52 个 KV scope
LLM默认 No-op（无 LLM，仅合成 BM25 压缩）/Anthropic/OpenAI/Gemini/OpenRouter/本地(Ollama/LMStudio/vLLM)
Embed本地默认 all-MiniLM-L6-v2(384,离线免费)/OpenAI/Gemini/Voyage/Cohere/CLIP(图像)
部署npx 自托管 / Docker(distroless) / fly.io·Railway·Render·Coolify 模板 / 明确不做 SaaS

优点

  • 零外部 DB：SQLite + 内存索引，真单二进制，无须起 Postgres/Qdrant/Redis
  • Agent 覆盖最广：30+ Agent 共享一个 MCP 块 + 宿主专属 hook/skill 插件
  • 检索基准强且可复现：LongMemEval-S 95.2% R@5 / 98.6% R@10 / 88.2% MRR
  • 隐私优先（存前剥离密钥）；本地嵌入+本地 LLM 可达 $0/年
  • Token 高效（~1900/会话 vs 22K+ 的 CLAUDE.md，省 92%）
  • MCP 工具集最丰富（54）；多 Agent 原语罕见；1596+ 测试；CJK 感知搜索

缺点 / 限制

  • 硬依赖 iii-engine v0.11.2：冷门、不透明的预编译二进制（非标准运行时），绑定单一版本
  • 暴力内存向量无 ANN：线性 O(n) 余弦，大语料会降级（除非换 iii-database）
  • Windows 二等公民：connect 不支持原生，需 WSL2，安装脚本仅 sh
  • 默认 LLM 是 No-op：开箱非全功能（压缩/摘要/图抽取全关），需配 LLM 才完整
  • 基准非同类对比（自测 R@5 vs 他人不同数据集）；README 营销重，DESIGN.md 是网站样式非架构
  • hook 健壮性脆弱（Stop-hook 递归 bug 致 Claude Agent SDK 降为 opt-in）；iii console 无 auth
PROJECT 05
RustC++Python字节跳动AGPL-3.0

OpenViking

把 Agent 上下文当文件系统。字节跳动/火山引擎出品。记忆/资源/技能统一为 viking:// 虚拟 FS，Agent 用 ls/tree/find/grep 浏览；每个条目写入时算成 L0/L1/L2 三级，按相关性渐进加载。检索留下可观测的目录浏览轨迹。VikingMem 论文（VLDB 2026）。

核心功能

  • 统一虚拟文件系统 viking://，Agent 用文件系统原语浏览所有上下文
  • L0(抽象~100token)/L1(概览~2k)/L2(全量) 三级渐进加载，先判相关性再读全文
  • 目录递归分层检索：向量搜找最高分目录 → 逐层下钻 + 分数传播 + 收敛检测
  • 可观测检索轨迹：每次查询记录浏览路径（调试 agent 上下文利器）

PROJECT 06

Mandol

长期对话的进程内分层记忆，检索时无 LLM。基础层 + 高级抽象层（情景事实/实体关系图/分层 L1·L2 摘要）统一进单一语义图；检索走查询自适应路由 → 两阶段去噪 + 冲突解决 → token 约束上下文，全程不调 LLM。自报 LoCoMo 92.21% / LongMemEval 88.40% SOTA。论文 arXiv:2606.29778。

核心功能

  • 分层记忆模型：基础层（MemoryUnit/Space/显式隐式关系）+ 抽象层（情景事件链/语义实体图/用户偏好）
  • 进程内统一混合存储 SemanticMap+SemanticGraph：KV + FAISS dense + BM25/SPLADE sparse + 图拓扑，消除跨 DB IO
  • 三塔检索（分层 / 图 / 情景）+ 查询自适应路由 + 跨塔剪枝 + 统一 rerank
  • 智能量化检索：自适应路由 → 两阶段去噪 → 冲突解决 → token 约束，全程无 LLM
  • LLM 仅用于记忆构建（auto_builder）：分层 L1/L2 摘要、情景事实、实体关系图
  • Leiden/DBSCAN 聚类做实体/事实去重；RocksDB 分层分页冷数据
  • 可恢复 + checkpoint 的基准管道（LoCoMo / LongMemEval 独立 harness）

引擎 · 数据库 · 技术栈

向量内嵌 FAISS（IDMap,Flat）Milvus/Neo4j/zep-cloud 仅在 pyproject 供基准对比，运行时不导入
稀疏内存 BM25(rank-bm25) + SPLADE(sentence-transformers)
图进程内自建语义图（非外部图 DB）
持久化RocksDB(rocksdict) 唯一 payload 后端（分层分页，高/低水位淘汰）无存储后端切换契约
LLMOpenAI 兼容：DeepSeek/OpenAI/OpenRouter/DashScope(阿里)/CSTCloud + Standard/Reasoning Provider（仅构建用）
Embed本地 sentence-transformers+torch（MiniLM 快速 / 论文用 Qwen3-Embedding-0.6B）；rerank bge-reranker-v2-m3（native 或 vllm.sh 服务）
部署pip install mandol(PyPI 0.1.0) / uv sync 源码 / 库导入 / FastAPI demo(非生产) / 可选 vllm reranker 服务

优点

  • 基准驱动 + 同行评审：双 SOTA + 延迟胜（H800@10QPS 搜索均值 82.2ms vs MemOS 440.5ms）
  • LLM-free 检索：路由+量化+去噪不调 LLM，查询期成本/延迟极低
  • 统一混合存储：KV+向量+稀疏+图同进程，消除跨 DB IO；RocksDB 冷数据分页
  • 刻意用轻量检索模型（Qwen3-0.6B + bge-reranker），非数十亿参数
  • 模块清晰、Apache-2.0、惰性导入（import mandol 不拉 PyTorch/FAISS）、可恢复基准管道

缺点 / 限制

  • Alpha，研究级：明确"非生产服务"，API 在 0.x 会变
  • 环境严格：仅 Python 3.12、Linux 定向、满血需 CUDA 12 + Torch 2.8 + Linux x86_64 flash-attn（Win/Mac 装不上）
  • 重依赖：torch2.8/faiss/numba/scipy/spacy 大模型/igraph/transformers/langchain/llmlingua/bert-score
  • 无存储可移植性：仅 RocksDB，无可切换存储后端契约
  • 高级记忆构建期 LLM 昂贵（多次抽取 + LLM 去重），需付费 key 且规模慢
  • 无一等生产 server（FastAPI 仅 demo）；tests/ 仅 1 文件；单进程无扩缩容；基准依赖 LLM-judge
